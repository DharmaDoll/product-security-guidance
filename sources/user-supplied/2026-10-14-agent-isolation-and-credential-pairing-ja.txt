AIエージェント実行環境における多層隔離と権限ペアリング技術設計仕様書

1. 目的とセキュリティ基本原則（なぜ多層隔離とペア設計が必要なのか）

1.1 目的と本設計書の背景

現代のソフトウェア開発組織において、Claude Codeをはじめとする自律型AIエージェントの導入は、コード生成、リファクタリング、テスト自動化、インフラ構築などの開発サイクルを飛躍的に加速させている。しかし、AIエージェントの「自律性の向上」と「セキュリティリスクの増大」は表裏一体の構造をなしている。エージェントに広範なアクセス権限と自己決定権を与えるほど生産性は高まるが、同時に単一の指示ミスや外部からの悪意あるプロンプトインジェクション（Prompt Injection）によって、基幹インフラの破壊や秘密情報の流出という組織的破滅を招くリスクが急増する。

この相反する二項対立を克服し、組織の事業継続性を担保するためには、人間のリアルタイムな介在や監視に期待する運用を排除し、事前に計算された「多層隔離（Multi-layer Isolation）」と「権限ペアリング（Credential & Permission Pairing）」をインフラおよび開発環境のコア設計として組み込むことが戦略的に不可欠である。本設計仕様書は、AIエージェントを最高度の安全性を保ちながら最大限の自律性をもって運用するための、堅牢な技術アーキテクチャおよび実装仕様を定義する。

1.2 「人間による都度確認」の形骸化と事前設計への転換

開発現場において広範に蔓延している誤解が、「人間が画面の前で承認・確認ダイアログ（Prompt）を監視しているから安全である（attended check）」という認識である。しかし、この有人監視による安全保障は構造的に成立しない。

Anthropicが公表した大規模な利用データ分析によれば、ユーザーはエージェントが表示する許可プロンプトの約93%を検証することなく無条件で承認（Yesを押下）しているという衝撃的な実態が判明している。過剰な確認ダイアログの連続表示は開発者に深刻な「警告疲労（Alert Fatigue）」を引き起こし、セキュリティチェックとしての機能を完全に喪失させている。

さらに、人間とAIエージェントの間には、セキュリティ判断において埋めようのない4つの構造的ギャップが存在する。

比較軸	人間（開発エンジニア）	AIエージェント
処理速度（Speed）	思考・認知・手動出力を伴い、1操作ずつ緩やかに進む	秒間に数分〜数十分相当のコマンドやコード修正を連続・高速実行する
処理規模（Scale）	単一のコンテキスト・リポジトリに集中して作業する	並列セッションやマルチエージェントで複数リポジトリ・クラウド基盤を横断処理する
再帰性（Recursion）	自身の操作結果を客観的に検証しつつ段階的に進む	自身が出力したコードや設定を即座に再読み込みし、自己増殖的に再実行する
事後説明能力（Explainability）	実行理由や判断経緯を人間に論理的に自己口述・説明できる	非決定論的であり、context compaction（文脈圧縮）等で推論過程の履歴が消滅し得る

特に速度と規模の観点において、人間が1件の承認内容を精査・思索している間に、AIエージェントは数十件の不可逆な処理を完遂できるため、異常発生後に人間が手動で介入して被害を止める「事後確認」の運用モデルは原理的に破綻している。したがって、運用中の「席にいるから安全（attended check）」という錯覚を完全に捨て去り、拒否ルール（deny）を最優先とする事前の内部制御と、カーネルレベルで境界を強制する外部隔離によって、最初から危険な境界線を引く「事前設計（Pre-designed Security）」へと全面的に転換しなければならない。

1.3 クレデンシャル（持つもの）とパーミッション（できること）のペア設計原則

セキュリティ設計において最も陥りがちな構造的不備は、「持つもの（クレデンシャル）」の制限と「できること（パーミッション）」の制限を個別に設計することである。これらは相互に作用するため、絶対に分離せず「ペア」として同時に設計されなければならない。

【ペア設計の破綻パターンと相互依存メカニズム】

 [パターン A: クレデンシャルのみ厳格 / パーミッションが緩い]
   IAMロールを最小権限化 ───(しかし)───> Bash/コマンド実行が広く許可（`Bash(*)` 等）
   ⇒ AIが python -c 等でローカルの .env や他トークンを読み出し、迂回して悪用
   
 [パターン B: パーミッションのみ厳格 / クレデンシャルが過剰・長寿命]
   settings.json や Sandbox を強固に設定 ─(しかし)─> 永続的なAPIキーや広範なAWS権限を保有
   ⇒ 鍵自体が外部へ漏洩した際、AI環境の制限（Sandbox/hooks）を一切経由せず直接悪用される

  ★ 結論: 全体の安全性 = min(クレデンシャル強度, パーミッション強度)


「Polly Trap（Pollyの罠）」による構造的解明

この破綻メカニズムを端的に象徴するのが、Amazon Pollyを利用した音声化処理等で発生する自律停止トラブル（いわゆる「Polly Trap」）である。開発者がAIエージェントに長時間のループ処理を委ねて席を外した際、STS（Security Token Service）の一時クレデンシャルが途中で失効して処理が停止する。このとき、開発者には「止まらないようにクレデンシャルを広げる（広範な権限を与える）、または長寿命の永続キーを渡す」という強烈なインセンティブが働く。

しかし、過剰な権限や長寿命クレデンシャルを持たせた状態で自律実行を行わせると、「広範権限 × 自律実行 = 事故の構図」が完成する。片方のみを強化・緩和しても、全体の安全度は相互の「弱い方」の強度へ平準化（下方吸着）する。このトラップを解く唯一の鍵が、後述する「作業単位でのペア絞り込み」と「二段TTLモデル（上段：人間SSO 8-12h / 下段：自動更新短命トークン 15m〜数時間）」の統合設計である。

1.4 セキュリティの2軸分解：認証設計（漏洩防止）と権限委譲設計（暴走防止）

本仕様書では、「人が画面に張り付かなくても安全を作業が進められる状態（席を外せる自律性）」を成立させるため、セキュリティ設計を以下の相互補完的な2軸へ分解して定義する。

1. 認証設計（Secretの漏洩を防ぐ軸）: クレデンシャルの有効期限（TTL）、保管場所、取得・伝播経路を最適化し、AIエージェントのコンテキスト（LLM）に直接平文の秘密を持たせない、または極限まで短命化する軸。
2. 権限委譲設計（AIの暴走を防ぐ軸）: AIエージェントに許可する操作、拒否する操作、実行環境の物理・論理的境界を定義し、誤動作や不正誘導による破壊を防ぐ軸。

米国標準技術研究所の Zero Trust アーキテクチャ（NIST SP 800-207）におけるリソース機微度考慮（Resource Sensitivity Factor）に基づき、AIエージェントは「開発者の端末内で自分と同じOSユーザー権限で動作するが、無条件には信頼しない存在（semi-trusted internal actor）」として位置付けられる。絶対的な信頼を与えるのではなく、開発者本人の権限を委譲しつつも、内部制御と外部隔離の多層境界で厳重に囲い込むことが基本思想となる。

1.5 結論と次セクションへの接続

事前設計による多層防御の第一陣となるのは、AIエージェント内部でツール呼び出しの直前に決定論的に評価される内部制御層のパーミッション設計である。次セクションでは、Claude Code等のエージェント内部で評価される settings.json、hooks、CLAUDE.md の具象的な階層構造と自動化制御機構について解説する。

2. 内部制御層：パーミッション設計と自動化機構（settings.json / hooks / CLAUDE.md）

2.1 導入

内部制御層は、AIエージェントがツール（Read, Edit, Write, Bash, WebFetch等）を起動する直前に、アプリケーション内部で決定論的（または確率論的）に権限を判定する第一線防衛帯である。設定ファイルの階層構造と評価アルゴリズムを正確に理解し、決定論的な拒否ルールを最優先で配置することが、エージェントの暴走や危険操作を即座に遮断するための基盤となる。

2.2 settings.json の構成・階層構造と評価優先順位

内部制御の中核を担う settings.json は、設定の適用範囲に応じた4つのスコープ（階層）を持ち、厳格なオーバーライド優先順位に従ってロードされる。

設定の階層構造と適用順序

1. managed: 組織管理者が配布する絶対的優先設定（Linux: /etc/claude-code/managed-settings.json 等）。個人の設定ファイルやCLI引数によっても上書き不能。
2. user: ユーザー個人のホーム設定（~/.claude/settings.json）。全プロジェクトに跨って適用される。
3. project: リポジトリ直下に配置されるチーム共有設定（.claude/settings.json）。Gitにコミットして運用。
4. local: プロジェクト直下の個人用上書き設定（.claude/settings.local.json）。.gitignore に含めて運用。

評価の全社的順序としては、managed > CLI引数 > local > project > user となる。上位スコープで定義された設定値は、下位スコープの記述を強制的に上書きする。

ルールの評価順序（決定論的優先ルール）

パーミッションの評価は、設定が記述された階層を問わず、常に以下の優先順位で処理される。

\text{deny（拒否）} \longrightarrow \text{ask（都度確認）} \longrightarrow \text{allow（許可）}

deny に該当する操作は、他のどのスコープや allow ルールに記述されていても絶対的に拒否される。

起動ディレクトリ（cwd）の落とし穴と防衛策

project スコープ（.claude/settings.json）は、claude コマンドを実行したカレントワーキングディレクトリ（cwd）を起点として読み込まれる。例えば ~/work/repo-A で起動すれば repo-A の設定が読まれるが、親ディレクトリの ~/work で起動した場合、repo-A の project 設定（deny ルールを含む）は一切読み込まれない。

しかし、プロセス自体は同一のOSユーザー権限で動作するため、親ディレクトリから起動された場合でも repo-A 内の全ファイルにアクセスできてしまうという致命的なセキュリティギャップが発生する。これに対する運用上の防衛策として、チーム内での起動ディレクトリ統一手順の策定とともに、組織レベルでの managed 設定の強制配置、および後述するOSレベルの外部隔離層（Sandbox/Container）を併用して多層防御を完成させる必要がある。

2.3 機能別（ファイル・Web・コマンド）のパーミッション境界と限界

Claude Codeが保持するローカル機能は3系統に分類され、それぞれ固有の評価構文と表記ルールを持つ。

パス表現における表記ルールの相違

パーミッション設定と外部隔離層（Sandbox）では、パス表現のルールが異なるため厳格に区別しなければならない。

* settings.json の permissions（ファイル系）: 絶対パス表現は //abs（先頭ダブルスラッシュ）、設定ファイル起点相対パスは /x（先頭シングルスラッシュ）で記述する。
* OS Sandbox (sbx / Seatbelt / bubblewrap): 絶対パス表現は /abs（先頭シングルスラッシュ）、プロジェクトルート起点相対パスは ./x で記述する。

機能別比較マトリクス

機能系統	代表ツール	評価単位・指定構文	代表的記述例	限界とリスク
ファイル系	Read / Edit / Write	glob表記<br>（//abs 絶対パス, /x 相対パス）	Read(//**/.env*)<br>Edit(/src/**/*.ts)	インタプリタ経由（python -c）での読み出しは Read ルールをすり抜ける
Web系	WebFetch / WebSearch	ドメイン許可リスト<br>（domain:host 形式）	WebFetch(domain:github.com)	Bash経由（curl, wget）の通信は本ルールの対象外（Sandbox制御が必要）
コマンド系	Bash	コマンド名の前方一致文字列マッチ	Bash(npm run *)<br>Bash(git commit *)	パイプ、シェル置換、ラッパーコマンド、インタプリタ経由で容易に迂回可能

【仕様上の重要注記】settings.json における Write(...) 構文の無効性

settings.json の permissions 設定において、Write(...) という形式のパスルールは判定ロジックで使用されず、起動時に無視され警告が発出される。Claude Codeにおけるファイル書き込み権限の制御は、ファイルの新規作成も含めてすべて Edit(...) ルールで一元的に判定・制御されるという仕様上の罠が存在するため、設定記述時は Edit(...) に集約させなければならない。

コマンド系（Bash）の文字列マッチ判定の限界とEgress多層境界

コマンド系における文字列マッチ（例：Bash(npm *) や Bash(python *)）は最も脆弱な境界である。Bash(python *) を allow に指定した瞬間、AIエージェントは python -c "open('.env').read()" などのワンライナーを実行し、ファイル系で設定した Read(//**/.env*) の deny ルールを完全に迂回できてしまう。

この迂回リスクに対抗するため、外向き通信（Egress）制御は以下の3層の多層境界として統合設計される。

【Egress（外向き通信）多層境界アーキテクチャ】

  [ Layer 1: アプリケーション層 (permissions) ]
    `WebFetch(domain:github.com)` ─ WebFetchツールからの直アクセスを制限（Bashのcurlには無力）
               │
               ▼
  [ Layer 2: OS / プロキシ層 (Sandbox network) ]
    `allowedDomains: ["github.com:443"]` ─ Bashサブプロセスも含めた全通信をドメインレベルで強制DROP
               │
               ▼
  [ Layer 3: トークン・権限層 (GitHub App Device Flow / IAM Role) ]
    トークン自体の最小権限化 ─ パス・ドメイン制限を破られても、トークンスコープにより他リポジトリへの破壊を阻止


2.4 auto mode（審査モデル）のアーキテクチャと信頼境界

auto mode は、従来の default（読み取り以外は都度確認）と bypassPermissions（全自動・保護なし）の中間に位置する、二段ゲート構造の自動承認機構である。

【auto mode 判定パイプライン（二段ゲート構造）】

  [ツール呼び出し (Bash, Read, Edit, WebFetch 等)]
                     │
                     ▼
  ┌─────────────────────────────────────────────────────────┐
  │ 【第一段：決定論ゲート】                                  │
  │ permissions (allow / ask / deny) 評価                   │
  └─────────────────────────────────────────────────────────┘
         │                          │                   │
      (deny)                   (該当なし)            (allow)
         │                          │                   │
         ▼                          ▼                   ▼
     【即拒否】             ┌────────────────┐     【即実行】
                           │ 【第二段：確率論ゲート】 │
                           │ 審査モデル (classifier) │
                           └────────────────┘
                                  │
                       ┌──────────┴──────────┐
                       ▼                     ▼
                   [ Block ]             [ Allow ]
                       │                     │
                       ▼                     ▼
               (代替策試行/都度確認)      (ツール実行)


4ステップの判定パイプライン

1. 決定論的ルール評価: permissions の allow / ask / deny と照合。deny は即拒否、ask は即確認プロンプト表示、allow は即実行（Protected pathsへの書き込みを除く）。
2. 安全パターンの自動承認: 読み取り専用操作およびプロジェクトディレクトリ内の一般的な編集操作を自動承認。
3. 審査モデル（classifier）評価: 残りの操作について、コンテキストを含めて独立した審査モデルがリスクを確率論的に判定。
4. ブロックと代替試行: 審査モデルが Block と判定した場合、理由がClaude本体にフィードバックされ、別のアプローチが自動試行されるか人間に確認が委ねられる。

審査モデルの判定特性と決定論的 deny の不可欠性

Anthropicの実測データによると、審査モデルは良性コマンドの誤ブロック率を約0.4%に抑える一方、危険寄り操作の見逃し率（通過率）が約17%存在する。この確率論的な隙が存在するため、auto mode を導入している環境であっても、絶対的に実行させてはならない処理については決定論的な deny 設定を配置することが不可欠である。

自動dropルール、会話内境界、および信頼境界の仕組み

* 自動dropルール: auto mode 起動時、Bash(*) や Bash(python *)、パッケージマネージャの広範な実行許可ルール（Bash(npm *) 等）は安全のため自動的に無効化（drop）される。
* 会話内境界の失効リスク: プロンプト上で「don't push」などの指示を与えた場合、審査モデルはそれを遵守するが、長時間タスクに伴う context compaction（会話履歴の圧縮）によって指示がコンテキストから消失すると、制約が無効化される危険性がある。
* 信頼境界の強制: リポジトリ共有設定（.claude/settings.json や .claude/settings.local.json）内に記述された autoMode 設定や defaultMode: "auto" は無効化（無視）される。auto mode はユーザーのホーム設定（~/.claude/settings.json）または管理設定（managed）からのみ有効化できる。

2.5 危険操作の三系統遮断と hooks による補強

内部制御層を完成させるため、以下の「三系統の遮断ルール」を優先的に設定する。以下はそのままプロダクションに適用可能な完全な ~/.claude/settings.json 設定例である。

{
  "permissions": {
    "deny": [
      "Edit(//etc/**)",
      "Edit(//usr/local/etc/**)",
      "Edit(~/.bashrc)",
      "Edit(~/.zshrc)",
      "Edit(~/.bash_profile)",
      "Edit(~/.profile)",
      "Edit(~/.claude/settings.json)",
      "Read(//**/.env*)",
      "Read(~/.aws/**)",
      "Read(~/.ssh/**)",
      "Read(~/.gnupg/**)",
      "Read(~/.netrc)",
      "Read(~/.npmrc)",
      "Read(~/.config/gh/**)",
      "Bash(curl *://*)",
      "Bash(wget *://*)",
      "Bash(nc *)",
      "Bash(netcat *)"
    ],
    "allow": [
      "Edit(/src/**/*.ts)",
      "Edit(/src/**/*.js)",
      "Edit(/src/**/*.json)",
      "Bash(npm run test)",
      "Bash(npm run build)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "defaultMode": "default"
  }
}


hooks による動的制御と権限判定委譲

事前ルール化が困難な動的条件（例：「特定のGitブランチ時のみ push を拒否する」「コマンド引数のパラメータ構造を詳細検査する」）に対しては、hooks スクリプトを利用する。

* PreToolUse: ツール実行直前に走る。allow / deny / ask / defer を動的に判定して返却可能。
* canUseTool / --permission-prompt-tool: Agent SDKの canUseTool コールバックや CLIの --permission-prompt-tool オプションを用いて、ツール呼び出しの評価ロジックを外部プログラムやMCPツールへ全面的に委譲するアーキテクチャが構築可能である。

CLAUDE.md による「お願いベース制御」の限界

CLAUDE.md は自然言語による指示書であるが、これはあくまで「お願いベース」の制御に過ぎない。間接的プロンプトインジェクションによって外部から悪性テキストが混入した場合、CLAUDE.md の指示は容易に無効化・上書きされる。また、悪性指示が永続化するメモリポイズニング（OWASP ASI06）のリスクも抱えているため、絶対的な制約として CLAUDE.md に頼ってはならず、必ず settings.json の deny や hooks と組み合わせなければならない。

2.6 結論と次セクションへの接続

内部制御層は「エージェントの協力」を前提としたベストエフォートな防衛線であり、コマンドの迂回やプロンプトインジェクションを完全に防ぐことはできない。これらを抜けてきた攻撃や誤動作をカーネルレベルで止めるため、外部隔離層（OS Sandboxes / Container / MicroVM）の構築へと展開する。

3. 外部隔離層：OS Sandboxes・MicroVM・コンテナによる隔離戦略

3.1 導入

外部隔離層は、内部制御の不備やAIエージェントの「裏切り（誘導・誤動作）」を前提とし、OSカーネルやハイパーバイザレベルで物理的・論理的に実行環境を閉じ込めるレイヤーである。AIエージェントがどのような不正コマンドを生成・実行しようとも、OSレベルの境界を越えてホスト環境や機密データに破壊が及ばない強固な隔離帯を構築することが本層の目的である。

3.2 アーキテクチャ別隔離技術の比較評価

AIエージェント実行環境における隔離方式は、アーキテクチャ特性によって4分類される。

隔離方式	代表技術	ホストカーネル共有	起動速度	セキュリティ境界の強度と技術的実態
OS機能制限	macOS Seatbelt<br>Linux bubblewrap	共有する	即時	低〜中: Bashサブプロセスのみを制限。Read/Edit等の直接ツール呼び出しやすり抜けに弱い。
コンテナ分離	Docker, Podman<br>devcontainer	共有する	高速	低: 名前空間（Namespace）の分離でありセキュリティ境界ではない。Linux特権昇格脆弱性の増大、docker.sock マウントや docker コマンド許可はホストの任意実行と同義。
MicroVM分離	Docker Sandboxes (sbx)<br>Firecracker	共有しない	高速<br>（数秒）	極めて高: ハイパーバイザ隔離。ホストカーネル非共有、攻撃面極小化。信頼できないコード実行に最適な分離境界。
完全クラウド型	AWS EC2 / Fargate<br>クラウド開発環境	共有しない	中〜低	極めて高: ホストから完全に物理隔離。ローカルでの微調整容易性とのトレードオフ。

3.3 Docker Sandboxes（sbx）および OS 機構ラッパーの実践構図

Docker Sandboxes（sbx）は、MicroVM技術をベースとしたAIエージェント専用の隔離環境である。クローズドソースであるが商用無料利用が可能（一部ガバナンス機能を除く）であり、組み込みプロキシを介してシークレットをHTTPヘッダへ注入する構造を持つ。

Claude Codeにおける標準Sandboxの適用範囲

Claude Codeの標準Sandbox（macOSのSeatbelt、Linux/WSL2の bubblewrap）は、Bashツール経由で起動されるサブプロセスのみが対象であり、Read、Edit、WebFetch などの直接ツール呼び出しは対象外となる。主要設定キーとして filesystem（denyRead, denyWrite）、network（allowedDomains）、credentials（files, envVars）を持つ。

sbx CLI コマンド体系のライフサイクル一覧

sbx は直感的なCLIコマンド体系によりサンドボックスのライフサイクルを管理する。

コマンド	機能と用途
sbx login / logout	Dockerアカウントによる認証セッションの確立および全サンドボックスの停止とログアウト
sbx run [agent]	指定したAIエージェント（claude 等）をサンドボックス内で即座に起動
sbx create [agent]	サンドボックスインスタンスを作成（--name で名前指定、--kit でKit指定）
sbx exec [name] [cmd]	作成済みサンドボックス内で指定コマンド（bash 等）を対話実行
sbx ls / stop / rm	起動中サンドボックスのꗗ表示、停止、および削除
sbx policy	ネットワークおよびファイルアクセスポリシーの表示・変更（allow, deny, reset）
sbx secret	プロキシ経由で注入するシークレットの管理（set, ls, rm）
sbx template load	ローカルのDockerイメージをパイプ経由で sbx のVMテンプレートとして読み込む
sbx daemon	バックグラウンドで動作する sandboxd デーモンの管理（start, stop, restart）

環境変数定着化の罠と解決策（/etc/sandbox-persistent.sh）

sbx 内において、Dockerfileの ENV 命令で設定した非シークレットな環境変数（PS1 や MISE_ 等）は、VMの初期化タイミング等により一部上書き・消失するトラブルが発生する。非シークレット環境変数をVM内に確実に定着させるには、以下のように /etc/sandbox-persistent.sh へリダイレクト書き込みを行う必要がある。

# Dockerfile内での環境変数定着化の必須テクニック
RUN echo 'export PS1="[sbx:\W]\$ "' >> /etc/sandbox-persistent.sh
RUN echo 'export MISE_MINIMUM_RELEASE_AGE=7d' >> /etc/sandbox-persistent.sh


sbx secret のスコープ指定（グローバル vs サンドボックス）

sbx secret set において、グローバルスコープ（-g）とサンドボックススコープ（[sandbox-name]）では動作特性が異なる。

* グローバルスコープ（-g）: 登録したシークレットは、既存のサンドボックスVMを再生成（sbx rm & sbx create）しない限り反映されない。
* サンドボックススコープ（[sandbox-name]）: 既存の起動中サンドボックスに対して即時反映される。そのため、GitHub App Device Flow等で動的生成された短命トークンの更新運用には、サンドボックススコープ指定が必須となる。

Kit構造（kind: sandbox / mixin）と複数Kitの重ね合わせ

sbx では、ベースVMイメージを定義する kind: sandbox と、プロジェクト固有のオプショナル依存（CA証明書、開発ツール等）を定義する kind: mixin を分離して管理できる。

# sbx/kits/ccbase/spec.yaml (kind: sandbox の例)
schemaVersion: "1"
kind: sandbox
name: ccbase
sandbox:
  image: "custom/ccbase"
  aiFilename: CLAUDE.md
  entrypoint:
    run: [claude]
network:
  allowedDomains:
    - "api.anthropic.com:443"
    - "github.com:443"


# sbx/kits/cato/spec.yaml (kind: mixin の例)
schemaVersion: "1"
kind: mixin
name: cato
network:
  allowedDomains:
    - "clientdownload.catonetworks.com:443"
commands:
  install:
    - description: Install CATO Root CA
      user: "0"
      command: |
        curl -fsSL https://clientdownload.catonetworks.com/public/certificates/CatoNetworksTrustedRootCA.pem -o /tmp/cato.crt \
        && install -m 0644 /tmp/cato.crt /usr/local/share/ca-certificates/cato.crt \
        && update-ca-certificates


カスタムVMイメージをビルドし、ローカルパイプ経由で sbx へ読み込ませて複数Kitを重ね合わせ起動するワンライナー手順は以下の通りである。

# カスタムイメージのビルドとパイプ経由のテンプレートロード、およびMixinを重ね合わせた作成
docker build -t custom/ccbase ./sbx/kits/ccbase \
  && sbx template load <(docker image save custom/ccbase) \
  && sbx create ccbase --name my-project \
     --kit ./sbx/kits/ccbase \
     --kit ./sbx/kits/cato \
     .


3.4 データ分類（TLP 2.0準拠4レベル）に基づく多層隔離マトリクス

情報の機密度（TLP 2.0準拠）に応じたSandboxおよびContainerの採用基準を以下のように定義する。

データ分類レベル	定義と対象データの例	Sandbox設定基準	Container (devcontainer/OCI) 基準
CLEAR（公開）	自組織に著作権があり、公開予定・公開済みのコード	ON（標準）: 通信先を標準開発サイトに制限	任意: 個人の開発効率を優先し任意利用
GREEN（内部）	自組織所有の内部限定コード、社内ドキュメント	ON（厳格）: denyRead で機微ファイルを遮断	推奨: 複数人開発時は環境再現性のため利用
AMBER（機密）	機密データ、顧客情報、認証クレデンシャルを含むコード	ON（厳格）: ローカルファイルアクセスを最小化	必須: ホストの ~/.aws 等を読み取り専用マウント
RED（他者所有）	第三者所有コード、Untrustedな外部リポジトリ	ON（極限）: 外部通信を特定ドメインのみ許可	必須: ホストのSSH/クラウド鍵のマウントを厳禁

3.5 隔離層の脱出リスク（エスケープ）と復元性（可逆性）の設計

隔離層の破綻事例として、Anthropicレッドチーム演習における credentials 奪取率24/25成功例、OpenAI Codexの $HOME 削除事故、CVE-2026-39861（symlinkバイパス）、docker.sock マウントリスク、domain fronting が存在する。

これらに対し、以下の可逆性（Reversibility）設計を義務付ける。

1. 細分化コミットの徹底: 作業の区切りごとに細かくGitコミットを行い、git reset で即座に復元できる状態を作る。
2. 書き込み不可壁（denyWrite）: 絶対に消されてはならない設定やディレクトリを denyWrite ルールに指定する。
3. クラウド側の保護機構: S3バージョニング有効化、RDS削除保護（Deletion Protection）および自動スナップショット保持を必須化する。

3.6 結論と次セクションへの接続

環境隔離が確立された後、その内部で安全に認証情報（Secret）を取り扱うためのシークレット集中管理アーキテクチャへと展開する。

4. シークレット集中管理と認証アーキテクチャ（4段階モデルと二段TTL）

4.1 導入

AIエージェントに直接秘密値（APIキーや長寿命クレデンシャル）を持たせない「シークレット集中管理」の目的は、コンテキスト（LLM）に対する秘密値の露出を極限まで排除し、認証情報の寿命（TTL）を制御することで漏洩時のリスクを局限化することにある。

4.2 AIエージェントにおけるシークレット扱いの4段階モデル

AIエージェントが秘密値に接触するアプローチは、セキュリティの成熟度に応じて以下の4段階に進化する。

【シークレット扱いの 4段階進化モデル】

  [第1段階：直読み型] ───────► [第2段階：平文外部注入型] ──► [第3段階：ストア経由注入型] ──► [第4段階：非直読み型ブローカー]
  ・.env や鍵ファイルを        ・プロセス起動時に環境変数     ・AWS Secrets Manager 等から  ・LLMコンテキストは秘密を不保持
    AIが直接ファイル開く         として平文渡し               取得して一時注入              ・裏のSDK/MCPが決定論的に
  （最悪のリスク）             （従来コンテナの標準）         （取得経路の集中管理）          SigV4署名等を完結（到達点）


* 第1段階（直読み型）: .env や ~/.aws/credentials をAIが直接開いて読み取る形態（最悪のリスク）。
* 第2段階（平文外部注入型）: プロセス起動時に環境変数（export API_KEY=...）として渡す形態。
* 第3段階（ストア経由注入型）: AWS Secrets Manager等から取得し注入する形態。
* 第4段階（非直読み型ブローカー）: 到達点。AIモデル自身はクレデンシャルを一切見ず、裏側のSDKやプロキシ、MCPサーバが決定論的に認証・署名（SigV4等）を完結させる形態。

4.3 二段TTLモデルによる自動更新と無人実行の両立

Amazon Polly等での一時クレデンシャル切れによる停止トラブル（Polly Trap）を解決しつつ、過剰権限の保有を防ぐため、「二段TTL（Time To Live）モデル」を提示する。

【二段TTLモデルの概念図】

 [上段：認証セッション (Human-in-the-loop)]
  ・人間が定期的に再認証（例: `aws login` / SSO認証）
  ・有効期限: 8時間 〜 12時間（1日の業務時間に合わせる）
       │
       ▼ (トークンキャッシュを自動更新)
 [下段：短命クレデンシャル (Automated Agent Execution)]
  ・バックグラウンドでSDK/プロキシが自動取得・更新
  ・有効期限: 15分 〜 数時間（超短命化）
  ・万が一漏洩しても悪用可能時間を最小化


4.4 AWS連携と Docker Sandboxes における認証実践

Bedrock 連携（CLAUDE_CODE_USE_BEDROCK=1）の利点

Bedrock経由の利用と IAM Identity Center の連携は、Auditログの CloudTrail 統合、AWS内データ閉じ込め、および IAM ロールによる「第4段階ブローカー化」を同時に実現する。

ホスト aws login と Sandbox/Container マウントにおける競合解決策

AWS CLI/SDK操作における本命パターンは、ホスト側で aws login を実行し、~/.aws/ をコンテナ/Sandboxへ読み取り専用マウントする構成である。

ここで、Sandboxや settings.json で denyRead: ["~/.aws"] を愚直に適用すると、~/.aws/login/cache や ~/.aws/sso/cache 内の短命トークンキャッシュまで遮断され、SDKが動作しなくなるという競合が発生する。このトレードオフを解く解決策は以下の通りである。

1. 永続鍵の厳格遮断: 永続アクセスキーが含まれる ~/.aws/credentials を明確に拒否指定（denyRead）する。
2. 短命キャッシュの例外許可: トークンキャッシュディレクトリ（~/.aws/login/cache, ~/.aws/sso/cache）のみを読み取り許可（例外化）する。

以下は、この本命パターンを実装する完全な devcontainer.json の設定例である。

{
  "name": "Claude Code Secure Agent",
  "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
  "features": {
    "ghcr.io/anthropics/devcontainer-features/claude-code:1": {}
  },
  "remoteUser": "vscode",
  "containerEnv": {
    "CLAUDE_CODE_USE_BEDROCK": "1",
    "AWS_PROFILE": "my-sso-profile"
  },
  "mounts": [
    "source=${localEnv:HOME}/.aws,target=/home/vscode/.aws,type=bind,readonly"
  ]
}


Docker Sandboxes における sbx secret の制限

sbx secret はHTTPヘッダ注入（例: x-api-key）に適用範囲が限定されるため、AWS Signature Version 4（SigV4）のようなリクエスト署名型認証には対応できない。SigV4認証を要する場合は、上記のマウント方式または環境変数渡し（aws-vault 併用等）を選択する。

4.5 結論と次セクションへの接続

シークレット管理の体系化を受け、これらを統合した全体アーキテクチャの評価およびインシデント対応・ガバナンス構造へと展開する。

5. 総合評価マトリクス・インシデント対応と組織ガバナンス

5.1 導入

これまでに定義した内部制御、外部隔離、シークレット管理を統合し、実運用におけるインシデント対応体制および組織全体への安全な展開ガバナンスを構築する。

5.2 actor × layer 総合評価マトリクス

4つの主体（actor）と4つの制御層（layer）の交差における制御強度を評価する。

actor \ layer	① permissions<br>（内部制御）	② sandbox<br>（OS隔離）	③ container<br>（環境隔離）	④ secret store<br>（認証隔離）
Claude（本体）	強: allow/deny/hooks で直接制御	中: macOS/Linuxの各種ラッパー	高: devcontainer等で丸ごと隔離	高: Bedrock経由でキー非保持
MCPサーバ	中: .mcp.json / allowlist	中: @anthropic-ai/sandbox-runtime	高: コンテナ内独立プロセス化	極めて高: クレデンシャルブローカー化
hook（スクリプト）	高: PreToolUse 等の動的判定	低: ホスト側実行時は対象外	高: コンテナ内実行で制限	中: 通信ヘッダの動的制御
subprocess（Bash）	弱: 文字列回避・迂回リスク大	極めて高: カーネルレベルで全遮断	極めて高: OSリソース制限・Cap drop	高: 環境変数のunset / 短命化

Bash(*) を許可した場合は subprocess × sandbox セルへの依存度が致命的に増大するため、単一セルの設定変更が他セルへ与える波及効果を意識して多層防御を維持しなければならない。

5.3 過去のインシデント・脆弱性ケーススタディと対策から得られる洞察

* DataTalks.Club インフラ全消失事件（2026年2月）: 本番環境での terraform destroy 誤実行と削除保護・バックアップ不備により10万人分の受講者データが消失。洞察: deny ルールの未設定とAWS側の削除保護（Deletion Protection）欠如の組み合わせが致命傷となった。
* CVE-2026-21852（ANTHROPIC_BASE_URL 書き換え）: trust dialog 認可前に設定が読まれAPIキーが奪取された。洞察: 平文キー保持のリスクを実証。
* CVE-2025-59536（trust前のhooks/MCP実行）: 認可前のコード実行によるサプライチェーン攻撃。洞察: リポジトリ共有設定を信頼境界外として扱う必要性を証明。
* Mini Shai-Hulud 類似攻撃: .claude/settings.json や .mcp.json への攻撃永続化。洞察: 設定ファイル自体の書き込み保護（denyWrite）が不可欠。

5.5 チーム展開・組織ガバナンス方針

組織管理設定（managed-only）として、/etc/claude-code/managed-settings.json を用いて以下の管理キーを設置し、開発者個人による上書きを強制遮断する。

* disableAutoMode: "disable": 未承認の auto mode 利用を組織一括で禁止。
* disableBypassPermissionsMode: "disable": --dangerously-skip-permissions の利用を全社的に遮断。

リポジトリ共有設定（project スコープの .claude/settings.json や .mcp.json）はGitで共有するが、allow と deny のみに限定し、個人の秘密値や過剰な権限昇格を含めないガイドラインを策定する。

自律性を活かしつつ組織的事故を防ぐ鍵は、「協力前提」の内部パーミッション設計と「裏切り前提」の外部隔離・短命クレデンシャル機構を正しくペアリングすることにある。組織は本仕様書で定義されたマトリクスと停止層に基づき、CloudTrailやOpenTelemetryによる継続的監査体制を維持しながら、安全なAI駆動型開発環境の構築を推進すべきである。
