# 参照資料の方針

## 参照資料の役割

| 区分 | 意味 | 書き方 |
|---|---|---|
| 規範資料 | 規格や仕様が直接要求・定義する内容 | バージョンと変更不能な改訂を示す |
| 調査資料 | 脅威、例、検証方法を補足する資料 | 規範的な合格条件へ昇格させない |
| 一次資料 | 製品、プロトコル、インシデントの一次情報 | バージョンまたは確認日を示す |
| ポートフォリオ分析資料 | 分野の偏り、空白、学習経路を見つける資料 | コントロール要件へ自動変換せず、分析軸としての採否を示す |
| リポジトリ内の統合資料 | 複数コントロールを攻撃経路や受け渡しで読み直した資料 | 元のコントロールを正本とし、対応範囲を誇張しない |
| リポジトリでの解釈 | 現場の設計判断へ適用する解釈 | リポジトリ独自の判断であることを明示する |
| 導出した洞察 | 複数の検討から得た再利用可能な洞察 | 参照資料に書かれた事実と混ぜない |

参照資料記録の正本は[`sources/`](../sources/README.md)に置きます。コントロール側には参照資料IDと、
その資料がセキュリティ特性へどう影響したかだけを置きます。フレームワークとの関係は
[`mappings/`](../mappings/README.md)へ分離します。

## ルール

- 参照資料IDは、題名に含まれる目立つ語ではなく、このリポジトリで資料が果たす主な役割を表す。
- 特定領域のIDは、その領域だけで使う資料に付ける。複数領域の偏りを調べる資料には、横断的な役割を表すIDを付ける。
- 資料の主な役割を見直してIDを変更した場合、旧IDは移行台帳だけに残し、新しい索引やリンクの別名として温存しない。
- 一次資料を優先し、二次記事だけで製品仕様やインシデントの時系列を確定しない。
- 随時更新される文書や製品画面には確認日を付け、古い記述を現在の仕様として引き継がない。
- 外部フレームワークの文章を大量に複製せず、必要な範囲を要約してリンクする。
- 参照資料が特定のツールを例示しても、それをコントロールの唯一の実装例にしない。
- 参照資料間の不一致、不明点、未検証箇所を隠さない。
- コントロール本文を短くするときも、参照仕様、参照した版、採否、除外理由を削除しない。
- 変更不能な改訂を特定できない製品文書には、確認日と`re-review-required`を明示する。
- コミュニティの互換性一覧で機能を発見しても、製品挙動は公式仕様で確認する。

## 参照資料を設計へ反映する流れ

```text
参照資料記録
  -> 資料の役割と信頼境界を決める
  -> 採用／変更して採用／不採用を記録する
  -> 脅威シナリオ、設計判断、セキュリティ特性へ結び付ける
  -> 実装例では製品仕様を追加確認する
  -> 評価では実環境の証拠を別に収集する
```

資料へのリンクだけでは、設計へ反映したことになりません。成果物側から、少なくとも次を説明できるようにします。

1. その資料を、要件、脅威、製品仕様、実装候補、ポートフォリオ分析のどれに使ったか。
2. どの判断を採用し、このリポジトリの境界に合わせて何を変更したか。
3. 採用しなかった推奨と、その理由。
4. 資料では証明できず、別の仕様、テスト、実環境の証拠が必要な範囲。

セキュリティ特性の直接の根拠は`control.yaml`の`source_refs`へ記録します。ポートフォリオ上の位置や
攻撃段階を確認するだけの資料は、直接の要件根拠と混ぜず、`analysis_lenses`または横断マッピングへ記録します。

## 二つの横断分析

[`REF-PORTFOLIO-001`](../sources/README.md#ref-portfolio-001)の七つのレイヤーは、リポジトリ全体の偏りと空白を
確認するために使います。個別要件の出典や、AIセキュリティを網羅したという主張には使いません。

[`LOCAL-SUPPLY-CHAIN-ATTACK-STAGES`](../sources/README.md#local-supply-chain-attack-stages)の十二段階は、
攻撃経路とコントロール間の受け渡しを確認するために使います。各コントロールの合格条件は、引き続き
コントロール記録と`control.yaml`が定義します。

人向けの分析結果は[横断分析の軸](ANALYSIS_LENSES.md)、機械可読な関係は
[`analysis-lenses.yaml`](../mappings/analysis-lenses.yaml)に置きます。空白は成果物を水増しして埋めず、
未移行、別コントロール、組織側の証拠のどれが必要かを記録します。

## 移行パイロットにおける参照資料の状態

`91fdb7661b38723ce6fb38da93cf3c68b701e521`から知識を再編集しています。
旧成果物でレビュー済みだったマッピングや製品仕様を新構造へ移しただけで、再レビュー済みとは扱いません。
製品固有の実装例は、採用時に公式資料を再確認します。

パイロット対象外の記録は、対応する成果物を移行するまで旧一覧に残します。
