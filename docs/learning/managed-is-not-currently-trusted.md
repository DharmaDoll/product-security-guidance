# Managed is not currently trusted

「管理対象の端末です」と「今この資産へのアクセスを許可できます」は、別の判断です。

## 登録は残り、観測が止まった

ある開発者の端末は、導入時に暗号化と監視を有効にし、台帳にも登録されました。
その後、更新の延期が続き、管理基盤との通信も途絶えました。しかしソース管理へのセッションは有効なままです。

ここで外部コードを通常の開発環境で実行し、そのコードが利用者のファイルやセッションへアクセスできたとします。
攻撃者は管理者権限を得なくても、利用者が読めるソースや変更できるリポジトリを狙えます。
登録時の良好な記録は、その処理が動いた時点の状態を説明していません。

## 三つの事実を分ける

- **登録**：誰が管理するどの端末か。対象一覧の事実です。
- **観測**：いつ、何を、どこから確認したか。取得できなかった状態も含みます。
- **アクセス判断**：その観測を受けて、どの資産への操作をいつまで許可するか。資産側で強制する判断です。

MDMに登録済みでも、古い観測を許可条件として使い続ければ、判断は変わりません。
また新規ログインだけを拒否しても、既存セッションや別途発行した認証情報は個別に確認する必要があります。

## 違う攻撃には違う境界が効く

電源を切った暗号化済み端末を盗み、回復鍵も持たない攻撃者には、ディスクからデータを読む障壁があります。
一方、ログイン済みの利用者として動く悪意あるコードは、利用者が読めるデータを扱えます。
「暗号化済みだから、認証情報の悪用も防げる」とは判断できません。

逆に、外部コードへソース管理の認証情報も対象ファイルも渡していなければ、この例の直接の読み取り経路は成立しません。
それでも隔離環境の迂回や、許可した書き込み先を通じた改変は別途確認します。

## レビューで問うこと

端末の観測が途絶えたとき、誰が気付き、どの権限がどこで止まるでしょうか。
端末がオフラインでも、サーバー側で止められる権限は何でしょうか。
接続が戻らなければ完了を確認できない消去・隔離と、既に実行されたソース変更をどう区別するでしょうか。

具体的な設計は[Managed developer endpoint](../../engineering/source-protection/managed-developer-endpoint/README.md)、
権限の停止は[Source credential lifecycle](../../engineering/source-protection/source-access-credential-lifecycle/README.md)で検討します。
この教材は[利用者提供資料のリポジトリによる解釈](../../sources/README.md#ref-developer-endpoint-baseline-001)です。
攻撃段階1の端末から段階2のソース管理、段階12の調査へ続く例であり、実際の組織への導入を評価したものではありません。
