# Credential is delegated authority, not a string

## 洞察

認証情報の安全性を「秘密値を漏らさないこと」だけで評価すると、過剰権限、長い有効期間、
広すぎる利用プロセス、失効漏れを見落とします。認証情報は、サービス提供側が受け入れる委任された権限です。

```text
認証情報
  = 身元の証明または権限の付与
  + 到達できるリソース
  + 許可された操作
  + 有効期間
  + 利用できるプロセスとセッション
```

## 具体例

同じ保護された場所に保存された二つのトークンでも、一方が一つのリポジトリへの読み取りだけ、
もう一方が組織全体への書き込みを許可するなら、窃取時のリスクは同じではありません。

逆に、短命なトークンでも親IDE全体へ渡し、すべての拡張機能が取得できるなら、利用プロセスの境界は広いままです。

## 設計レビューへの応用

- シークレットスキャナーの有無だけでなく、現在有効な権限の棚卸しを見る。
- トークン種別の名称ではなく、対象リソース、権限、有効期限を確認する。
- 利用者とワークロードのIDを分ける。
- 保管場所とプロセスへの受け渡しを分けて図示する。
- ローテーション、有効期限切れ、失効、セッション無効化を別の状態として追う。
- 監査事象と現在有効な権限を、同じ証拠として扱わない。

## 他領域への適用

この見方はソース管理用トークンだけでなく、クラウド認証情報、レジストリトークン、署名権限、
MCP認証情報、データベース接続、一時承認にも使えます。

[横断分析の軸](../ANALYSIS_LENSES.md)では、この見方を開発端末、AIツール、ソース管理、CI/CDのID、
レジストリ、デプロイの間で権限が引き継がれる箇所に適用します。一つの段階で権限を狭めても、
次の段階がより広い別の認証情報を発行するなら、攻撃経路全体の権限は狭まりません。

## 限界

権限を狭めても、認証情報の窃取自体は防ぎ切れません。端末保護、フィッシング耐性のある認証、
実行時の隔離、検知、インシデント対応を組み合わせます。
