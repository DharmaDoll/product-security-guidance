# Cooldown buys observation time, not trust

## 洞察

依存パッケージの待機期間は、一定時間が経過した成果物を信頼済みに変えるコントロールではありません。
公開直後には不足している外部からの警告が現れるまでの時間を確保するコントロールです。

```text
公開
   |
   |  判断材料が乏しい期間
   |  検知／報告／公開停止／注意情報が現れ得る
   v
レビュー済みの観測境界
```

## なぜ区別が必要か

「7日経過＝安全」と扱うと、長期潜伏型マルウェア、タイポスクワッティング、侵害されたレジストリ、
成果物のすり替えを見落とします。一方で、時間の経過はパッケージの内容を保証しなくても、
公開直後の自動採用を避けるという独立した価値を持ちます。

## 設計レビューへの応用

- 何時間待つかだけでなく、どのような警告が現れるのを待つのかを言語化する。
- 公開時刻を提供する情報源が信頼できるか確認する。
- 待機期間の判定をコード実行より前に置く。
- スキャナー、プロキシの評価、ロックファイル、完全性確認が提供する保証を分ける。
- 緊急修正では、全体の規則を弱めず、正確な一つのバージョンだけを期限付きで扱う。

## 他領域への適用

同じ考え方は、新しいコンテナイメージ、ツールのプラグイン、AIモデル、エージェント用スキル、
ブラウザー拡張機能、GitHub Actionsなどの公開直後のリスクにも応用できます。ただし成果物ごとに、
信頼する公開者の識別方法と実行境界を定義する必要があります。

[横断分析の軸](../ANALYSIS_LENSES.md)では、待機期間を依存関係の選定段階に置き、CI、ビルド、
リリース、本番環境へは「待機期間を通過した」という限定的な判断だけを渡します。後続工程が必要とする
完全性、来歴、署名、実行時検知まで、時間の経過から推論してはいけません。

## 限界

観測期間の長さに普遍的な正解はありません。更新速度、活発な悪用、警告情報の質、
代替コントロールを踏まえて決めます。時間が経過したという事実だけを、正式な信頼の根拠にはしません。
