# 文書品質

## 日本語の書き方

- 本文は日本語だけで意味が通るように書く。英語は製品名、規格名、設定キー、状態値など、正確さのために必要な場合に限る。
- 専門用語より先に、読者が何を判断・確認するのかを平易な日本語で書く。検索に必要な英語名は、その後に括弧で添える。
- control title、domain名、pattern名、検索・参照で使う重要キーワードは、無理に日本語化しない。
  `Dependency release cooldown`、`Untrusted PR boundary`、`Source credential lifecycle`のように、英語のまま読者が探せる名前を優先する。
- 英語の名詞へ日本語の助詞や動詞を直接つなげない。たとえば`reviewする`ではなく「レビューする」、
  `credentialをrevokeする`ではなく「認証情報を失効させる」と書く。
- 独自の成果物名は、名前として定着させたい表記を先に決める。英語名を正本にした場合は、本文で日本語の説明を添える。
- `authority`、`scope`、`boundary`のように訳し分けが重要な原語は、文脈に応じて「権限」「適用範囲」
  「境界」と訳し、原語だけで説明を済ませない。
- 一文に英語の概念語を並べず、誰が、何を、どの条件で行うかを日本語の文として組み立てる。

## 有用な文書の判定

成果物を追加する前に、対象読者が読み終えた後で何を判断できるようになるかを一文で説明します。
説明できなければ作成しません。

## コントロール記録

- 一つのセキュリティ上の成果に焦点を当てる。
- 脅威主体または障害要因、攻撃経路、影響を受ける資産を具体化する。
- 合格候補、直接の不合格、証拠不足、隣接コントロールの不合格を混同しない。
- 製品固有例をコントロールの唯一の実現方法にしない。
- 「導入する」「適切に設定する」だけで終わらせず、守るセキュリティ特性を示す。

## 学習ノート

- 主なコントロールのディレクトリへ`learning.md`として置き、コントロールから自然にたどれるようにする。
- 一つの具体的なシナリオを最後まで追ってから抽象化する。
- 用語をシナリオ内の主体、データ、操作へ結び付ける。
- よくある直感的な誤りと、なぜ誤りかを残す。
- 移行後の再学習で見つけた問いや誤解は、まず対応する`learning.md`へ戻す。
- 複数のコントロールにまたがる場合は問いを分けるか正本へリンクし、同じ教材を複製しない。
- 複数の教材で再利用価値が確認できてから洞察を、具体的な技術経路を試す価値が確認できてから実装例を検討する。
- 生の会話ログ、挨拶、機械的な言い直しを保存しない。
- コントロール本文の複製にしない。

## 設計パターン

- アーキテクチャの選択肢とトレードオフを示す。
- どの境界でセキュリティ上の判断を強制するかを示す。
- 脅威と緩和策を別々の一覧へ分断しない。
- 一製品の画面操作だけで一般パターンを定義しない。
- コントロールとのマッピングからパターンを逆生成しない。

## 実装例

- 対象プラットフォームと対応バージョンを明示する。
- 変更するファイル、設定、サービスと、実効性が生まれる場所を示す。
- 手元または使い捨ての対象へ入れる最短手順と、元へ戻す方法を示す。
- 安全な入力と無効なcanary等を使い、主張する成功・拒否・失敗の少なくとも代表経路を観測できるようにする。
- テストは、実際に観測できるセキュリティ特性だけを検査する。
- サンプルを本番導入の証拠と表現しない。
- 未対応のプラットフォームを埋め草として列挙しない。

## 診断で確認する項目（異常時テスト）

「できてはいけないこと」が実際に起きないかを確認する項目です。禁止した操作や異常な入力を試し、
拒否されること、迂回できないこと、必要な情報がなければ処理を許可しないことを確かめます。
一般に`Negative test`と呼ばれるため、検索できるよう用語も残します。脆弱性診断や設計レビューで使う
チェックリストだけでも成果物として十分であり、実装例、テストコード、実行結果を必須にしません。

- 各項目は「何を試すか」と「何が起きてはいけないか」が分かるように書く。短い箇条書きでよく、固定のテンプレートは要求しない。
- 例えば「一般利用者が他人の請求書IDを指定しても、内容を取得・更新できないか」「認可情報の取得がタイムアウトしたとき、処理を許可していないか」のように書く。
- 製品に依存しない項目はコントロールのセキュリティ特性や直接の失敗に結び付ける。構成に依存する項目は設計パターン、製品固有の手順・コードは実装例、実環境の実施結果は評価へ置く。同じ項目を複製せず、詳細の正本へリンクする。
- 項目を書いたことを、診断の実施済み、拒否動作の確認済み、脆弱性がないことの証拠にしない。まだ試していなくても、確認項目としては完成してよい。

## 参照資料と横断分析

- 参照資料へのリンクだけでなく、採用、変更して採用、不採用、限界を記録する。
- 規範要件、製品仕様、脅威調査、実装候補、ポートフォリオ分析の役割を混同しない。
- ポートフォリオ上のレイヤーや攻撃段階との関係を、コントロールへの合格や導入済み状態と表現しない。
- `直接`、`隣接`、`受け渡し`、`空白`を区別し、空白を一般論や空ファイルで埋めない。
- 攻撃経路では、一つのコントロールが変える矢印と、変えない前後の矢印を示す。

## 禁止する水増し

- READMEの文字列だけを確認するテスト。
- `secure: true`を受理するだけの検証器。
- 同じ段落を複数のコントロールへ複製すること。
- 講義で生じた一般論を、利用場面が育つ前に独立成果物として切り出すこと。
- 空の`secure/`、`insecure/`、`tests/`、`expected-results/`。
- 「TBD」を隠すための一般論。

## レビュー時の問い

1. 最初の画面で「何を問う成果物か」が分かるか。
2. セキュリティ効果が生まれる強制点を特定できるか。
3. 読者が実装方式を選ぶ材料があるか。
4. 別成果物と重複していないか。
5. 参照資料に書かれた事実と、リポジトリでの解釈が区別されているか。
6. 自動化できないことを、形式的な自動化で隠していないか。
7. 主要な判断を、参照資料の版、採否、限界までたどれるか。
8. 攻撃段階の前後で、別のコントロールへ引き継ぐ責任が明確か。
9. [具体化判断](ARTIFACT_MODEL.md#主題ごとの具体化判断)に照らし、読者に必要な設定・コードを省略していないか。逆に不要な実装を増やしていないか。
10. 文書の完成、必要な実装の残作業、確認項目の完成、実際に試した結果を区別しているか。
11. 実装例は手元または使い捨ての対象へ導入でき、主張する代表的な挙動と解除方法を読者が確認できるか。
