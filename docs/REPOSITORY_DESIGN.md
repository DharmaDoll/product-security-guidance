# リポジトリ設計

## 三つの入口

### コントロールの見方

`controls/`は「何を満たすべきか」を扱います。コントロールは特定のツールや一つの実装方式に依存せず、
セキュリティ上の成果を診断する軸です。

### 設計・実装の見方

`engineering/`は「どのように失敗し、どう設計すべきか」を扱います。パターンはフレームワークの一覧から
機械的に作らず、システム、インシデント、信頼境界、繰り返し発生する設計上の問題から見つけます。

### 横断分析の見方

`docs/ANALYSIS_LENSES.md`は「どの分野が空白か」「攻撃連鎖の前後で何を引き継ぐか」を扱います。
ポートフォリオの七つのレイヤーと、サプライチェーン攻撃の十二段階を使いますが、外部資料の章立てを
トップレベルのディレクトリや新しいコントロールへ自動変換しません。

### 後から評価する対応関係

マッピングはコントロールとパターンを独立に理解した後で作ります。マッピングの有無を成果物の成熟度や
組織導入の条件にしません。

横断分析の関係も同様です。`直接`は分析軸との関係を示すだけで、実装済み、導入済み、完全な対応範囲を意味しません。

## 分類領域の選び方

AI Development Securityの適用範囲は[Security scope](SECURITY_SCOPE.md)を正本とします。
AIを使う開発環境を本PJで扱い、製品自体のAI securityはai-security-foundryへ委ねます。10 domainの名称と一般的なApplication Securityの範囲は維持します。

ディレクトリは、外部フレームワークの章構成やツール名ではなく、読者が問題を探す場所に合わせます。
複数領域にまたがる関係は文章を複製せず、リンクとマッピングで表現します。

[ADR-001](#adr-001)に従い、現行の10 domainを基本分類とします。名称と一覧は
[Domain一覧](../controls/README.md#domain一覧)を参照してください。
Control記録は主な一つのdomainへ置きます。工程をまたぐengineeringはテーマ名で直下へ置き、複数domainとの関係はControl ID・リンク・マッピングで示します。
学習ノートは主なcontrolの隣に`learning.md`として置きます。複数controlに関係する教材は、それぞれの問いへ分けるか
一方の正本へリンクし、同じ本文を複製しません。評価・参照資料も成果物の役割に沿って置きます。
基本分類の追加・変更は、読者の探索性と既存領域の境界を検討してADRに記録します。

Secure Designは、個別システムの脅威モデルを作る場所ではありません。システム情報からDFDやSTRIDEなどの脅威候補を生成する作業は
[ModelForge](https://github.com/DharmaDoll/ModelForge)で進めます。本PJでは、そこで見つかった問題や既知の悪用経路について、
再利用できるセキュリティ上の成果、強制点、設計の選択肢を整理します。脅威候補をそのまま新しいcontrolへ変換せず、
既存controlとの重複と読者が必要とする判断を確認します。[参照した版と限界](../sources/README.md#ref-modelforge-001)も記録します。

### Secure CodingとASVS

Web application／web serviceに共通するSecure Codingの検証観点は、版を固定した[OWASP ASVS 5.0.0](../sources/README.md#spec-owasp-asvs-5-0-0)を主な参照先とします。認証、認可、入力処理などのASVS要件を、このPJのcontrolへ一対一で書き直して網羅しません。必要な要件IDと原文はASVSへたどり、PJ側には具体的な失敗経路、強制点、設計上の選択、教材、診断観点、実装で確認できたことを残します。ASVSの章立てを10 domainの代わりには使いません。

Secure Codingには独立controlを置かず、要件の入口をASVSへ統一します。個別技術の設計、教材、診断観点、実装例はengineeringに置き、その主題に直接関係する一次資料を使います。[Unicode source review](../engineering/unicode-source-review.md)もこの扱いです。ASVSがUnicodeなどの個別技術をすべて網羅するとは主張しません。分類は現行10 domainのままです。

利用者が後日提供する経験由来の脆弱性診断チェックリストは、ASVSに上書きされない独立した入力です。原本を受領した後に出所・版・公開可否を確認し、[進め方](MIGRATION_PLAN.md#secure-codingの進め方)に従って対応関係を評価します。現在は項目も対応範囲も推定しません。

| 軸 | 答える問い | 使う場所 |
|---|---|---|
| 10 domain | 今取り組む分野の何を読めばよいか | Controlの分類と索引 |
| 七つのレイヤー | PJ全体がどの観点に偏り、何が欠けているか | ポートフォリオ分析 |
| 十二の攻撃段階 | 脅威がどの境界を越え、前後のcontrolへ何を渡すか | 攻撃経路・受け渡しの分析 |

レイヤーと攻撃段階はdomainを横断する分析軸です。未移行domainも一覧で明示しますが、
内容がない領域のディレクトリやREADMEは作りません。「未移行」は旧リポジトリの未実装や組織の未導入を意味しません。

## コントロール記録の長さ

行数を機械的に制限しませんが、一度の読書で境界と実装判断をつかめることを目標にします。
具体的なシナリオ、Q&A、製品別の画面名、コマンド、テスト項目表が必要になった時点で、別の成果物へ分けます。

## 設計パターンの構成

パターンは必要な範囲で次を含みます。

```text
利用場面
  -> 適用範囲と前提
  -> 資産と信頼境界
  -> 脅威と悪用経路
  -> セキュリティ不変条件
  -> 推奨構成とコントロールの配置
  -> 実装方式とトレードオフ
  -> 観測すべき状態
  -> 残余リスク
```

製品固有の値やコマンドは`implementations/<platform>/`へ置きます。

## 生成物

人が読む本文を大量生成しません。生成対象は索引、逆引きのマッピング、リンク検査など、正本を複製せず
探索性または整合性を改善するものに限定します。生成物が正本にならないよう明示します。

## ADR-001：検査・公開資産の判断をGOVへ統合し、SOCは横断案内にする

2026-10-13、利用者の指示により採用しました。

旧Detection / Verificationの二件は、検査結果を判断材料として使えるか、公開サービスが管理台帳から漏れていないかを扱います。この二件だけでSOCの監視・対応領域を表すのは分かりにくいため、独立domainを廃止しGovernance / Operationsへ統合します。二つの問いは異なるため、一つの本文へ混ぜずGOV-009・010として保持します。対応する設計パターン、教材、診断項目、根拠も同じdomainへ移します。

SOCは独立domainを増やさず、[Control一覧の横断案内](../controls/README.md#soc-reading-path)を入口にします。CONTAINER-004の実行時検知、CONTAINER-003のホスト管理、GOVの影響調査・認証情報対応・復旧をつなぎます。既存Controlの本文を複製せず、コンテナー中心の観測をSOC全体の完成とみなしません。

結果として11から10 domainとなり、Control数は52件のままです。Secure Codingは引き続きASVSが要件の入口です。旧IDと移動先は[移行台帳](MIGRATION.md#detect-to-gov)に記録し、過去の日付の記録は当時の分類として残します。フレームワーク対応の範囲や実環境での検証済み状態は変更しません。

## ADR-002：個別対策の方式をControlへ、工程をまたぐ設計をengineeringへ

2026-10-29、利用者と合意した構成整理を採用。10 domainとControl IDは維持する。Controlと一対一に分かれた方式説明はControlへ統合し、engineeringはテーマ・シナリオと工程間の受け渡しを入口にする。独立した設計問題は関連Control数にかかわらず残す。教材の洞察・説明は削らない。

実装は本文整理の後に別作業で移し、原則`engineering/implementations/<用途と技術>/`へまとめる（配置は下記ADR-003で更新）。移管済みの秘密情報検査はagent-control-planeから戻さない。廃止patternのIDは移行台帳へ残し、新しい意味へ流用しない。旧URLの一律転送ページは作らない。詳細と進捗は[構成整理の台帳](MIGRATION.md#engineering-restructure)を正本とする。

## ADR-003：engineeringをdomainフォルダで分けない

2026-10-29、利用者の指摘を受け、横断シナリオを探す前にdomainを選ぶ必要をなくす。ガイドと独立した設計資料は`engineering/<テーマ>.md`、実装例は`engineering/implementations/<用途と技術>/`に配置する。Controlの10 domain分類は維持する。

ADR-001のdomain配置はControlに適用し、ADR-002で想定した実装のdomain配下配置はこの判断で置き換える。索引は「何を設計したいか」で選び、各ガイドの要素からControl IDで個別要件へ進めるようにする。実装には用途と技術が分かる名前を付け、同じ実装を複数domainへ複製しない。

内容を確認済みのDependency・Source Protection・AI Developmentから適用する。残る旧domainフォルダは内容整理と関連テストを終えた順に解消する。旧URLの一律転送ファイルは作らず、既知の参照を更新し、変更前後の対応を移行台帳へ記録する。

Controlを持たない個別技術の教材は`engineering/<テーマ>-learning.md`とし、対応するガイドから案内する。Control配下のlearning.mdの原則は維持する。2026-10-29に旧50 patternの本文整理と関連実装の移動を完了し、engineeringのdomainフォルダを解消した。確認範囲は移行台帳に残す。
