# Detection engineering lifecycle

`ENG-GOV-009` / `governance-operations`

「公開アプリから想定外の内部管理操作が起きた」という行動を、調査できる通知へ変える設計です。検知担当、サービス担当、基盤担当、初動担当が、検知を作ってから運用・廃止するまで使います。

## 検知の流れと責任

```text
守る対象と攻撃シナリオ
  → 必要なデータを確認 → 条件と正常例を設計
  → レビュー・検証 → 限定配備 → 有効な版を確認
  → 検知 → 対象と根拠を付けて通知 → 受領・担当決定
  → 調査・処置の判断 → 結果をルールの改善へ戻す
```

データの準備は[記録の設計](../security-event-collection-and-investigation/README.md)へ渡します。検知担当は条件と試験、サービス担当は正常な業務・保守の説明、基盤担当は配備と入力・配送の状態、初動担当は調査と対応先への引き渡しを担います。一人が兼務しても、判断を省略しません。

## 何を検知するか

検知ごとに、行動、対象、必要なログと項目、識別情報、正常例、限界、通知先、初動の用途を記します。管理製品の標準ルールも、設定しただけで対象を拾えるとは扱いません。

公開アプリが管理APIを使わない設計なら、そのアクセスは調査のきっかけになります。正当な呼出しがあるなら、主体・用途・対象や変更予定を使って区別します。「夜間」「知らないIP」だけで不正と決めません。requestの内容やシェル起動だけに依存すると、記録されない侵入経路を見逃す可能性も残ります。

複数のイベントを関連付ける場合は、対象の識別と時間幅を根拠付きで選びます。長い時間幅は無関係な操作を混ぜやすく、短い幅は遅延や時間を置いた行動を逃します。入口の通知が欠けても、内部で確認した重要な不正操作を単独で通知できるようにします。

## 管理方法を選ぶ

| 方式 | 利点 | 必要な確認 |
|---|---|---|
| 管理製品の標準ルールを設定 | 導入・更新の負担を抑えやすい | 対象、入力要件、版や変更通知、除外設定、設定の復元方法。内容が非公開なら確認できない範囲も残す |
| 製品固有の検索式を管理 | 実際のデータに合わせやすい | 製品依存、項目の変換、検索負荷、配備先の差分 |
| 共通形式を版管理して変換 | レビューや複数環境への展開をそろえやすい | 変換先で条件が同じ意味か、必要項目があるか、実際のルールが有効か。変換成功だけで完了にしない |

いずれも識別子、担当者、変更理由、レビュー、試験の範囲、例外の期限、配備した版と対象を追えるようにします。SigmaやDetection as Codeは選択肢です。独自のルール管理システムは必須にしません。

## 試験から配備へ

| 確認 | 例 | 分かる範囲 |
|---|---|---|
| 条件だけの確認 | 無害な検知対象例、似た正常例、欠落項目、例外、時間幅の境界 | 検知条件の挙動。実際の収集や配備は別 |
| 入力から通知まで | 非本番の安全な操作で、取得元から通知まで追う | その対象と経路の取り込み、対象特定、配送 |
| 担当者の初動 | 通知を受け、根拠を開き、処置を判断する机上演習 | 受領と役割・手順の使いやすさ。実際の隔離や失効の効果は別 |

模擬データは条件試験に使えますが、SaaS設定や本番運用を合格にする証拠にはしません。非本番で一部の対象へ配備し、検知すべき行動が拾えることに加え、正常通知の負担、処理時間、遅延を確認します。本番では配備対象・有効な版・入力の状態を確かめ、拡大します。悪化した場合は確認済みの版へ戻し、その間に失う範囲も示します。試験が本番停止などの自動対応を呼び出さないよう対象と実行権限を分けます。

## 通知が処置へつながる条件

通知には対象、時刻、検知理由、証拠参照、未確認範囲を付けます。生のpayloadやtokenは載せません。送信成功、受信、担当割当、受領、調査開始を区別します。担当不在や通知経路の障害時には、別の連絡先や経路へ渡す条件を決めます。監視対象と同じ障害で通知経路も止まる構成には代替が必要です。

繰り返す通知は、対象・行動・継続中の事案との関係でまとめます。件数の集約で、新しい移動先や権限変更の情報を消しません。例外には対象・理由・期限・再確認担当を付け、広い保守時間除外にしないようにします。

重大度だけを操作許可に使わず、[封じ込めの設計](../incident-impact-and-response-planning/README.md#intrusion-containment)へ対象・根拠・未確認範囲を渡します。自動対応を選ぶなら、事前承認した条件、対象の確かさ、権限、被害を限定する仕組み、停止・解除方法、事後確認を別に設計します。本patternは自動対応を実装しません。

## 改善と廃止

調査結果を「誤検知」「不正」「未確定」に分け、未確定を正常扱いにしません。誤検知を減らす変更後も重要な試験例を再確認します。演習や事案で分かった見逃しは、入力不足・条件不足・配送障害・初動遅れのどこで起きたかを調べます。

通知数より、重要な試験行動の取りこぼし、調査の負担、入力・通知の遅延、未対応の滞留を見ます。未知の攻撃を含む真の見逃し率を、通知0件から算出しません。ログ形式・サービス・ルール版を変えたときも再確認します。

対象サービスの廃止や検知の置換時は、失う検知範囲、代替ルール、残す記録、担当者を確認して停止します。ルールのファイルだけ消して、有効な旧版や期限切れの例外を残さないようにします。
