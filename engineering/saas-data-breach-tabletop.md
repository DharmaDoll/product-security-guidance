# 机上演習：SaaSの脆弱性で別テナントの個人データが漏えいした夜

金曜21:00、テナントAの利用者からサポート窓口に電話が入る。「20:58ごろ、顧客一覧に知らない方の氏名とメールアドレスが出ました。画面を送りますか？」 CS当番はどう答え、その電話を誰につなぐか。ここから演習を始める。

## 進行役の準備

- CS、PSIRT当番（指揮・記録）、SRE、開発・QA、法務、広報、担当役員を割り当てる。少人数なら兼任できる。法務判断、顧客通知の承認、S1の修正版配信の承認は、それぞれ誰の役で行ったか記録する。[プレイブックの役割分担](../controls/records/governance-operations/product_incident_response_playbook.md#2-役割分担raciマトリクス)
- 各場面では引用した状況だけを読み上げ、受け手に「今わかったことは何か。誰に何を頼むか」と聞く。下のチェック項目は回答後の照合用とする。依頼された役は引き受けた作業と回答予定時刻を復唱する。
- 時刻は架空事案のJST。契約・証拠・件数も演習用とし、操作・送信・受領は演習内で模擬する。記録係は決定ごとに **時刻｜根拠となる記録｜決定・保留事項｜担当→受け手｜次の確認時刻** を演習チケットに残す。

## 1　21:00　顧客からの電話を受ける

> CSが確認できたのは、通報元がAであることと表示時刻だけ。Web、モバイル、デスクトップは同じ顧客一覧APIを使い、LLMエージェントにも一覧を参照する機能がある。

- [ ] **CS → PSIRT当番**　通報者には「追加の閲覧は控えてください。画面の送付は不要です」と伝える。利用経路と要求IDが分かれば控え、非公開チケットに表示時刻20:58と受付時刻21:00を別々に記録し、当番を呼ぶ。
- [ ] **PSIRT当番 → 関係者**　他テナントの個人データが見えた疑いを暫定S1として招集する。SREへ記録保全と進行中のアクセス確認、開発へ表示元の調査、法務・CSへ通知条件の確認を依頼する。広報と担当役員へ「影響人数は調査中」と初報し、次の集合時刻を決める。応答のない役は第0節の代理へ回す。

## 2　21:12　12名分の漏えいを確認する

> 開発から当番へ。「21:06の要求で、Aの認証済みアカウントにBの12名分の氏名とメールアドレスが返りました」。要求記録、アプリの応答記録、DB上の所属が一致した。同じアカウントからの要求が続く。20:30〜20:50のAPIログは欠けている。

- [ ] **開発 → PSIRT・SRE**　一覧取得時のテナント認可に不備があると報告する。漏えいを裏付ける記録の参照先と確認範囲を渡す。21:06は確認できた悪用の一件で、最初の悪用時刻は調査中とする。
- [ ] **PSIRT → 法務・CS・担当役員**　S1を確定し、「少なくともBの12名。追加の対象者、他テナントへの影響、DBの変更有無は調査中」と伝える。法務には21:00の疑いの受付と21:12の漏えい確認を渡す。
- [ ] **SRE → 指揮者**　被害が続くため先行遮断を決める。並行して当該時間帯のAPI・DB監査記録、稼働版、欠測区間の情報をアクセス制限付きで保全し、遮断の対象と実施時刻を報告する。

## 3　21:20　遮断が効いたかを確かめる

> CSから「Webの一覧は閉じましたが、モバイルではまだ開けるようです」。SREが時刻を照合すると、Web停止後にもモバイルからの成功応答がある。エージェントの参照経路は未確認。

- [ ] **SRE・開発 → 指揮者**　共通APIで一覧取得を止め、エージェント側の経路を確認できるまで該当ツールも停止する。Web・モバイル・デスクトップ・エージェントごとに、停止後の時刻とテスト用アカウントによる拒否結果を渡す。確認できない経路は担当を付けて遮断を継続する。
- [ ] **CS → 広報**　停止した機能と利用を続けられる機能をSREに確認し、問い合わせ窓口用の回答を作る。「現在一覧を停止しています。過去に閲覧された範囲は調査中です」と、現在の利用可否と過去の被害を分けて答える。

## 4　21:30　全容が分かる前に委託元へ知らせる

> Bは国内の委託元。架空の契約では「漏えいの疑いを受託者が知ってから2時間以内」に指定窓口への初報が必要。Bの担当者から「12名で全員ですか。今夜中に社内説明が必要です」と連絡が入る。

- [ ] **法務 → 指揮者・CS**　契約初報は21:00起算、23:00期限と記録し、指定窓口をCSと照合する。法務責任者は当局報告・本人通知について、義務を負う主体、判定根拠、必要な追加事実、次回判断時刻を別に記録する。[プレイブック5.3の通知判断](../controls/records/governance-operations/product_incident_response_playbook.md#notification-requirements)
- [ ] **PSIRT・CS → 広報責任者**　Bへの初報案を渡す。例「貴社の少なくとも12名分の氏名・メールアドレスが、別の契約者のアカウントへ返されたことを確認しました。一部の記録が欠けており、影響人数は引き続き調査中です。次回は22:30 JSTに、調査中の事項も含めてお知らせします。」
- [ ] **広報責任者 → CS → 指揮者**　法務と協議して文案を承認し、CSは指定窓口に模擬送信する。進行役がBの受領を返したら、送信時刻・受領時刻・次回連絡担当を記録する。不達ならCSは契約の代替窓口を確認し、期限前に指揮者へ戻す。

## 5　22:10　修正版を配信し、再開できるかを決める

> QAから「修正版では別テナントの一覧取得は拒否され、自テナントの一覧は表示できました」。本番には旧版Podが稼働中。営業からは「もう顧客に復旧と言ってよいか」と聞かれる。

- [ ] **開発・QA／SRE → 担当役員**　開発は修正版の識別子と試験結果、SREは配信対象、失敗時の再遮断策を提示する。担当役員はS1の配信可否と条件を記録し、SREに伝える。
- [ ] **進行役 → SRE**　配信を承認したら「対象Podの一つが旧版のまま」と伝える。SREは一覧の遮断を維持する。旧版を配信対象から外したことをどう確認するか参加者が答えたら、「稼働版の照合完了。各経路でテスト用の他テナント参照を拒否し、正規操作は成功」と渡す。
- [ ] **SRE・開発 → PSIRT → CS**　SREは再開した機能・時刻と監視担当を報告する。開発は共通APIの修正で各クライアントを保護できた根拠と端末更新の要否を伝える。指揮者は確認できた範囲で再開を共有し、CSは営業に回答する。確認が揃わなければ停止中の経路と次の確認時刻を伝える。

## 6　22:30　続報を渡して夜勤へ引き継ぐ

> Bとの約束の時刻になった。APIログの欠測は埋まらず、DBの書き込みへの影響も調査中。夜勤の指揮者が到着した。

- [ ] **CS・広報 → B**　承認を経て、現時点の利用可否、確認済みの人数・項目、欠測による調査の限界、次回の更新予定を伝える。Bの質問、回答、受領を通知記録に追記する。
- [ ] **指揮者 → 後任**　SREには再開後の監視、開発にはDB更新履歴と追加影響の調査、法務には報告・本人通知の判断、CSには次の顧客連絡を割り当てる。後任が担当・期限・証拠の場所を読み返し、引受時刻を記録したら演習を終える。

## 振り返りで照合する記録

1. **演習チケット**から、誰が漏えいを疑ったか、何を根拠に確認したか、誰が遮断を決めたかをたどる。
2. **通知記録**から、Bへの初報を期限内に届けたか、22:30の続報で確認済みの範囲と未解明の範囲をどう説明したかを読む。
3. **配信・引き継ぎ記録**から、担当役員の配信承認、SREの再開確認、後任が引き受けた未完事項をたどる。判断が止まった箇所を一つ選び、改善担当・期限・次回演習での確認方法を決める。
