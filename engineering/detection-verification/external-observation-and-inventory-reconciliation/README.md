# External observation and inventory reconciliation

`ENG-DETECT-002` / `detection-verification`

## 解く設計問題

外部から見える候補を、管理台帳の「意図して公開しているもの」と比べる。候補の出所、収集できた範囲、帰属、担当者の判断を切らさず、観測停止を正常な0件と混同しない。

```text
管理責任を確認した起点 + 許可された観測方法
  → 収集元ごとの候補とcoverage / health
  → 名前・サービスの正規化と帰属確認
  → 台帳の期待する公開状態との照合
  → 未登録 / 期待外 / 再出現 / 観測障害
  → 担当者の調査、是正、再観測
```

## 最初に決めること

| 判断 | 選択肢と代償 |
|---|---|
| 起点 | 管理するドメイン、クラウドアカウント、公開IPなどを責任の根拠と結ぶ。ドメイン起点だけならIPだけの公開資産を見落とす |
| 観測手段 | 証明書ログは過去の名前の候補、DNSは名前と参照先、クラウドAPIは管理下の設定、外部観測サービスは選んだ公開面の状態を示す。対象に応じて組み合わせ、全手段を一律に要求しない |
| 台帳 | 安定した資産ID、担当者、環境、意図した公開、期待するサービス、見直し期限を持つ。古い台帳との一致は合格ではない |
| 確認方法 | 受動的な照合から始め、能動的な通信は対象、方法、頻度、委託先との境界ごとに許可する |
| 結果の意味 | 観測された候補、正常に観測した範囲、未観測範囲を分ける。候補0件は全公開面の不在を証明しない |

## 帰属と照合の境界

外部データの名前は正規化しても、所有の証拠になりません。起点の所有確認、DNSや委託先への委任、管理台帳の担当者を突き合わせ、`自組織が管理する名前`、`委託サービス`、`第三者の共有基盤`、`未確定`を区別します。共有IPの発見を、IP全体へのスキャン許可へ拡張しません。

台帳との差分は少なくとも、未登録の候補、登録済みだが期待外の公開、見直し期限切れ、以前是正した候補の再出現に分けます。台帳にないことと悪意あることは同義ではありません。担当者の判断を通じて、資産登録、公開停止、委託先への確認、脆弱性診断の依頼へ送ります。

## 観測障害と状態

収集元ごとに照会範囲、時刻、ページやcursor、上限、最後の成功、収集失敗を残します。「収集APIは成功したが一部のページが欠けた」場合は得られた候補を捨てず、coverage不足も同時に伝えます。台帳取得、照合stateの保存、通知のいずれかが失敗した場合も、完了した正常観測と区別します。

候補の識別は表示名だけに頼らず、名前、サービス、観測元、変化を追える参照を使います。是正済みと閉じるには、設定変更などの処置と、許可された手段での再観測を照合します。検索から消えたことだけを完了条件にしません。保存・通知は判断に必要な識別子と参照に絞り、応答本文や認証情報を複製しません。

## 実装を作る開始条件

実装例を作る際は、対象となる使い捨てのドメイン・クラウド環境または明示的に許可された外部収集元、台帳の正本、収集APIの版・契約、能動的確認の許可範囲、通知先を先に決めます。次に、正常な一致、未登録・期待外の公開、収集失敗または部分取得、再出現をその環境で観測し、導入と解除の最短手順を示します。旧Python verifier（`scripts/verify.py`）には照合ロジックがあるものの、collectorは同梱されず、旧profileも固定のため、そのまま実装例としては移しません。
