# ENG-REL-004: Supplier SBOM intake boundary

## 利用場面と推奨構造

外部供給者や共通基盤チームから受け取ったSBOMを、脆弱性影響調査に使う部品台帳へ入れる前の設計です。受領できたこと、署名を検証できたこと、期待する製品の情報として使えることを別の判断にします。

```text
利用者が承認した調達・受入条件 ----> 供給者 / 製品 / 版 / 成果物 / 信頼根拠 / 取込先
                                             |
供給者の成果物 + SBOM + 受渡し証拠 ----> 隔離領域
                                             |
                     bytes固定 -> 出所・内容の検証 -> exact対象の照合
                                             |
                         形式・参照・既知の欠落を確認
                                             |
                       受入候補 / 隔離 / 評価不能
                            |            |        |
                            v            v        v
                      限定した取込先    調査     運用障害
                            |
                      台帳処理・分析は別に確認
```

## 1. 期待値を受領物から独立させる

調達・採用の承認時に、供給者ID、製品・版、成果物digestを得る方法、SBOMの受渡し先、許可する署名者または配送元、形式・版、台帳の取込先を決めます。供給者から届いたSBOMやenvelopeの値をそのまま期待値にすると、別製品の正しい署名も通ります。信頼根拠の追加・交代は、通常のSBOM更新とは別の変更として扱います。

実際の成果物digestを事前に得られない契約では、取得した成果物のbytesから計算し、契約で定めた製品・版と証拠の結合を確認します。製品名・版・ファイル名だけを成果物の同一性にしません。

## 2. 受渡し方式に応じて出所と内容を確認する

| 方式 | 確認すること | 見落としやすい点 |
|---|---|---|
| SBOMまたは配送物の署名 | 署名対象のbytes、暗号検証、利用者が承認した署名者の身元と権限、方式が要求する時刻・失効・透明性の証拠 | 文書内の公開鍵は信頼根拠ではない。署名が正しくても別製品向けかもしれない |
| 合意した認証済み配送経路 | 認証された供給者側の配送元、取得したbytesの完全性、必要なら別経路で合意したdigest | 通信路の認証は、保存・転送後の持続的な署名証拠とは同じではない |
| 両者の併用 | 配送元と文書署名を独立して照合 | 一方の成功で他方の失敗を上書きしない |

方式固有の検証器は、対象versionと信頼根拠の更新方法を固定します。Sigstore bundle、証明書、固定公開鍵では、署名者の特定、署名時刻、鍵の交代・失効の扱いが異なります。「現在期限切れ」の一項目だけで過去の署名を機械的に許可・拒否せず、採用方式の証拠と受入方針に従います。必要な状態を取得できなければ評価不能として止めます。

## 3. SBOMを今回の成果物へ結ぶ

出所と内容を確認した後、認証されたSBOMのdigest・serial・version・root subjectを、期待する製品と受領した成果物のdigestへ照合します。署名対象がSBOMだけなら、成果物との関係は別の認証されたmanifestやSBOM内のroot hashと照合しなければなりません。認証されていないsidecarの`artifact_sha256`を信用しません。

Schema validatorで採用形式・版を検査し、参照関係と既知の欠落を確認します。CycloneDXかSPDXか、単一BOMか複数BOMかで検査方法は変わります。供給者の`complete`という表明だけで、組み込み部品を全部観測できたとみなしません。必要なら、受領した成果物に対する独立したscanや調達時の質問と突き合わせます。

## 4. 隔離から取込先へ一方向に渡す

受領直後の成果物・SBOMは隔離領域に置きます。検証担当の処理は台帳の広い管理権限を持たず、受入候補だけを、事前に決めた製品・projectへ渡します。隔離と評価不能を、空の部品一覧や脆弱性なしへ変えません。

| 状態 | 意味 | 次の動作 |
|---|---|---|
| `INTAKE_CANDIDATE` | この境界で必要な出所・対象・形式の確認を通過 | 限定した台帳取込へ渡す。処理完了は別に待つ |
| `QUARANTINE` | 入力が不正、不一致、未知、または未対応 | 通常取込を止め、供給者・担当者へ調査を渡す |
| `ERROR` | 検証器、信頼根拠、状態情報を評価できない | 通常取込を止め、運用障害として復旧・再評価する |

判断記録には対象のdigest、供給者・製品の識別子、使用した方式と信頼根拠の版、判断時点、結果、確認できなかった範囲を残します。SBOM本文、署名、鍵素材、認証情報は必要な保管場所へだけ置き、一般的なCI logへ複製しません。訂正・撤回が来たら古い結果を上書きせず、新しい文書と関係付けて再評価します。

## 典型的な失敗経路

- 署名を確認した後、別の製品・成果物へSBOMを付け替える。
- 供給者が同梱した公開鍵をそのまま信頼し、攻撃者の自己署名を通す。
- 署名付きSBOMと実際に取得した成果物との関係を名前だけで決める。
- 古い失効情報や検証器の停止を、署名者が有効という結果へ変える。
- Schema適合や署名成功をcomponent coverageの証明にする。
- `QUARANTINE`のSBOMが、別の自動取込や管理者権限から通常台帳へ入る。
- 訂正・撤回後も、古い受入済みSBOMだけで影響なしと判断する。

## 具体化判断

旧リポジトリにはOpenSSLで合成Ed25519 envelopeを検証するscriptがありました。暗号計算とbytesの照合は実際に行いますが、envelope形式は独自で、署名者状態は手書きsnapshot、台帳権限はJSONの自己申告です。これを新しい汎用受入実装として移すと、供給者の信頼根拠・失効・台帳隔離まで実装済みに見えます。

本移行ではcontrol、教材、設計パターン、診断観点までを選び、実装例は作りません。再開時は、実際に採用する供給者と製品・成果物、署名または配送方式、利用者が管理する信頼根拠、署名者状態・時刻の確認方法、使い捨ての台帳取込先を一組で選びます。その上で成功、別製品・改変・未知署名者、状態取得不能、隔離からの迂回を観測できる限定実装を作ります。暗号検証だけを再現するための独自envelopeは採用しません。

## このpatternの境界
