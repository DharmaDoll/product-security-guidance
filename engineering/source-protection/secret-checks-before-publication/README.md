# ENG-SOURCE-003: Secret checks before publication

対象読者は開発者とリポジトリ管理者です。Git hooksで早く誤りを知らせつつ、hooksを通らない経路にも共有先の判断を置く設計を扱います。
認証情報を一度コミットしてから削除した変更を例に、最新ファイルだけの検査がなぜ足りないかを考えます。

## 検査を置く場所

```text
作業内容 → コミット対象・メッセージのローカル検査 → ローカル履歴
  → push対象の履歴検査 → 通信 → 受信側の検査 → 共有refへの受入
  → 送信後のCI検査 → merge・後続利用

Web UI・API・bot・mirror → 経路ごとの受入判断へ接続
共有先への露出候補 → 認証情報の所有者 → 失効・利用履歴とコピーの調査
```

| 場所・方式 | 防ぐことと選択条件 | 代償・限界 |
|---|---|---|
| `pre-commit`・`commit-msg` | コミット予定の内容とメッセージを早く検査する | 利用者が変更・省略できる。起動時間や誤検知が作業へ影響する |
| `pre-push` | 送信対象のrefと導入履歴を検査する | 最新状態だけの検査より時間がかかる。これも省略でき、ローカル強制だけでは全経路を守れない |
| 受信側の検査・push protection | ローカル検査から独立して受入を止める | 提供元で扱える経路・形式・例外に依存する。受信処理へのデータ到達自体は防がない |
| CIと必須merge検査 | 送信後の継続検査と、保護されたブランチへの統合を止める | 検査開始前に共有先へ届く。未mergeでも露出候補が残る |

Gitの`pre-receive`はref更新前の検査ですが、受信オブジェクトはその前に隔離領域へ入ります。
「受入拒否」と「サーバーへ一度も送信しなかった」を同じ保証にしません。
Git仕様の根拠と製品ガイダンスは[参照資料](../../../sources/README.md#ref-secret-publication-001)に分けています。

## 検査対象と許可対象を結び付ける

コミット前には作業ツリー全体ではなく、コミット予定の内容を検査します。部分的なステージングでは両者が異なります。
push前には、実際の送信先と更新対象refから導入する履歴を求めます。既存ブランチへの通常更新だけを前提にせず、
新規ref・複数ref・タグ・履歴書換え・削除の扱いを決めます。ref削除を検査免除の口実にせず、同時に導入する他のrefを分けて評価します。

履歴を取得できない、対象を確定できない、内容が変わった場合は、過去の検出なしを再利用しません。
LFS・submodule等を参照するだけの検査では、その先の内容を検査済みにできません。別経路で検査するか、対象外の格納を制限するかを決めます。
コミットメッセージ、タグのメッセージ、ファイル名などのメタデータは、採用する検査器の対応を確認し、未対応なら代替の審査・利用制限を決めます。

## hooksと検査方針を誰が管理するか

リポジトリにhookコードを置く方式はレビューしやすい一方、ブランチの変更で実行コードも変わります。
チェックアウトしただけの未レビューコードを信頼せず、導入する版と更新の承認を管理します。
中央配布の方式では、配布元と更新権限、適用先の一致を確認します。相対パスか絶対パスかだけで信頼を決めません。

どちらの方式でも、clone先ごとの配置・実行権限・実効設定を確認します。hookファイルがあるだけでは、有効化の証拠になりません。
受信側の必須方針は、検査対象の変更者が同じ変更の中で書き換えられない位置に置きます。ルールや除外の更新は、
無害な検出例、許可すべき類似入力、検査障害、値の非表示を確認する観点とともにレビューします。

スキャナーの追加が必要かは対応形式と固有の検出価値で判断します。複数エンジン、Docker、特定のhook frameworkを必須にしません。
取得物と検査結果の信頼性は[Scanner acquisition and evidence boundary](../../detection-verification/scanner-acquisition-and-evidence-boundary/README.md)を参照してください。
CIで検査する場合は[Untrusted PR boundary](../../cicd-security/untrusted-pr-boundary/README.md)を維持し、変更に含まれるコードを検査のために権限付きで実行しません。

## 省略・例外・障害からの再開

検出なし、検出あり、検査不能を別の状態として扱います。大きなファイルや処理時間の上限を超えた場合も、検査不能を成功にしません。
誤検知の除外は、秘密値を申請に貼らず、対象コミット・パス・ルール等の限定した識別情報と理由を使います。
期限、承認者、再評価条件は[Security exception decision boundary](../../governance-operations/security-exception-decision-boundary/README.md)で管理し、
何を除外してよいかはリポジトリの所有者が決めます。スキャナー障害や範囲不明を隠す除外は認めません。

検査器の復旧後は、同じ対象を再検査してから再開します。hooksを無効化して続行する運用を、検査成功として記録しません。
GitHub等の機能名だけで全経路・全形式の拒否を推定せず、利用する書込経路、除外権限、通知と拒否の違いを確認します。
受入前の検査が提供されない経路では、書込経路を制限する等の代替を選びます。CIしか使えない構成では、送信前・受入前の混入防止は未達として残します。

## 診断と導入判断

[コントロールの診断で確認する項目](../../../controls/records/source-protection/psb-source-002-secret-publication-boundary/README.md#failure-checks)を、経路と拒否境界に対応付けて使います。
確認項目の一覧だけでも成果物として成立し、実際に試したことにはしません。試す際は、未発行の検出用文字列を隔離した検証用リポジトリで使用します。
拒否された場所、検査した範囲、未検査部分を残し、値が通知やログへ再流出していないことも確認します。

既に共有先へ届いた場合の失効は[Source credential lifecycle](../source-access-credential-lifecycle/README.md)へ引き継ぎます。
最新ファイルの修正、履歴の整理、認証情報の失効は別の作業です。秘密値を消したコミットだけで対応完了としません。

## 移行範囲

[旧SOURCE-002との対応](../../../docs/GIT_HOOKS_MIGRATION.md)に、Git設定、署名、スキャナー、導入スクリプトの採否を残しています。
本patternは方式を選ぶガイダンスです。具体化判断に基づき、Linux上のGitとGitleaksを使う
[境界を厳しく扱う実装](implementations/git-gitleaks/README.md)と、Python標準ライブラリだけで正規表現とhookの接続を読める
[小さな自作scanner](implementations/python-pattern-scanner/README.md)を追加しました。後者は旧scannerを再編集したローカル用の例で、
Gitleaks相当の検出や受信側強制を主張しません。旧Docker wrapperとinstallerは移植していません。
隔離環境で実装テストを実施しましたが、本PJ自身のGit hooks、本番repository、SaaSの設定は変更していません。
実装範囲と残る作業は[実装計画](../../../docs/MIGRATION_PLAN.md#source-002の具体実装計画)を参照してください。
