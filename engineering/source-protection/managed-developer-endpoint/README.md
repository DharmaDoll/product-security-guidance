# ENG-SOURCE-002: Managed developer endpoint

開発者端末を「設定を配った機器」ではなく、所有者・現在の状態・利用できる権限を継続して管理する対象として設計します。
対象読者は、端末管理者とProduct Security担当者です。[PSB-SOURCE-001](../../../controls/records/source-protection/psb-source-001-developer-endpoint-trust/README.md)の端末管理特性に対応します。旧29項目全体の移植や実環境への導入完了ではありません。

## 起点となるシナリオ

管理台帳には登録済みの端末でも、更新が止まり、監視エージェントが通信できず、開発用セッションだけが有効なまま残ることがあります。
その端末で取得した外部コードが実行されると、攻撃者は利用者が読めるソースや認証済みセッションを悪用できます。
管理者権限を奪わなくても、利用者の権限でできる操作は被害になり得ます。

一方、電源を切った端末の盗難では、ディスク暗号化と回復鍵の保護が中心です。ログイン済みプロセスによる持ち出しと同じ対策ではありません。
端末管理はこれらの条件を分け、どの状態なら業務資産へアクセスさせるかを、資産側の管理者と決めます。

## 管理する境界

端末には、日常作業を行うホストと、外部コードを実行する隔離環境が共存します。本patternは前者の基準と管理を扱います。
MDM（端末設定の集中管理）、認証基盤、監視・対応基盤が別々でも、同じ端末を識別でき、運用責任者がいることを前提とします。

| 境界 | 決めること | 強制・確認を担う場所 |
|---|---|---|
| 台帳から実機 | 所有者、用途、OS、対象資産、廃棄・紛失状態。重複や未登録を残さない | 端末管理者が資産台帳と管理基盤の一覧を照合 |
| 管理方針から実効設定 | 方針の版、配布結果、現在の設定、観測日時。登録済みだけで合格にしない | MDM等の管理基盤とOS側の観測 |
| 端末の状態から業務権限 | 未更新・監視停止・紛失時に、何を止め、何だけを復旧用に許可するか | 認証基盤、ソース管理、ネットワーク等のアクセス制御 |
| 異常から初動 | 誰が端末を隔離し、認証情報を失効させ、既存セッションを確認するか | 端末管理者、認証情報の所有者、インシデント担当者 |

端末自身の申告を無条件に信じず、管理基盤側の登録情報、観測元、鮮度、対象の一致を確認します。
管理基盤が侵害された場合は、この判断の前提自体が崩れます。その管理者権限や監査の保護も別途必要です。

## 基準を設計する

以下は[利用者提供資料の再編集](../../../sources/README.md#ref-developer-endpoint-baseline-001)です。外部規格への準拠要件ではありません。

| 主な脅威・障害 | 残す判断 | 誤解しやすい限界 |
|---|---|---|
| 盗難・放置端末の利用 | ディスク暗号化、回復鍵へのアクセス、画面ロックと再認証、保管・輸送・紛失報告を組み合わせる | 暗号化はログイン済みの悪意ある処理を止めない。リモート消去は端末へ届かなければ完了しない |
| 古いOS・開発ツールや不要アプリからの侵害 | サポート対象、更新期限、再起動を含む適用確認、承認済みアプリと拡張の一覧を定める | 「最新版」だけを基準にしない。正規の更新元の侵害と互換性・例外期限も別に扱う |
| 日常作業から管理権限への拡大 | 標準ユーザーを基本に、昇格の目的・範囲・時間を限定する。不要な外部待受も制限する | 標準ユーザーでもソースを読める。管理者グループの一覧だけでは実際の昇格経路を確認できない |
| バックアップからの情報流出・復旧不能 | 保存対象、暗号化、鍵の保管、復元権限、保持・削除を決め、限定した復元を確認する | 暗号化だけでは復旧可能性を示せない。復元で古い秘密情報を再配置しない |
| 監視停止を見逃す | EDR等の登録、稼働状態、最終観測、通知先、初動担当を分けて確認する | インストール済みや検知ゼロは、正常な観測・通知・隔離の証明ではない |
| 管理外経路での持ち出し | 許可する通信と業務資産を定め、直接通信・代替経路が制御を迂回しない構成を選ぶ | DNSやproxyの設定を配るだけでは迂回を止められない。許可済みサービス内の送信先・権限も残る |

高リスク作業を遠隔の管理環境へ移す場合も、接続元端末には画面、入力、接続セッションが残ります。
遠隔環境の採用を、接続元端末の保護が不要になる理由にしません。

## 方式の選択と代償

- **管理されたローカル端末**：端末上のツールやオフライン作業を使いやすい一方、OS・拡張・データの管理範囲が広がります。更新と例外の責任を開発者個人へ丸投げしません。
- **管理された遠隔開発環境**：ソースや実行環境を集中管理しやすい一方、接続基盤の可用性、接続元セッション、データの持ち出し、環境破棄の責任が増えます。
- **高リスク作業だけ隔離**：通常の作業を維持できますが、どの操作を隔離対象にするか、認証情報・マウント・runtime socketを渡していないかを継続して確認する必要があります。

後二者の実行境界は[Development runtime isolation](../../ai-development-security/development-runtime-isolation/README.md)と
[Build execution boundary](../../build-security/build-execution-boundary/README.md)へ引き継ぎます。VMやコンテナという名前だけで隔離を判定しません。

## 状態の悪化をアクセス制限へつなぐ

1. 端末管理者が対象端末、観測元、状態、最終確認時刻を識別する。情報が古い、欠ける、取得に失敗した状態を良好に変えない。
2. 資産管理者が、状態ごとの拒否・制限・期限付き是正を決める。期限と復旧用の最小アクセスは明示し、取得失敗を無期限の許可にしない。
3. 紛失・侵害の疑いでは、新規ログインの停止だけでなく、既存セッションと発行済み認証情報を[SOURCE-004](../../../controls/records/source-protection/psb-source-004-source-access-credential-lifecycle/README.md)の所有者へ渡す。
4. 端末隔離と調査情報の保全を調整する。端末を消去しても、既に行われたrepository変更や公開済み成果物は取り消されない。[影響調査](../../governance-operations/incident-impact-and-response-planning/README.md)へ対象と時間範囲を渡す。
5. 復旧時は再登録・設定・更新・監視の状態を確認し、誰がアクセスを戻したかを残す。端末から応答がない場合、隔離や消去を完了扱いにしない。

アクセスを止めるまでには、観測間隔・配送・評価・各サービスへの反映の遅れがあります。
組織は許容する時間とその間に残る権限を決めます。本patternは具体値や即時失効を保証しません。

## 導入判断で確認すること

[Negative testの診断観点](../../../controls/records/source-protection/psb-source-001-developer-endpoint-trust/README.md#negative-test脆弱性診断のチェック観点)を、対象環境の確認計画に使えます。観点の記載は実施済みの証拠ではありません。

まず対象となる端末群と利用資産を一つ選び、端末・認証・監視の担当者を確定します。
基準の配布だけでなく、管理下の検証用端末で、基準を満たさない状態と復旧した状態が実際のアクセスへどう反映されるかを確認します。
本番端末の監視停止や実データの持ち出しを試験手段にしません。

ローカルの読み取り専用検査は、特定のOS設定を観測する補助です。コンテナ内の観測を物理ホストの評価に流用せず、
観測できない設定、管理基盤の状態、通知や失効の実効性を別に残します。検査失敗と基準違反も分けます。
製品別の設定例、収集器、評価手順の実装はまだ移行していません。
