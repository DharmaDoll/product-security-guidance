# Development action authorization

`ENG-AI-002` / `ai-development-security`

## 解く設計問題

開発用agentにソースの公開や開発基盤の変更を任せるとき、承認した操作だけを実行させるには、どこへ判断と権限を置くべきか。
対象はIDE・CLI・開発用MCP・CIでの操作です。製品内のAI機能は[対象外](../../../docs/SECURITY_SCOPE.md)です。

この資料は旧PSB-AI-004の認可部分を先行して再編集した設計パターンです。[Control記録](../../../controls/records/ai-development-security/psb-ai-004-development-agent-runtime-boundary/README.md)はガイダンス移行済みです。製品別設定、実行可能な認可サービスは未移行です。

## 前提と守る境界

端末上の到達範囲と管理方針の設計は[Development runtime isolation](../development-runtime-isolation/README.md)へ分離しています。操作承認と隔離は互いの代替ではありません。

リポジトリ内の指示、issue、ツールの出力は攻撃者が変更できると仮定します。Agentの提案も信頼済みの命令ではありません。
認可を行う仕組みと認証情報は、agentが編集できる作業領域の外に置きます。Agentが同じ操作を直接実行できる認証情報を持つ場合、この構成だけでは迂回を防げません。

```text
agentの提案（未信頼）
  → 操作・対象・引数を確定し、独立した方針で分類
  → 必要な操作だけ、人がその内容を承認
  → 実行側が承認者・期限・対象・引数・方針の版・使用済み状態を照合
  → 一度だけ送信
  → 成功／未実行／結果不明を区別して記録
```

## 方式を選ぶ

| 方式 | 利点 | 条件・代償 |
|---|---|---|
| 読取り専用で開始し、公開は人が行う | 自動化する権限が小さく、判断点が少ない | 人への引き渡しが増える。読取り対象にも秘密情報があれば漏えい対策は必要 |
| 構造化した操作を仲介サービスへ渡す | 対象と引数を固定し、実行権限をagentから分離できる | 仲介サービスの運用、認証、重複防止、直接経路の遮断が必要 |
| 任意のshellを許可し、事前hookで確認する | 既存作業へ接続しやすい | script・alias・子プロセスの意味が変わり得る。hook単体では認可の強制点としない |

操作名だけで自動化の可否を決めません。例えば読取りでも送信先が外部なら情報公開になり、ローカルの変更でも認可方針の編集なら後続の権限を変えます。
承認回数を増やす前に、自動実行できる対象・操作・変更量を狭くします。意味を解決できないコマンドは、低リスクと推定せず拒否または手動作業へ戻します。

## 承認と実行を結び付ける

拡張の利用承認と、この一回の操作承認は別です。操作承認が有効でも、拡張や認証情報の利用資格が失効していれば未送信の呼出しを許可しません。[失効時の責任分界](../agent-extension-admission/README.md#失効を実行環境へ渡す)に従い、実行側が両方の現在の状態を確認します。

承認対象には、依頼者、agent、操作、接続先、リポジトリや環境の識別情報、引数、適用方針の版を含めます。表示も実行も同じ確定済み要求を使います。
「公開してよい」という会話だけでは、別のremote・branch・強制更新まで許可したことにしません。承認後に対象が変われば再承認です。

有効期限は作業とリスクに応じて定めます。旧サンプルの300秒は普遍的な基準ではありません。承認者を偽装できず、利用済みの承認を同時に複数回使えない仕組みが必要です。
認可処理が停止・時間切れ・不正な応答になった場合は送信しません。事前hookが動いたはずという想定ではなく、操作を実行する側で有効な許可を確認します。

送信後のタイムアウトは「未実行」ではありません。承認を未使用へ戻して再送すると二重実行になり得ます。同じ要求の識別情報で実行先へ結果を照会し、結果不明なら自動再送を止めます。
実行先の重複防止機構と照会手段がない場合、人による確認を含む運用が必要です。

## 導入時に確認すること

### 自動化の範囲と承認の真正性

自動実行する変更は、対象、操作、変更量、元へ戻せる条件、重複防止を実行側で確認できる範囲へ限定します。Toolの説明が「安全」「読取り専用」でも、独立した方針より権限を広げません。危険な操作や意味を解決できない操作を、承認画面を出すだけで許可可能な操作へ変えないでください。
旧サンプルの「通常操作は確認0回、重要操作は1回」は承認疲れを減らす設計入力です。固定回数を合格条件にせず、重要な対象変更が新しい判断を必要とすることと、人が実行内容を把握できることを確認します。

承認ファイルの内容が一致するだけでは、誰が発行したかは分かりません。署名付きの承認を使う場合は、信頼する発行者・鍵・アルゴリズム・有効期間を管理し、確定した要求全体を検証対象にします。信頼設定自体をagentが書き換えられる構成では成立しません。
別方式として、認証された承認サービスから実行側が直接決定を取得する構成も考えられます。その場合も通信相手の認証、対象との結合、失効、再利用防止が必要です。これは本PJの設計上の選択肢であり、旧実装の検証済み方式ではありません。

使用済み状態の確認と更新は、並行した呼出しが両方通らないよう一つの不可分な処理にします。旧SQLiteの方式は実装候補であり、分散した実行側へそのまま保証を広げません。また、承認を一度だけ消費できることと、外部操作が一度だけ成功することは別です。
事前hookの適用漏れ・起動失敗・不正出力を、正常な許可と同じに扱わず、実行先で要求に結び付いた許可を確認します。製品固有のhookの失敗挙動は導入時の確認事項です。

これらは旧AAR-013〜017の再編集です。[資料の版・変更して採用した判断](../../../sources/README.md#ref-development-runtime-reconciliation-001)に記録しています。

### 採用先の試験

- 承認後にremote・branch・引数・方針を変えても、実行前に拒否されるか。
- 期限切れ、承認の偽造、並行した再利用、認可サービスの停止で実行されないか。
- script経由や直接API呼出しで仲介サービスを迂回できないか。
- 送信後に応答だけ失われても、二重実行せず結果を確認できるか。
- 監査記録から要求・判断・結果を結び付けられ、秘密情報やソース本文を記録していないか。

これは実環境で確かめる観点であり、本資料による検証結果ではありません。人が内容を正しく判断すること、端末隔離、実行先の認可、ログ配送、復旧は別途必要です。

## 前後の責任と根拠

[Agent extension admission](../agent-extension-admission/README.md)は何を読み込むかを判断し、このパターンは読み込んだ後の操作を制限します。
[Source credential lifecycle](../../source-protection/source-access-credential-lifecycle/README.md)は発行・保管・失効、[Workload federation boundary](../../cicd-security/workload-federation-boundary/README.md)はCIでの権限取得を扱います。
通常の操作承認は[GOV-002の例外管理](../../../controls/records/governance-operations/psb-gov-002-security-exception-lifecycle/README.md)とは別です。承認しただけでsecurity gateの例外を発行しません。
