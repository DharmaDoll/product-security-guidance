# Development runtime isolation

`ENG-AI-003` / `ai-development-security`

## 解く設計問題

開発用agentが未信頼のリポジトリや拡張を扱うとき、開発者本人の端末権限をそのまま引き継がせないための設計です。
操作を許可するかは[Development action authorization](../development-action-authorization/README.md)、許可した処理がどこまで届くかは本資料で扱います。
満たすべき状態は[AI-004](../../../controls/records/ai-development-security/psb-ai-004-development-agent-runtime-boundary/README.md)、具体的な判断例はその教材で確認できます。

## 作業フォルダを狭めただけでは足りない

開発者がIDEからagentを起動し、修正対象のフォルダだけに書込みを許可したとします。未信頼のテストスクリプトが実行されると、親プロセスから渡されたトークンや、到達可能なローカルサービスを使って、フォルダ外の資産を操作する経路が残ります。
その経路が成立するには、実行コードが認証情報を取得できるか、権限を持つサービスへ接続できる必要があります。ファイルだけでなく、渡す環境変数、ソケット、通信先も制限すれば、この経路を狭められます。

ここでいう隔離は、プロセスのアクセスをOSや実行基盤で制限することです。「秘密を読まない」という指示や、実行前の確認画面だけを隔離とは呼びません。

## 三つの到達経路と管理面

| 境界 | 決めること | 見落としやすい経路 |
|---|---|---|
| ファイル | 必要な読取り範囲、変更対象、一時領域、保護する設定 | 別のmount、リンク先、共有cache、後で高権限で読み込む設定 |
| 認証情報 | どの処理に、何の操作用の権限を渡すか | 親の環境変数、既存セッション、認証補助サービス、管理ソケット |
| 通信 | 必要な接続先と、そこへ送ってよい情報 | 直通、proxy、redirect、localhost、private network、クラウドmetadata |
| 管理面 | 誰が制限と例外を変更できるか | リポジトリ内設定による権限追加、隔離なしの再実行、子プロセスだけの適用漏れ |

Agentが編集できるファイルで、そのagentの最大権限を定義しません。管理する方針を外側へ置き、作業側の設定は権限を狭める方向にだけ使います。
Gitやagentの管理用設定は通常のソース編集と分けます。修正が必要な場合も、普段の作業権限へ恒久的に含めず別の管理操作として扱います。

Codex CLIでは、trusted projectの`.codex/config.toml`がuser設定より優先されます。Repositoryをtrustedにする判断には、その設定へ優先権を与える判断が含まれます。`AGENTS.md`のような作業指示と、実際に読み込まれる設定・管理requirementsを分けてレビューします。これは[Codex版の資料と公式仕様の照合](../../../sources/README.md#ref-codex-cli-hardening-001)に基づく製品固有の確認例であり、他の開発agentへ設定の優先順位を一般化しません。

## 方式を選ぶ

| 方式 | 向く状況 | 代償と前提 |
|---|---|---|
| 製品のOS sandbox | ローカル開発の操作性を保ちたい | 対象ツール・子プロセス・読取り・例外経路を確認する。設定名だけで全ツールへ有効とは判断しない |
| 専用container・VM | 開発者のhomeやセッションから分離したい | Host mount・socket・認証情報を持ち込めば境界が弱くなる。生成・更新・破棄の運用が必要 |
| Remote開発環境・専用runner | 管理された短命環境で実行したい | 管理者権限、共有領域、通信、ログ、成果物の持出し先は引き続き設計が必要 |

必要入力を先に取得できるなら、実行中の通信を閉じる方式を検討します。接続が必要なら、agent全体へ自由な通信を与えず、用途を限定した経路へ分けます。
許可したホストでも、ソースを送ってよいとは限りません。接続許可と送信する情報の判断を分けてください。

通信経路の棚卸しでは、shellの子プロセスだけでなく、agent自身のWeb検索、MCP、hookも別々に扱います。一つのsandbox設定から、すべての経路の遮断を推定しません。ローカルの設定や履歴へ残る情報も、送信とは別の持出し経路として確認します。どの保存物を制御できるかは採用するclientの版で確かめます。

## 渡す認証情報と、実行できる操作を一緒に決める

テスト用の短命tokenだけを渡しても、同じプロセスが開発者の別の鍵や認証キャッシュを読めるなら、そちらの権限を使う経路が残ります。逆に実行環境のアクセスを制限しても、外へ漏れたtokenが別の場所から使えるなら、環境を停止するだけでは不十分です。[利用者提供資料の§1.3・4・5](../../../sources/README.md#ref-user-agent-isolation-pairing-001)を、この二つを同時に確認する設計入力として採用しました。

| 作業ごとに決めること | 確認する経路 |
|---|---|
| 必要な対象・操作・権限・期限 | 作業用tokenだけでなく、親の環境変数、マウントした鍵・キャッシュ、認証補助サービスから得られる権限も確認する |
| 誰が秘密を扱うか | agent本体、MCP、hook、子プロセス、外部の仲介サービスを分け、秘密を読める主体と操作を依頼できる主体を確認する |
| どこで操作を止めるか | ツールの許可規則、OS・VM等の隔離、通信境界、サービス側の認可を照合する。一つのツール向け設定を全経路に効くものとしない |
| 期限切れと更新をどう扱うか | 更新に必要な認証元と権限、更新を打ち切る条件、発行済みの権限の失効を決める。失敗時に長寿命・広範な鍵へ自動で切り替えない |
| 停止の効果をどう確かめるか | セッション、子プロセスやMCP、認証情報、通信の各経路を確認する。画面の停止表示だけで終了にしない |

読取り専用mountでも、秘密を読む能力は残ります。開発者の認証ディレクトリを丸ごと渡す構成を標準にせず、作業で必要な情報と更新経路に絞ります。保管と受け渡しは[SOURCE-007](../../../controls/records/source-protection/psb-source-007-developer-local-credential-storage/README.md)、ソース管理の認証情報の寿命は[SOURCE-004](../../../controls/records/source-protection/psb-source-004-source-access-credential-lifecycle/README.md)へつなぎます。

短命トークンのキャッシュも保護対象です。更新に使える認証情報を同じ環境へ渡すと、その環境から権限を得続けられる場合があります。作業用の権限だけでなく、その取得・更新元を誰が使えるか確認します。[公式資料との照合結果](../../../sources/README.md#開発端末の認証情報保護に絞った追加照合2026-10-15)には、Claude Codeの読取りルールとsandboxの適用範囲、Dockerの読取り専用mount、AWS CLIのSSOキャッシュについて、採用した判断と未確認の範囲をまとめています。

秘密を保持する仲介サービスを別に置けば、agentへの秘密値の露出を減らせます。ただし、値を見せないだけでは無制限の操作依頼を防げません。仲介側でも呼出し元、対象、操作、引数、期限を確認します。SDKが同じ実行環境で鍵を読める構成を、独立した仲介による分離と同一視しません。

読取り・送信の制限は、無効なダミー値と許可された試験先で確認します。専用の読取りツールだけでなく、許可した他の実行経路からも保護領域を読めないかを確かめます。停止時には子プロセスが残らないかも確認します。一方、発行済みの権限が失効したかは、無効なダミー値では確認できません。対象サービスの検証用アカウントと限定した権限で、失効前の利用と失効後の拒否を別に確かめます。実環境のtoken失効と被害調査は[GOV-004](../../../controls/records/governance-operations/psb-gov-004-credential-exposure-containment/README.md)、調査記録と初動への受け渡しは[GOV-011・012](../../../controls/README.md#soc-reading-path)へ渡します。今回は設計観点の追加で、試験は未実施です。

## 許可した宛先と実際の接続先を一致させる

通信が必要な作業では、用途に必要なscheme・host・portを指定します。Path単位の制限が必要なら、その情報を確認できるアプリケーション層の仲介が必要です。通常の暗号化された通信を中継するだけの仕組みで、pathまで照合できるとは扱いません。
名前を許可した後も、DNSの解決先と実際の接続先が管理方針に一致することを確認します。公開ホスト向けの経路では、同じ名前がlocalhost・private network・metadataのアドレスへ変わっても接続させません。Redirectの各接続先も再評価し、別proxyやsocket経由の迂回を閉じます。
正当な社内サービスが必要なら、公開ホスト向けの制限を丸ごと緩めず、別の限定した経路として管理します。旧サンプルの「HTTPS・443・public addressのみ」はそのprofileの条件であり、全開発環境の普遍的要件ではありません。
DNS情報が欠けた場合や接続先の照合ができない場合は、正常な通信許可としません。テスト用の管理下宛先で、許可・拒否・redirect・解決先変更・実接続先不一致を確認します。今回実通信は行っていません。

## ローカルの判断から監査・通知まで

実行前の許可・拒否・評価不能と、実行後の結果を分けて記録します。時刻、端末・session・要求の識別情報、適用方針の版、判断理由、結果状態を関連付けます。Prompt全文、ソース、引数、tokenは通常の集約ログへ含めません。Hash化した識別子にも推測や照合による漏えいリスクがあるため、閲覧権限と保存期限を定めます。

監査保存を必須条件とした重要操作は、記録不能なら実行前に止めます。一方、送信後の記録障害で既に起きた外部操作を未実行扱いにせず、[結果不明の照合](../development-action-authorization/README.md)へ渡します。
中央配送が停止した場合のローカル保存量、許容する遅延、停止対象の操作を事前に決めます。無期限に正常扱いすることも、すべての障害を無条件に端末全停止へ結び付けることも避け、保証できない範囲を明示します。

中央側では、管理対象端末の一覧と実際の送信元を照合し、欠落・遅延・順序の途切れを確認します。受信側の保存、通知ルール、担当者への到達までを別々に観測します。ローカルにログがあるだけでは、組織が異常に気付けるとは限りません。
収集結果を署名付きsnapshotで渡す場合は、発行者、内容、方針の版、時点、前回からの進み方を確認し、古い正常結果の再送を拒否します。鍵と最後に受理した状態は独立に保護します。署名は出所と改変有無の根拠であり、収集者の侵害や元データの虚偽まで否定しません。

旧AAR-019〜021、025〜026の設計判断を再編集しています。[参照資料](../../../sources/README.md#ref-development-runtime-reconciliation-001)を保持し、製品の収集機能・中央保存・通知は未検証として残します。本番アプリケーションの監視は[Runtime detection to triage](../../container-cloud-iac-security/runtime-detection-to-triage/README.md)の責任であり、開発端末の結果を流用しません。

## 失敗時と確認方法

必要な隔離が使えなければ、制限なしで続行せず処理を止める設計にします。起動できたことと、必要な境界が有効なことは別です。
承認付きの例外実行も「sandbox内で成功した」と記録しません。例外を認める場合は、増える到達範囲と別の管理手順を明示します。

採用先では、管理下の使い捨て環境とダミー情報で次を確認します。本番の秘密情報や実metadataサービスを試験対象にしません。

- 許可した作業ファイルは変更でき、保護する方針・認証情報の試験領域は読取り／書込みの指定どおり拒否される。
- 親から子へ不要な環境変数や認証補助用socketが渡らない。
- 管理下の許可先へは接続でき、拒否先・迂回経路へは接続できない。
- 作業側の設定、子プロセス、隔離障害、例外的な再実行で境界が広がらない。
- Trusted projectにした時の設定優先順位と実効権限、shell以外のtool経路、ローカル保存物を個別に確認する。
- 設定宣言と実際の拒否結果を分けて残し、未実施は`NOT_CHECKED`、評価不能は`ERROR`とする。

この資料では上記の試験を実行していません。Host自体の侵害、隔離実装の脆弱性、許可範囲内の破壊や漏えい、生成コードの欠陥は残ります。

## 隣接領域との責任分界

| 正本 | その資料に残す判断 | 本資料との受け渡し |
|---|---|---|
| [Source credential lifecycle](../../source-protection/source-access-credential-lifecycle/README.md) | 発行・保管・権限・期限・失効 | 限定した認証情報でも、どのプロセスへ渡すかを確認する |
| [Build execution boundary](../../build-security/build-execution-boundary/README.md) | 取得・build実行・観測・成果物の受入 | Agentが起動するbuildにも同じ分離を適用し、公開権限を渡さない |
| [CI state and runner lifecycle](../../cicd-security/ci-state-and-runner-lifecycle/README.md) | Job間の残存状態とrunnerの破棄 | 一回の実行を隔離しても、次のjobへの持越しは別に確認する |
| [Development action authorization](../development-action-authorization/README.md) | 対象・引数・期限に結び付いた操作許可 | 隔離内で可能な操作も無条件に承認済みとはしない |

端末全体の更新・管理・侵害検知を、このagent用の境界で代替しません。製品内AI機能は[対象外](../../../docs/SECURITY_SCOPE.md)です。
根拠の版・採否は[参照資料](../../../sources/README.md#ref-development-runtime-isolation-001)、旧項目の扱いは[移行台帳](../../../docs/MIGRATION.md)へ記録しています。
