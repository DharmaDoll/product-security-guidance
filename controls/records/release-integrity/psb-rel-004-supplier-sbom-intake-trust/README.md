# PSB-REL-004 Supplier SBOM intake trust

**供給者から届いたSBOMは、期待する製品と実際に使う成果物のものか。**

## なぜ必要か

例えば、署名が正しいSBOMでも別製品のものなら、部品台帳へ入れると影響調査を誤ります。誰から何を受け取るはずかを先に決め、確認できるまで通常の台帳へ混ぜません。

## 満たすべきこと

1. **受け取る相手と対象を決める。** 供給者、製品、版、成果物、配送方法、許可する署名者や配送元を利用者側で定める（SUP-INTAKE-1）。採用方式でSBOMの内容と出所を確認し、同梱された鍵を自動で信頼しない（SUP-INTAKE-2）。
2. **成果物との対応と内容を確認する。** SBOMを実際に受領・使用する成果物の変更不能な識別子へ結び付ける（SUP-INTAKE-3）。形式、部品の識別子と関係、既知の欠落を確認し、署名や形式の合格を部品の完全性の証明にしない（SUP-INTAKE-4）。
3. **不一致と確認不能を台帳へ入れない。** 対象違い・無効な入力は隔離し、検証器や署名者状態の取得失敗は評価不能として止める（SUP-INTAKE-5）。訂正・署名者変更・撤回時は再評価し（SUP-INTAKE-6）、通常台帳への取込先と権限、判断記録に残す情報を絞る（SUP-INTAKE-7）。

<a id="failure-checks"></a>

## 診断で確認する項目（異常時テスト）

- 署名が有効でも、別製品・別成果物のSBOMを通常台帳へ入れられないか。
- 同じ製品名・版のまま成果物やSBOMのbytesを変えても、古い受入結果を再利用できないか。
- 同梱された鍵、未承認の配送元、失効・期限を確認できない署名者を信頼していないか。
- 形式や参照の不備、既知の欠落を、完全な部品表として扱っていないか。
- 検証失敗や部分取得で隔離を解除できないか。訂正・撤回後も古いSBOMが正本として残らないか。
- 隔離したSBOMを別の自動取込経路から入れられないか。判断ログへ非公開の本文や鍵素材を余分に残していないか。

これらは診断・設計レビューの確認項目であり、実際の供給者や台帳で試した結果ではありません。

## フレームワークとの関係

- NIST SSDF 1.1 PW.4.1: 供給者・製品・成果物に合うSBOMの出所を確かめ、第三者部品の来歴を採用判断へ使う部分を支えます。供給者の実認証、部品の安全性評価、台帳への導入は未確認です。

対象特性と限界は[マッピング](../../../../mappings/frameworks.yaml)にあります。SBOMを受け取っただけでSSDFのタスクを満たしたとは扱いません。

## このコントロールの範囲

対象は外部供給者から受け取るSBOMを、通常の部品台帳へ入れる前の判断です。自組織のrelease SBOMは[REL-003](../psb-rel-003-release-sbom-identity-and-analysis/README.md)、成果物そのものを使う判断は[REL-001](../psb-rel-001-signature-provenance-verification/README.md)へ渡します。受け入れたSBOMでも部品の網羅性や脆弱性の適用性は保証しません。

隔離、検証方式、台帳への受け渡しは[engineering](../../../../engineering/release-integrity/supplier-sbom-intake-boundary/README.md)で選びます。[教材](learning.md)、特性IDを残した[control.yaml](control.yaml)、[参照資料と採否](../../../../sources/README.md#ref-supplier-sbom-intake-001)、[移行記録](../../../../docs/MIGRATION_RELEASE.md#supplier-sbom-migration)、部分的な[framework mapping](../../../../mappings/frameworks.yaml)へも辿れます。
