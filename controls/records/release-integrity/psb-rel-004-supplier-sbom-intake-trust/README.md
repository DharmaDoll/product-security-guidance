# PSB-REL-004: Supplier SBOM intake trust

学ぶ：[署名が正しくても別製品のSBOMは受け入れない](learning.md) ·
設計する：[Supplier SBOM intake boundary](../../../../engineering/release-integrity/supplier-sbom-intake-boundary/README.md)

## 問い

供給者から受け取ったSBOMを、承認した供給者・対象製品・実際に使う成果物へ照合し、未確認の情報を通常の部品台帳へ混ぜずに判断できるか。

## できてはいけないこと

供給者と異なる相手が送ったSBOM、別製品・別版・別の成果物向けのSBOM、検証不能なSBOMを、通常の部品台帳の正本として扱ってはいけません。署名が数学的に正しいだけで、署名者の権限、対象成果物、記載内容の網羅性まで確認できたことにしてはいけません。

検証サービスや署名者状態の取得が失敗したとき、受入成功へ切り替えてはいけません。隔離したSBOMを自動取込や広い権限の認証情報で通常の台帳へ流してはいけません。

## 適用範囲と非適用

外部供給者または共通基盤チームから受け取るSBOMと対応する製品・成果物、利用者が管理する期待値、受渡し方法、署名や配送元の確認、取込前の隔離と判断が対象です。調達時だけでなく更新・訂正・撤回時にも適用します。

[REL-003](../psb-rel-003-release-sbom-identity-and-analysis/README.md)は自組織のrelease SBOMの取得地点、完成物との結合、公開と分析への受け渡しを扱います。[REL-001](../psb-rel-001-signature-provenance-verification/README.md)は使用する成果物と来歴の受入判断を扱います。本controlは供給者のSBOMを部品台帳へ入れる境界を扱い、成果物を使用してよいかを単独で決めません。脆弱性の適用性、供給者の開発環境、記載内容の完全性も別の判断です。

## 必要なセキュリティ特性

| ID | 成立すべき状態 |
|---|---|
| `SUP-INTAKE-1` | 利用者側で供給者、製品、版、想定する成果物、受渡し方法、許可する署名者または配送元を事前に定める。SBOMに同梱された鍵や相手の自己申告から信頼根拠を作らない |
| `SUP-INTAKE-2` | 採用した方式に従ってSBOMの内容と出所を確認し、署名・配送経路・検証器の結果を区別する。署名付きなら対象bytes、署名者、信頼根拠を照合し、方式に必要な時刻・失効・透明性の証拠を確認する |
| `SUP-INTAKE-3` | 認証されたSBOMを、期待する供給者・製品・版と実際に受領または使用する成果物の変更不能な識別子へ結ぶ。名前や版だけで同一成果物と推測しない |
| `SUP-INTAKE-4` | 採用形式と版を検証し、識別子・参照関係・既知の欠落を保持する。署名成功やschema適合を、部品の網羅性・正確さの証明にしない |
| `SUP-INTAKE-5` | 不一致・未知の署名者・無効な入力は隔離し、検証器・信頼根拠・状態取得の障害は評価不能として止める。どちらも通常の台帳へ自動取込しない |
| `SUP-INTAKE-6` | 受入後も供給者・製品・成果物・SBOMの関係と判断時点を保持する。訂正、鍵の交代、失効、撤回時は対象を再評価し、古い受入結果を無条件に再利用しない |
| `SUP-INTAKE-7` | 台帳への取込先と操作権限を限定し、判断記録にSBOM本文、署名、鍵素材、不要な内部情報を複製しない。台帳側での処理完了は別に確認する |

## 診断で確認する項目（異常時テスト）

- 署名が有効な別製品・別版のSBOMを提示しても、期待する製品の台帳へ入れられないか。
- 同じ製品名・版を保ったまま成果物またはSBOMのbytesを替えても、以前の受入結果を再利用できないか。
- SBOM内の公開鍵や未承認の配送元を、利用者側の信頼根拠として自動登録しないか。
- 署名者の交代・失効・期限や必要な時刻証拠を確認できないとき、検証済みにしないか。
- 署名は通るが形式が未対応、参照が解決できない、既知の欠落があるSBOMを、完全な台帳情報と扱わないか。
- 検証器の実行失敗、状態取得の停止、部分的な取得を、隔離不要または脆弱性なしへ変えないか。
- 隔離した入力を別の自動取込経路や過大権限の認証情報から通常の台帳へ入れられないか。
- 訂正・撤回されたSBOMが、以前の受入結果だけで検索結果の正本として残らないか。
- 判断記録やログへ供給者の非公開inventory、署名本文、鍵素材を余分に残さないか。

これらは設計・診断の確認項目です。実際の供給者、署名方式、台帳での拒否を確認した結果ではありません。

## 実装判断

受領した情報は隔離領域へ置き、利用者が管理する期待値と信頼根拠で検証します。使う方式は供給者との契約と配送経路で選びます。署名付き文書、署名付き配送物、事前合意した認証済みの配送経路では、検証に必要な証拠と失敗時の扱いが異なります。採用方式を決めずに、単一の署名検証コマンドを全供給者の受入条件にしません。

判断は「受入候補」「隔離」「評価不能」に分けます。受入候補も成果物の使用許可、SBOMの完全性、台帳での分析完了を意味しません。

## このcontrolが直接保証しないこと

- 正規の供給者や署名者が誠実で、SBOMに欠落・誤記がないこと。
- 受領した成果物が脆弱性や悪意を含まないこと。
- 特定のPKI、Sigstore、失効情報サービス、台帳に組織として導入済みであること。
- SSDFその他のframeworkへの準拠。
