# PSB-REL-004 Supplier SBOM intake trust

**供給者から届いたSBOMは、期待する製品と実際に使う成果物のものか。**

## なぜ必要か

例えば、署名が正しいSBOMでも別製品のものなら、部品台帳へ入れると影響調査を誤ります。誰から何を受け取るはずかを先に決め、確認できるまで通常の台帳へ混ぜません。

## 満たすべきこと

1. **受け取る相手と対象を決める。** 供給者、製品、版、成果物、配送方法、許可する署名者や配送元を利用者側で定める（SUP-INTAKE-1）。採用方式でSBOMの内容と出所を確認し、同梱された鍵を自動で信頼しない（SUP-INTAKE-2）。
2. **成果物との対応と内容を確認する。** SBOMを実際に受領・使用する成果物の変更不能な識別子へ結び付ける（SUP-INTAKE-3）。形式、部品の識別子と関係、既知の欠落を確認し、署名や形式の合格を部品の完全性の証明にしない（SUP-INTAKE-4）。
3. **不一致と確認不能を台帳へ入れない。** 対象違い・無効な入力は隔離し、検証器や署名者状態の取得失敗は評価不能として止める（SUP-INTAKE-5）。訂正・署名者変更・撤回時は再評価し（SUP-INTAKE-6）、通常台帳への取込先と権限、判断記録に残す情報を絞る（SUP-INTAKE-7）。

## 期待する相手と対象を先に決める

調達・採用の承認時に、供給者ID、製品・版、成果物digestを得る方法、SBOMの受渡し先、許可する署名者または配送元、形式・版、台帳の取込先を決めます。供給者から届いたSBOMやenvelopeの値をそのまま期待値にすると、別製品の正しい署名も通ります。信頼根拠の追加・交代は、通常のSBOM更新とは別の変更として扱います。

実際の成果物digestを事前に得られない契約では、取得した成果物のbytesから計算し、契約で定めた製品・版と証拠の結合を確認します。製品名・版・ファイル名だけを成果物の同一性にしません。

## 受け渡し方に応じて出所と内容を確認する

| 方式 | 確認すること | 見落としやすい点 |
|---|---|---|
| SBOMまたは配送物の署名 | 署名対象のbytes、暗号検証、利用者が承認した署名者の身元と権限、方式が要求する時刻・失効・透明性の証拠 | 文書内の公開鍵は信頼根拠ではない。署名が正しくても別製品向けかもしれない |
| 合意した認証済み配送経路 | 認証された供給者側の配送元、取得したbytesの完全性、必要なら別経路で合意したdigest | 通信路の認証は、保存・転送後の持続的な署名証拠とは同じではない |
| 両者の併用 | 配送元と文書署名を独立して照合 | 一方の成功で他方の失敗を上書きしない |

方式固有の検証器は、対象versionと信頼根拠の更新方法を固定します。Sigstore bundle、証明書、固定公開鍵では、署名者の特定、署名時刻、鍵の交代・失効の扱いが異なります。「現在期限切れ」の一項目だけで過去の署名を機械的に許可・拒否せず、採用方式の証拠と受入方針に従います。必要な状態を取得できなければ評価不能として止めます。

## SBOMを今回の成果物へ結ぶ

出所と内容を確認した後、認証されたSBOMのdigest・serial・version・root subjectを、期待する製品と受領した成果物のdigestに照らして確認します。署名対象がSBOMだけなら、成果物との関係は別の認証されたmanifestやSBOM内のroot hashと照合しなければなりません。認証されていないsidecarの`artifact_sha256`を信用しません。

Schema validatorで採用形式・版を検査し、参照関係と既知の欠落を確認します。CycloneDXかSPDXか、単一BOMか複数BOMかで検査方法は変わります。供給者の`complete`という表明だけで、組み込み部品を全部観測できたとみなしません。必要なら、受領した成果物に対する独立したscanや調達時の質問と突き合わせます。

## 隔離した情報を確認してから台帳へ渡す

受領直後の成果物・SBOMは隔離領域に置きます。検証担当の処理は台帳全体の管理権限を持たず、受入候補だけを、事前に決めた製品・projectへ渡します。隔離と評価不能を、空の部品一覧や脆弱性なしへ変えません。

| 状態 | 意味 | 次の動作 |
|---|---|---|
| `INTAKE_CANDIDATE` | この境界で必要な出所・対象・形式の確認を通過 | 限定した台帳取込へ渡す。処理完了は別に待つ |
| `QUARANTINE` | 入力が不正、不一致、未知、または未対応 | 通常取込を止め、供給者・担当者へ調査を渡す |
| `ERROR` | 検証器、信頼根拠、状態情報を評価できない | 通常取込を止め、運用障害として復旧・再評価する |

判断記録には対象のdigest、供給者・製品の識別子、使用した方式と信頼根拠の版、判断時点、結果、確認できなかった範囲を残します。SBOM本文、署名、鍵素材、認証情報は必要な保管場所へだけ置き、一般的なCI logへ複製しません。訂正・撤回が来たら古い結果を上書きせず、新しい文書と関係付けて再評価します。

## 診断で確認する項目（異常時テスト）

- 署名が有効でも、別製品・別成果物のSBOMを通常台帳へ入れられないか。
- 同じ製品名・版のまま成果物やSBOMのbytesを変えても、古い受入結果を再利用できないか。
- 同梱された鍵、未承認の配送元、失効・期限を確認できない署名者を信頼していないか。
- 形式や参照の不備、既知の欠落を、完全な部品表として扱っていないか。
- 検証失敗や部分取得で隔離を解除できないか。訂正・撤回後も古いSBOMが正本として残らないか。
- 隔離したSBOMを別の自動取込経路から入れられないか。判断ログへ非公開の本文や鍵素材を余分に残していないか。

これらは診断・設計レビューの確認項目であり、実際の供給者や台帳で試した結果ではありません。

## フレームワークとの関係

- NIST SSDF 1.1 PW.4.1: 供給者・製品・成果物に合うSBOMの出所を確かめ、第三者部品の来歴を採用判断へ使う部分を支えます。供給者の実認証、部品の安全性評価、台帳への導入は未確認です。

対象特性と限界は[マッピング](../../../../mappings/frameworks.yaml)にあります。SBOMを受け取っただけでSSDFのタスクを満たしたとは扱いません。

## このコントロールの範囲

対象は外部供給者から受け取るSBOMを、通常の部品台帳へ入れる前の判断です。自組織のrelease SBOMは[REL-003](../psb-rel-003-release-sbom-identity-and-analysis/README.md)、成果物そのものを使う判断は[REL-001](../psb-rel-001-signature-provenance-verification/README.md)へ渡します。受け入れたSBOMでも部品の網羅性や脆弱性の適用性は保証しません。

隔離、検証方式、台帳への受け渡しは[受入方式](#期待する相手と対象を先に決める)で選びます。[教材](learning.md)、特性IDを残した[control.yaml](control.yaml)、[参照資料と採否](../../../../sources/README.md#ref-supplier-sbom-intake-001)、[移行記録](../../../../docs/MIGRATION_RELEASE.md#supplier-sbom-migration)、部分的な[framework mapping](../../../../mappings/frameworks.yaml)へも辿れます。

工程間の受け渡しは[ビルドした成果物を署名・公開し、使用するまで](../../../../engineering/release-build-to-use.md)で確認できます。
