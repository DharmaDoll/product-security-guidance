# 学習：通知がゼロでも、異常がなかったとは限らない

対応するcontrol：[PSB-CONTAINER-004 Runtime threat detection](README.md) · 設計：[Runtime detection to triage](../../../../engineering/container-cloud-iac-security/runtime-detection-to-triage/README.md)

## 通知が途切れた本番アプリ

架空の場面です。使用を許可したイメージで動くアプリが侵害され、想定外のシェルが起動しました。
行動を監視するセンサーは検知記録（イベント）を作りましたが、記録を通知先へ送る転送処理が切断され、担当者には届きませんでした。
担当者の画面ではイベントがゼロです。「攻撃がなかった」と「監視・通知できなかった」は同じ表示になり得ます。

この場面で必要なのは、イベント件数とは別に、何を検知するかを決めるルール、センサー、送信待ちの記録、転送処理、受信先の状態を見ることです。
通知がない理由を調べずに「問題なし」と判断すると、攻撃を見逃したまま運用を続けてしまいます。

## 通知を復旧したら、確認は終わりか

まず、どのノード・アプリの、いつからいつまでの通知が欠けているかを記録します。既に得られた検知記録は残し、転送の障害も別に扱います。障害が起きたからといって、シェル起動の検知まで無効になるわけではありません。

転送を復旧したら、残っている記録を回収できるか、失われた区間があるかを確かめます。そのうえで、検証用環境で無害な試験イベントを発生させ、期待するルールが正しい対象を検知し、通知先で受信され、担当者へ割り当てられ、受領されるところまで確認します。「送信成功」という表示だけでは、担当者が対応できる状態になったとは言えません。

試験に成功しても、途切れていた時間帯に攻撃がなかった証明にはなりません。回収できない記録や監視できなかった範囲を残し、利用できる別の記録で調査を続けます。通知経路の復旧と、過去の影響調査の完了は分けて判断します。

## 通知された名前だけで止めてよいか

イベントが届いても、イメージ名やアプリ名だけで対象を判断すると、再作成・再配置後の別のコンテナーを止めるおそれがあります。
発生時刻、コンテナーID、イメージの内容を識別するdigest、配置先の記録を照合して、どの実行を指すか確認します。

イベントにdigestや完全なコンテナーIDがなく、稼働記録と照合しても特定できなければ、「対象未確定」として残します。調査は続けますが、名前だけで停止対象を選びません。同じイメージでも複数の実行があるため、digestだけで一つのコンテナーを特定したことにもなりません。

## 三つの状態を分けて扱う

| 状態 | 読み取れること | 読み取れないこと |
|---|---|---|
| 対象を特定できた検知 | 定義した行動が観測された | 侵害の確定、他製品への影響、停止などの操作をしてよいか |
| 正常に監視できた区間で検知なし | 設定した範囲・ルールでは該当する記録がない | 監視していないノードや行動を含めた、全体の安全性 |
| 監視・通知の障害 | 必要な判断材料が欠けている | 検知対象の行動が起きなかったこと |

検知と障害は同時にも起こります。一つの障害で既に得た検知を消さず、一部の検知が届いたことだけで監視全体が正常だと判断しません。

例えば、シェル起動が承認済みの障害調査だったと分かった場合は、正当な操作との区別を検討します。通知が多いからといって全アプリでシェルの検知を無効にすると、別のアプリへの侵入まで見えなくなります。誤検知の調整は、対象アプリ・ルール・期間を絞ってレビューします。

## 初動へ渡すもの

対応担当には、特定できた対象のIDと照合根拠、発生・観測時刻、ルールとセンサーの版、監視できた範囲と欠けた範囲、通知の到達状況、最小限の検知理由を渡します。
実行コマンドの全文や認証情報などを、そのまま通常の通知へ貼り付けません。追加調査に必要な証跡は、閲覧できる担当者を絞って扱います。

ノード自体の侵害が疑われる場合は、そのノード上のセンサーの正常表示だけに頼りません。[ホストと管理経路の教材](../psb-container-003-container-host-daemon-boundary/learning.md)に沿って管理経路と認証情報を調べ、ノード外に届いた記録とも突き合わせます。
担当者は追加情報から正当な運用か侵害疑いかを判断し、影響する稼働環境・製品を調べます。
隔離や認証情報の失効は、サービスの継続や調査証跡にも影響するため、検知の重大度だけで実行せず、対応として別に承認し、復旧条件も決めます。

イメージの置換が必要なら[GOV-005](../../governance-operations/psb-gov-005-deployed-artifact-recovery/learning.md)で旧版が稼働していないことまで確認します。ノードの隔離や再登録は別の判断です。

この教材は、運用で見つけた異常を製品のセキュリティ対応担当（PSIRT）へ引き継ぐ説明例です。[REF-PORTFOLIO-001](../../../../sources/README.md#ref-portfolio-001)の運用・ガバナンス間の関係、供給経路の段階11→12に当たりますが、侵入経路や全製品への波及を一つのイベントだけで確定しません。

検知方式の根拠は[コントロールの参照資料](README.md#このコントロールの範囲)、採用先での確認方法は[設計パターン](../../../../engineering/container-cloud-iac-security/runtime-detection-to-triage/README.md)を参照してください。実環境での検知・通知・担当者の受領は、この教材で確認したものではありません。
