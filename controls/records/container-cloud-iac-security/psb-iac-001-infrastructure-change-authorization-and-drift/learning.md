# 学習：承認した変更と、実際のインフラ設定は同じか

## シナリオ

架空の場面です。開発チームは、インフラの構成をコードで管理するTerraformを使っています。変更をプルリクエストへ出すと、CIが変更計画（plan）を表示しました。暗号化や外部公開の検査も通過し、レビュー担当者はその計画を承認します。

ところが、マージ後の適用処理（apply）は承認した計画を使わず、設定から計画を作り直しました。その間に、外部から取得する設定部品（module）の版と本番用の入力値が変わっています。外部公開に関わる値の一部も、適用時まで不明なまま検査を通りました。適用ジョブには広いクラウド権限があり、そのまま作成できました。

後日、運用担当者は管理画面から一時的に通信を公開しました。設定の差分を確認する処理は、管理対象の一部しか取得しておらず、認証情報の権限不足も「差分なし」と表示していました。CIの検査は成功していても、承認した変更、実行した変更、今ある設定は一致していませんでした。

## どこで境界が切れたか

この流れには少なくとも五つの異なる対象があります。

1. 人がレビューした設定コードと依存部品・入力値
2. ツールが具体化した変更計画
3. 検査ルールが評価した入力と結果
4. 適用ジョブの権限でクラウドへ行った操作
5. クラウド上に現在ある資源と設定

同じプルリクエストや実行番号が付いていても、内容が同じとは限りません。どの入力から作った計画を、誰が承認し、どの環境へ適用したかを結び付けます。対応を確認できなければ、その承認で適用を進めません。

## この場面でどう判断するか

適用前に計画が作り直されていたら、古い承認を使うのを止めます。新しい計画が必要なら、その内容を改めて検査・レビューします。外部公開を許すかなど、判断に必要な値が不明なら「違反なし」とは扱いません。適用前に止めるか、クラウド側で禁止状態を作れない仕組みへ引き継げるかを判断します。

適用が途中で失敗した場合は「何も変わっていない」と考えず、実際に作成・変更・削除された対象を調べます。成功した操作と失敗した操作を確認し、残った状態から復旧や再適用を計画します。

管理画面からの変更が見つかった場合は、誰が何のために変えたかを確認します。障害対応として必要だった変更なら、直ちに元に戻すことで障害が再発する可能性があります。不要な公開なら閉じる対応を判断し、必要な一時変更なら担当者と期限を決めます。恒久的に残す変更も、コードと新しい計画のレビューへ戻します。差分を消すためだけに現在値を正しい設定として取り込んではいけません。

取得に失敗した対象は、差分の有無を判断できていません。取得権限や対象範囲を直して再確認し、確認できなかった対象と期間を記録します。

## 用語

- **期待する状態（Desired state）**：コード、設定部品、入力値、ルールなどで定めた状態。実環境の現在値とは分ける。
- **確認用の計画（Speculative plan）**：変更の見通しをレビューするための計画。そのまま後で適用する保存計画とは役割が異なる。
- **保存した実行可能な計画（Saved executable plan）**：適用処理へ渡せる形で保存した計画。設定や入力値などの機微情報を含み得るため、保管先と閲覧・変更権限も守る。
- **未確定の値（Unknown value）**：計画時点では確定せず、適用時に決まる値。空の値や「存在しない」という意味ではない。
- **IaC state**：ツールが管理している資源とその情報の記録。クラウド上のすべての資源を把握しているとは限らない。
- **Drift**：期待する設定やIaCの管理記録と、実環境との間に生じたずれ。正当な緊急変更か侵害かなど、原因は別に調べる。情報の取得失敗は、ずれを確認できない状態として区別する。
- **Golden Path**：安全な既定値や標準の設定部品・作業手順を、使いやすい入口として提供する設計。利用しただけで実環境が安全になるわけではない。

## 悪用・失敗経路を分解する

1. 変更の投稿者や侵害された依存部品が、コード、module、クラウド接続用の部品（provider）、入力値、検査ルールを変える。
2. レビュー時とは異なる入力から計画が作られる。
3. 検査が新規作成の一部しか見ない、不明な値を許す、評価失敗を「問題なし」にする。
4. 承認が画面表示やコミットだけに結び付き、実際に適用する保存計画には結び付かない。
5. 適用ジョブが計画を作り直し、広い権限で別の環境や追加の対象まで変更する。
6. 管理画面、API、別のツールで、CIを通さず変更される。
7. 観測範囲や取得権限が不足し、古い情報も使われて、現在の設定とのずれを見落とす。
8. 影響を判断せず自動修正し、サービスの停止や調査証拠の消失を起こす。

## よくある誤解

### 「承認済みのmoduleを使えば安全」

Moduleは安全な既定値や、変更できる入力を絞った入口を提供できます。一方、取得する版、上書きした値、providerの既定値、部品の組み合わせ、対象ごとの要件は別に確認します。Moduleを通らない変更経路も残ります。

### 「`.terraform.lock.hcl`がmoduleとproviderを全部固定する」

本PJが参照するTerraformの仕様では、依存ロックファイルが追跡するのはproviderです。外部moduleの版などは別に固定します。ロックファイルがあっても、最初に選んだproviderを信頼してよいか、moduleの取得元や内容は正しいかという判断は必要です。

### 「計画の検査が通ったので、適用後も安全」

計画時には不明な値、providerが決める値、別経路からの変更、適用後のずれは残ります。検査で分かる範囲を示し、禁止状態を止める仕組みと、実際の設定の観測へつなぎます。

### 「保存計画を使えば、承認と完了も保証される」

Terraformでは、保存計画を指定して適用すると、追加の対話承認なしで変更を始めます。計画を取得できることと、実行してよいことは別です。適用前に承認記録・保存計画・対象環境を照合します。途中失敗では一部が変更済みの可能性があり、保存計画だけでは完了を証明できません。

### 「適用前に計画を作り直せば、最新の状態に追随できる」

作り直すことが必要な場合はあります。ただし、新しい計画は新しいレビュー対象です。以前の計画に対する承認を、そのまま使いません。

### 「設定のずれは、自動的に元へ戻せばよい」

緊急対応や外部サービスによる変更、IaCへの取込み漏れなど、原因を確認します。削除、通信の遮断、認証情報の変更は、復旧や調査を妨げる場合があります。新しい変更として影響と戻し方を判断し、自動修正はそれらを確認できる範囲に限ります。

## 判断基準

- レビューしたコード、module、provider、入力値、検査ルール、対象環境を何で識別するか。
- 検査はどの作成・更新・削除と値を見るか。不明な値、未対応の対象、評価失敗をどう扱うか。
- 承認をどの保存計画へ結び付け、誰かに差し替えられないようにするか。
- 適用ジョブは、どの環境でどの操作だけを、いつまで実行できるか。
- 管理画面、API、別のツール、緊急時の操作をどこで拒否または観測するか。
- 実環境の一覧と取得処理の状態をどう確認し、未管理・未取得・古い情報を区別するか。
- 設定のずれや例外を誰がいつまでに判断し、どの修正なら自動化してよいか。
