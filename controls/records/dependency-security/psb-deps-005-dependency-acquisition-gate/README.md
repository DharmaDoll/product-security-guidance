# PSB-DEPS-005: Dependency acquisition gate

**依存パッケージを承認した経路から取得し、拒否対象は開発端末やCIへ届く前に止められるか。**

## なぜ必要か

例えば、CIだけが悪意あるパッケージを遮断するレジストリプロキシを使い、開発端末は公開レジストリから直接取得しているとします。CIで遮断できても、開発端末にはそのパッケージが届き、インストール時にコードが動く可能性があります。守りたい対象と取得経路を先に決め、方針を通らない経路を残さないことが本題です。

## 満たすべきこと

1. **対象と経路を決める。** 対象とする開発端末・CI、パッケージの種類、公開・社内レジストリ、直接URLやキャッシュなどの取得経路を把握する（DEP-ACQ-1）。対象外の経路も明示する。
2. **取得前に方針を適用する。** 対象の依存について、承認した取得元と遮断方針を取得前に適用し、拒否対象を利用先へ渡さない（DEP-ACQ-2）。別の設定、パッケージ管理ツール、直接接続で迂回できないようにする。
3. **判定不能を成功にしない。** 方針の取得・適用やプロキシへの接続に失敗したとき、無検査の取得へ黙って切り替えない（DEP-ACQ-3）。対象外や判定できなかった依存を「安全と確認済み」と表示しない。
4. **後から対象を追えるようにする。** 取得した名前・版・取得元と利用先を追跡し、後日その版が問題と分かった場合に対象を調べて担当者へ渡せるようにする（DEP-ACQ-4）。追跡できない運用なら、その制限を明示する。

## 診断で確認する項目（異常時テスト）

- 遮断対象の版を、開発端末・更新ボット・CIの別経路や別設定から取得できてしまわないか。
- プロキシ障害時に公開レジストリへ自動で切り替わり、無検査のパッケージを使えてしまわないか。
- 直接URL、社内レジストリ、キャッシュなど、対象とした経路が実際には方針を通らず「検査済み」と表示されないか。
- 後から問題が判明した版について、取得した利用先を特定できず、通知・調査から漏れないか。

これらは確認項目です。実環境での遮断、追跡、通知を確認した結果ではありません。

## フレームワークとの関係

- [NIST SSDF 1.1 PW.4.1](../../../../sources/README.md#spec-nist-ssdf-1-1): 承認した取得元を使い、対象の依存を利用前に判断することが、第三者部品の取得・維持を部分的に支えます。SSDFは特定のプロキシや遮断一覧を要求していません。部品の利用文脈、来歴、稼働中の更新もこのControlだけでは扱えません。

この関係は[マッピング](../../../../mappings/frameworks.yaml)に記録した設計上の部分的な対応です。実環境の取得拒否やSSDFへの準拠を示すものではありません。

## 方式と境界

[Takumi Guard](../../../../sources/README.md#ref-deps-001)のようなレジストリプロキシは、取得時の遮断や履歴の把握に使える方式です。このコントロールは特定製品の導入を要求しません。プロキシを設定しただけでは、すべてのパッケージ管理ツールや取得経路へ方針が適用されたとは言えません。製品が遮断できる対象、認証の有無による追跡・通知の違い、社内パッケージの別経路を確認します。

ここで扱うのは取得経路と遮断です。公開直後の版を待つ判断は[DEPS-001](../psb-deps-001-dependency-release-cooldown/README.md)、取得したファイルの同一性は[DEPS-003](../psb-deps-003-dependency-artifact-identity/README.md)、変更の採用審査は[DEPS-004](../psb-deps-004-dependency-change-review/README.md)、インストール時の実行許可は[DEPS-002](../psb-deps-002-install-execution-policy/README.md)で確認します。遮断情報に載っていないパッケージが安全だとは判断しません。

特性IDと参照資料は[control.yaml](control.yaml)に記録しています。
