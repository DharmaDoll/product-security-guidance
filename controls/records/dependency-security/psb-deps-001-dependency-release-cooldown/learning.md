# 学習：公開直後の依存版をいつ止めるか

[対応するcontrol](README.md) · [設計パターン](../../../../engineering/dependency-security/dependency-release-cooldown/README.md)

## シナリオ

パッケージの公開権限を奪った攻撃者が、悪意ある版を公開しました。数分後、更新ボットがその版を選び、プルリクエスト（PR）を作ります。CIは最初に依存をインストールし、パッケージに含まれるインストール用のコードを実行しました。その後、外部から問題が報告され、PRはマージされませんでした。判断を学ぶための架空の例です。

マージを止めても、CIで既に実行されたコードは取り消せません。CIがソースや認証情報へアクセスできたなら、PRが未マージでも調査が必要です。待機期間で守るべき境界は、**新しく選んだ公開直後の版を、そのコードを最初に実行する前に止めること**です。

## この場面の判断例

更新ボットが選んだ候補について、パッケージ名、正確な版、取得元と、その版が取得元で公開された時刻を確認します。PRの作成日やローカルファイルの時刻は公開時刻の代わりになりません。組織が決めた待機期間に達していない場合、インストールより前にその版の採用を止めます。公開時刻を取得できない、情報が古い、判定に失敗した場合も「十分に待った」とは扱いません。

この例のCIは、判定より先にコードを実行しています。後からPRを拒否しても、DEPS-001が実行前に効いたとは言えません。まず実行済みのCIが何にアクセスできたかを調べ、判定をインストール前へ移します。開発者による更新やロックファイルの再生成など、ボット以外の新しい版の選択経路も同じように確認します。

待機期間は、悪意ある公開への警告や公開停止などの情報が現れる時間を作ります。期限を過ぎた版を「安全」と認定する仕組みではありません。スキャナーに指摘がないことも、まだ知られていない問題がない証拠にはなりません。

## 似た対策との違い

ロックファイルは、すでに選んだ版を通常ビルドで再現する助けになります。新たに選ぶ版の公開後経過時間は、それだけでは判断できません。また、プロキシを通すだけでは待機を強制したことになりません。取得時の経路と遮断は[DEPS-005](../psb-deps-005-dependency-acquisition-gate/README.md)、取得したファイルが承認したものと一致するかは[DEPS-003](../psb-deps-003-dependency-artifact-identity/README.md)、インストール時に何を実行させるかは[DEPS-002](../psb-deps-002-install-execution-policy/README.md)で別に判断します。

緊急の更新で待機できない場合は、そのパッケージの特定版だけを対象に、理由と期限を付けた[GOV-002の例外](../../governance-operations/psb-gov-002-security-exception-lifecycle/README.md)を判断します。通常の待機条件を満たした扱いにはせず、将来の版へ許可を広げません。

必要な状態は[control](README.md)、強制点と方式の選択は[設計パターン](../../../../engineering/dependency-security/dependency-release-cooldown/README.md)を参照してください。公開時刻の仕様や資料の採否は[Sources](../../../../sources/README.md#spec-npm-registry-metadata)と[互換性一覧](../../../../sources/README.md#ref-deps-004)にあります。この例は実際のCIでの実行や拒否を確認した結果ではありません。
