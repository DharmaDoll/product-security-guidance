# 同じに見えるコードが違う意味になる

戻る：[PSB-CODE-005 Unicode source review](README.md) · 次へ：[設計pattern](../../../../engineering/secure-coding/unicode-source-review/README.md) · [Python実装](../../../../engineering/secure-coding/unicode-source-review/implementations/python/README.md)

## シナリオ

レビュー画面では、追加された一行が普通のコメントに見えます。しかしソースの中には文字の表示順を変える制御文字があり、画面の並びとファイル内の順序が違います。別の変更では、識別子の一文字だけが似た別scriptの文字に置き換わっています。レビュー担当者は見慣れた変数名だと思っても、Pythonは別名として扱います。

ここで守るのは、レビュー担当者が「このコードを受け入れる」と判断した対象と、実際に解析・実行される文字列の一致です。投稿者が差分を作り、表示環境がそれを人へ示し、言語処理系が元のcode pointを読むところに境界があります。

## 用語を具体例でつかむ

**双方向制御文字**は、右から左へ読む文字を表示する際の並びに影響します。コメントや文字列で正当に使う場面もありますが、コードをplain textとして描く画面では構文の見え方を変え得ます。**不可視文字**は画面で気付きにくい文字です。表示支援が必要ですが、言語によって正当な用途もあります。

**紛らわしい識別子**は、たとえばラテン文字の`a`とキリル文字の`а`（U+0430）を混ぜた名前です。見た目だけでは同じ名前に見えることがあります。**正規化**は、処理系が元の綴りを比較用の形へ変換することです。Pythonは識別子をNFKCで解釈するので、ソースに書かれた見た目と処理系が比較する名前を別々に考えます。

## 判断する順序

1. 変更に含まれる言語とファイルを決め、レビュー画面が実際の文字と字句構造をどう表示するかを確認する。
2. 双方向・不可視文字の存在を示し、文字列やコメントなど正当な用途と、コードを偽る用途を分ける。
3. 識別子は、言語の正規化規則とプロジェクトの命名規則で照合する。単純なmixed-script判定だけでは、正当な多言語名と攻撃を分けられない。
4. 検査結果を受入条件にするなら、対象revision・実行範囲・検査方針を受入側で保持する。解析失敗を合格にしない。

「Unicodeをすべて禁止すればよい」は誤解です。Unicode公式のSource Code Handlingは、字句構造に沿う表示と不可視文字の可視化を勧め、正当な文字の用途にも注意しています。付属のPython例は、ASCII識別子という狭い方針を選んだプロジェクトの実装例です。
