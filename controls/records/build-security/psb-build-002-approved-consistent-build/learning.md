# 学習：同じbuilderでも、別の手順で作れば別のrelease

対応するcontrol：[PSB-BUILD-002 Approved and consistent release build](README.md) · 設計：[Approved release build process](README.md)

製品チームは、ホステッドのビルド基盤で`v3.0`を作ると決めています。担当者はレビュー済みソースを指定しましたが、リリースジョブを手動起動し、通常は無効な`debug=true`を渡しました。ジョブは同じ基盤で成功し、成果物には正しいversion名が付きます。この時、ホステッド基盤で作られたという事実だけでは、レビューしたリリース手順で作られたとは言えません。

ビルド基盤（builder）は「どこがビルドを動かしたか」です。ビルド定義は「何を実行するか」、外部パラメーターと起動条件は「今回どの条件で動かしたか」、ソースのrevisionは「どのコードを入力にしたか」です。これらは異なる問いです。さらに、成果物のdigestは「実際にできたbytes」を指します。名前やversionだけでは、その実行の出力かどうかを判別できません。

直感的な誤りは二つあります。一つは、基盤が承認済みならビルド手順も正しいと思うことです。同じ基盤でも、異なる定義やパラメーターで実行できます。もう一つは、ジョブが`builder.id`や`hosted: true`と書いた記録を基盤の証明とみなすことです。未信頼のジョブはその文字列も作れます。

正規リリースと判断するには、作り手側が承認した基盤と手順を先に定め、今回の成果物digestに結び付いた基盤由来の記録と照合します。ビルド定義を別repositoryで管理するなら、そのrevisionも追跡します。証拠が取得できない時は「問題なし」とせず、公開を止めます。

SLSA Build L2を目標にすると、ホステッド基盤でのビルドと、基盤による認証可能な来歴情報（provenance）が必要です。このcontrolでは、作り手側が選んだ基盤と一貫した手順を確認します。ビルド中の権限・隔離は[BUILD-001](../psb-build-001-build-containment/README.md)、来歴の生成と認証は[BUILD-003](../psb-build-003-platform-provenance-generation/README.md)、利用者側の採否は[REL-001](../../release-integrity/psb-rel-001-signature-provenance-verification/README.md)で別に確認します。

今回の`debug=true`を基盤が正確に記録したなら、来歴の生成は正しくても、承認手順との照合では公開を止めます。逆に、承認済みの設定だとジョブが書くだけでは、その手順で動いたことを確認できません。[BUILD-003の教材](../psb-build-003-platform-provenance-generation/learning.md)で、この記録の出所を続けて考えられます。

ここでいう「一貫した手順」は、毎回同じbytesができる再現可能なビルド（reproducible build）とは異なります。判断するのは、今回使った手順・入力が承認した範囲かどうかです。参照仕様と採否は[SPEC-CONSISTENT-BUILD-PRODUCER](../../../../sources/README.md#spec-consistent-build-producer)を参照してください。

## 実務では、正式なリリース経路を決める

まず、正式なリリースに使うCIの手順を決め、その変更をレビュー対象にします。ソースだけでなく、ビルドスクリプトや呼び出す別のワークフローも対象です。公開に影響する手動入力は、自由に指定させず、許可した値に限定します。例の`debug=true`が未承認なら、CIが成功していても通常リリースへ進めません。

次に、公開するファイルが、その実行で作られたものかを確認します。「v3.0」という名前だけでは、担当者の端末で作った同名ファイルと区別できません。成果物のハッシュと、CI基盤を出所とする実行記録を対応させ、承認したソース・手順・入力と照合します。記録を取るだけでなく、不一致なら公開を止めるところまでが必要です。

これは、ビルドのたびに人が大量のログを読む運用を求めるものではありません。承認した条件を公開前の確認へ組み込み、人は手順や例外の変更をレビューします。条件を満たしたことと、成果物に脆弱性がないことは別です。

## 比較するハッシュを、誰が保証するか

ファイルとハッシュ一覧を担当者が両方持ってきただけでは、今回のCIで作った証拠にはなりません。署名付きの来歴情報を使う構成では、成果物のハッシュとビルドの記録を結び付け、その記録の出所を署名で検証します。

署名は、承認したCIの生成・署名経路で行います。依存コードが動くビルド処理へ長期の署名鍵を渡したり、任意の自己申告へ無条件に署名したりしない構成が必要です。記録生成の責任は[BUILD-003の教材](../psb-build-003-platform-provenance-generation/learning.md)で扱います。

固定鍵を使う方式なら、検証側があらかじめ信頼した公開鍵で署名を確認します。成果物と一緒に渡された知らない公開鍵を、そのまま信用しません。証明書を使う方式なら、証明書内の公開鍵で署名を検証するだけでなく、信頼した認証局につながるか、証明された署名者が許可したCIの実行主体かも確認します。鍵を長期保管しない方式でも、検証鍵や信頼の起点が不要になるわけではありません。

公開前には、署名・署名者の確認、手元のファイルと記録内のハッシュの一致、ソース・手順・入力が承認条件を満たすことを、それぞれ確認します。署名の成功だけでは記録の内容が真実であることや、公開してよいことまで保証しません。根拠は[SLSAの検証手順](https://slsa.dev/spec/v1.2/verifying-artifacts)、採否は[参照資料](../../../../sources/README.md#spec-consistent-build-producer)に残します。

## 講義と振り返りの記録

2026-10-22、BUILD-001に続き、正規のCIでも未承認のdebug入力でビルドした場合を説明しました。実務の出発点として、リリース手順の保護、重要な入力の制限、実際の成果物と実行記録の照合、不一致時の公開停止を補いました。

1. 正規のCIで成功しましたが、未承認の`debug=true`が使われていました。そのまま正式リリースへ進めてよいでしょうか。
2. 正規のCIの成果物と同じ名前を付けたファイルを、担当者が端末から持ってきました。何を照合すれば、今回のCIで作った成果物かを確認できますか。

2026-10-23、一問目には「No」、二問目には「hash値だと思うが、どこで署名したものでどの鍵で検証するのでしょうか？」と回答・質問がありました。講師から、以前の説明で比較するハッシュの出所の説明が不足していたことを認め、署名する経路、固定公開鍵と証明書による検証、署名者の許可条件を本文へ補いました。これは署名方式を導入した記録ではありません。実際のビルド記録・成果物の照合や公開停止は未検証です。
