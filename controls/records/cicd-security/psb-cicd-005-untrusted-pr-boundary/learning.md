# PRが作ったものを、公開ジョブで使ってよいか

[コントロール記録](README.md) · [設計pattern](../../../../engineering/cicd-security/untrusted-pr-boundary/README.md)

外部PRから変更できるものを、誰が作り、どの処理が使うかを追います。問題は特定のGitHub Actionsイベント名だけでは決まりません。使う側にどんな権限があるかまで見て判断します。

## 具体的なシナリオ

公開リポジトリは、外部コントリビューターのPRへ自動的にテスト結果をコメントしようとしています。
ワークフローはコメントを書き込むために`pull_request_target`で起動し、PR側の変更を取得してから
リポジトリ内のテストスクリプトを実行します。ジョブにはコメント用トークンのほか、保護された環境、
自組織のランナー、内部パッケージレジストリへの到達性があります。

攻撃者はテストスクリプトを変更したPRを送ります。その変更が実際に読み込まれて実行されると、スクリプトは
トークンを目的外に利用し、ランナー上のファイルを読み、内部サービスへ接続できます。

チェックアウト時の保護がPRコードの読み込みを止める場合、この経路は成立しません。ただし、別の取得処理やAction、
成果物、キャッシュから読み込む経路もあるため、一つの保護機能だけで信頼境界の確認を終えないようにします。

```text
PR作成者がテストスクリプトを変更
  → 権限付きジョブがPR側の変更を取得
  → 変更されたスクリプトを実行
  → トークン／秘密情報／ランナー／内部ネットワークへ到達
  → リポジトリの変更、情報流出、後続処理の汚染
```

イベント名だけが原因ではありません。実害には次の三条件が必要です。

1. 攻撃者が変更できるコードやファイルが、実際に読み込まれる。
2. 読み込む処理、またはその結果を後で使う処理が、書き込み権限、秘密情報、内部ネットワークなどへ届く。
3. 読み込んだ内容から、それらの権限を使うか、後の処理で使われるファイルを書き換えられる。

三つ目までつながらない場合、ここで説明する最大の被害は成立しません。ただし将来の権限追加で経路が
完成しないよう、未信頼の実行と権限を構造的に分離します。

## 用語

- **PR由来のもの**: PR作成者が直接・間接に変更できるコード、依存関係、入力、成果物、キャッシュ、出力。
- **作る側（producer）**: PRジョブに加え、依存関係を取得したりキャッシュを保存したりする処理。
- **使う側（consumer）**: 作られたものを読み、展開し、解釈し、または実行する処理。
- **使える権限と到達先**: トークンだけでなく、秘密情報、OIDC、保護された環境、ランナー上の資産、内部ネットワークも含む。
- **信頼判断**: 変更のどの版と入力を、どの権限で処理してよいかを新たに決めること。単なる実行承認とは異なる。

## 境界を越える経路

### 同じジョブで越える

PRのコードを取得してから秘密情報を参照する、書き込み可能なトークンを残す、OIDCを発行できるようにする経路です。
`persist-credentials: false`はcheckoutが残す認証情報を減らしますが、ジョブ自体に別の権限があれば十分ではありません。

### 別の実行へ持ち込む

未信頼ジョブが作った成果物、キャッシュ、出力を権限付きジョブが実行したり、その内容だけで公開を決めたりする経路です。
ワークフローを二つに分けても、実行できるファイルや環境をそのまま運べば境界にはなりません。

### ランナーを介して越える

再利用する自組織のランナーへファイルやプロセスを残す、ランナーに残った認証情報を読む、内部ネットワークへ接続する経路です。
`GITHUB_TOKEN`が読み取り専用でも、ランナーが持つ権限は消えません。

## 守るべき境界

```text
PRの変更を実行する処理
  = 書き込み権限や秘密情報を持たない
  + 権限付き処理へ実行できるファイルや環境を残さない

権限を必要とする処理
  = レビュー済みの変更から新しく開始
  + PRの実行で作ったファイルや環境を引き継がない
```

データだけを渡す必要がある場合は、作成元、途中での改変の有無、形式、許可する用途を検証し、
shellの命令、テンプレート、コード、依存関係として解釈されないことを確認します。
想定した実行から届いたことと、内容が事実を表すことも別です。PR実行が作った「検査成功」というデータを形式どおりに受け取っても、
公開の承認や必要な検査の代わりにはしません。

## この場面でどう判断するか

PRへコメントする処理が必要なら、PRの題名など必要なデータだけを受け取り、PRのコードや成果物は実行しないようにします。コメント用の権限があっても、その権限をPRのテストへ渡す理由にはなりません。

一方、PRのテストが作ったスクリプトを公開ジョブでも使いたいと言われたら、そのまま渡しません。公開ジョブはレビュー済みの変更から新しく始め、必要な処理をそこで取得・実行します。テスト結果を表示するためのデータを受け取る場合も、形式と使い道を限定します。「成功」と書かれたデータだけで公開を承認しません。

## 正しい形式の検査結果でも、公開を決めてよいとは限らない

PRの検査jobが、結果ファイルへ「検査成功」と対象のコミットを記録し、公開jobへ渡す設計を考えます。公開側は、想定したjobから届いたこと、ファイルが改変されていないこと、形式が正しいことを確認しました。しかし、PR作成者が結果ファイルを作る処理を変更できるなら、検査せず成功と書くこともできます。

この場合、配送や形式の確認だけでは公開を許可できません。誰が結果を作る処理や判定基準を変更できるか、必要な検査が本当に実行されたか、その結果が公開対象の版に対応するかを確認します。出所を確認することと、その出所が正しい判定を行うと信頼できることは別です。

対策は、公開を許可する検査と判定基準をPR側で勝手に変更できない経路へ置くことです。その検査がPRのコードを実行する場合でも、実行環境には公開権限を渡しません。PR側の結果を表示するだけなら、投稿者側の報告だと分かる扱いにし、独立した公開判断の代わりにしません。

### 検査した版と、公開する版をそろえる

コミットAで検査が成功しても、その後に追加されたコミットBの変更まで確認したことにはなりません。PR番号が同じでも内容は変わります。公開判断では、検査したコミットと公開対象を照合し、Bに必要な検査を行ってから判断します。結果ファイルに書かれたコミット番号も、PR側が自由に書ける自己申告だけでは根拠にできません。

公開する成果物についても、検査結果がどの成果物に対応するかを追えるようにします。「誰が、変更から守られたどの判定処理で、何を検査したか」をそろえることが要点です。これは必要な検査を通った範囲の判断であり、すべての脆弱性がないという保証ではありません。

## よくある誤解

### 「`pull_request_target`は常に危険」

イベント自体ではなく、権限付きの処理がPR由来のコードやファイルを読み込むことが問題です。PR本文を
検証済みのデータとして扱い、限定した権限でラベルだけを操作する処理は設計できます。ただし、後から
PRのコード取得やスクリプト実行が追加される変更も保護する必要があります。

### 「一度、メンテナーが承認すればコードは信頼済み」

承認は実行を許可しますが、内容を作った人は変わりません。承認後のPR更新、依存関係、成果物、キャッシュまで
自動的に信頼済みになるわけではありません。

### 「最初のジョブがread-onlyなら後続も安全」

後続の権限付きジョブが、最初のジョブの成果物やキャッシュを実行すれば攻撃経路は残ります。実際に使う処理まで追跡します。

### 「`main`へのpushならレビュー済み」

`push`イベントと取得したSHAの一致は、レビューの有無を示しません。直接pushやブランチ保護・rulesetの
迂回で入る変更もあり得ます。権限付き処理をレビュー済みの変更だけから始めるなら、採用先の有効な保護条件と例外を確認します。

### 「ワークフローのファイルを見れば導入を証明できる」

forkからの実行設定、実際の権限、秘密情報、保護された環境、ランナーの割当、実際に動いた版は提供元側の状態です。
取得できない場合は`PASS`にしません。

### 「新しいランナーなら、PRの実行の影響は残らない」

別の実行環境でも、PRの成果物や外部キャッシュを戻して実行すれば影響は残ります。
[キャッシュの教材](../psb-cicd-009-cache-trust-boundary/learning.md)は保存者と取得範囲、[ランナーの教材](../psb-cicd-007-runner-lifecycle-isolation/learning.md)は同じホストに残るプロセスや保存領域を分けて扱います。

## 設計レビューで使う問い

1. PR作成者が直接・間接に変更できるものは何か。
2. それを読むすべてのジョブ、ワークフロー、キャッシュ、成果物、スクリプト、サービスは何か。
3. それぞれの処理が持つトークン、秘密情報、OIDC、保護された環境、ランナーの資産、ネットワーク到達性は何か。
4. 権限付き処理は、変更のどの版と入力を新しく信頼したのか。
5. 実行できるファイルや環境を別の実行へ持ち込んでいないか。データだけなら、どこで何を検証するか。
6. 確認できていないワークフローや提供元設定を、どの状態で記録するか。

実際に確認する項目は[Controlの診断項目](README.md#failure-checks)にあります。トークンや権限の用途は[CICD-004の教材](../psb-cicd-004-workflow-authority-minimization/learning.md)で考えます。

## 攻撃連鎖の前後

このノートが詳しく扱うのは[サプライチェーン攻撃の第5段階](../../../../docs/ANALYSIS_LENSES.md#サプライチェーン攻撃の12段階)です。
第2段階のソース変更と第4段階の依存関係を入力として受け取り、第6段階のCI/CD ID、第7段階のランナー、
第9段階のリリースへ、信頼境界を壊さず引き継ぐ必要があります。

## 講義と振り返りの記録

2026-10-21、CICD-004に続き、PR側が作る検査結果を公開jobへ渡すシナリオで講義を開始しました。出所・形式・改変の有無の確認と、判定の信頼性・対象の版を分ける説明を補いました。正しい配送だけで公開してよいか、検査後に対象の版が変わった場合を二問で確認しました。

- 一問目には「結果の元となるロジックや主体」と回答がありました。講師から、誰が判定処理を変更できるかに加え、必要な検査が実際に行われたかを確認する、と補足しました。
- 二問目の、Aの成功だけで更新後のBを公開できるかには「No」と回答がありました。講師から、PR番号ではなく検査対象の版と公開対象を対応させ、Bに必要な検査を行う、と補足しました。

出所の確認、判定処理の保護、対象の一致を別々に確かめる判断を教材へ反映しました。実CIの検査・公開拒否は未検証です。
