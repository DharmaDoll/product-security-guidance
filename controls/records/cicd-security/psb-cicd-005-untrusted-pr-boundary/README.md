# PSB-CICD-005: Untrusted PR boundary

具体的な攻撃経路を学ぶ：[学習ノート](learning.md)

設計する：[Untrusted PR boundary pattern](../../../../engineering/cicd-security/untrusted-pr-boundary/README.md)

## 問い

コントリビューターが変更できるコード、依存関係、入力、成果物、キャッシュ、出力を、リポジトリへの書き込み、
秘密情報、OIDC、保護された環境、永続ランナー、内部ネットワークへ到達できる処理から分離できるか。

## できてはいけないこと

未信頼の変更を検証するために実行したコードや、その実行が作った状態が、同じジョブまたは後続処理で
権限を利用できてはいけません。レビュー承認、イベント名、実行者名、ラベルだけを新しい信頼判断として扱うこともできません。

## なぜ重要か

プルリクエストを作成できること自体は、リポジトリやクラウドへの権限ではありません。実害は、攻撃者が
変更できる処理が実行され、その処理から価値のある権限または状態へ到達し、API操作、外部通信、永続化、
後続処理の汚染によって利用できる場合に成立します。イベント名ではなく、「誰が状態を作り、どの処理が
それを消費し、その処理には何の権限があるか」を追跡します。

## 横断分析での位置

| 分析軸 | 関係 | このコントロールが扱うこと | 次へ引き継ぐこと |
|---|---|---|---|
| プラットフォームとインフラストラクチャ | 直接 | CIの実行境界と権限の分離 | CI基盤の管理面、ビルド基盤、クラウド認可 |
| 外部依存とサプライチェーン | 直接 | 外部コントリビューター由来の状態が権限処理へ進む経路 | 依存関係、来歴、署名、配布 |
| 攻撃段階5：CIワークフロー、PR、Action、キャッシュ | 直接 | 未信頼のproducerと権限を持つconsumerの分離 | CIのID、ランナー、ビルド、リリースでの境界維持 |
| 攻撃段階6：CI/CDのIDと管理面 | 隣接 | 未信頼処理からtoken、secret、OIDCを外す | 信頼条件、audience、管理面の変更保証 |
| 攻撃段階7：ランナーとビルド実行 | 隣接 | 未信頼処理に永続資産や内部到達性を与えない | 一回限りの実行環境、破棄、隔離、検知 |

この位置付けは[`REF-PORTFOLIO-001`](../../../../sources/README.md#ref-portfolio-001)と
[`LOCAL-SUPPLY-CHAIN-ATTACK-STAGES`](../../../../sources/README.md#local-supply-chain-attack-stages)を使った
探索用の関係です。コントロールへの合格や組織への導入を示しません。

## 適用範囲

外部または低信頼のコントリビューターが変更できる状態を実行・消費するCIワークフローと、その状態を
受け取る後続ジョブ、再利用ワークフロー、キャッシュ、成果物、リリース処理に適用します。

次は直接の対象ではありません。

- 個々のトークンやOIDC信頼条件を最小化する詳細設計。
- ランナーイメージ、登録情報、一回限りのライフサイクルを保証する仕組み。
- 依存パッケージ、外部Action、ビルド成果物自体の完全性。
- マージ後のソース変更が正当であることや、リリース承認の妥当性。

## 必要なセキュリティ特性

| ID | 成立すべき状態 |
|---|---|
| `PR-BOUNDARY-1` | コントリビューターが変更できるコードと状態、そのproducer、すべてのconsumer、各consumerの実効権限を特定する |
| `PR-BOUNDARY-2` | 未信頼の状態を実行する処理から、書き込み権限、秘密情報、OIDC、保護された環境を除く |
| `PR-BOUNDARY-3` | 未信頼の処理を、永続資産、後続ジョブへ残る状態、内部ネットワークへ到達できない実行境界に置く |
| `PR-BOUNDARY-4` | 未信頼の成果物、キャッシュ、出力、依存関係を、権限処理が実行可能または信頼済みの状態として自動的に受け取らない |
| `PR-BOUNDARY-5` | 権限処理はレビュー済みrevisionから新しく開始し、未信頼の実行状態に依存しない。データだけを受け取る例外では、形式、完全性、用途を別に検証する |
| `PR-BOUNDARY-6` | 全ワークフロー、実効設定、実際の実行を確認できない場合は、合格ではなく`NOT_CHECKED`または`ERROR`とする |

## 実装判断の羅針盤

1. イベント名ではなく、コントリビューターが変更できるすべての状態を列挙する。
2. producerからconsumerまでを追跡し、途中のcache、artifact、output、workspaceも入力として扱う。
3. 未信頼の実行から権限を外す。権限が必要な処理は、レビュー済みrevisionから別に開始する。
4. `pull_request_target`を一律に安全または危険とみなさない。PR由来の実行可能状態を読み込むかで判断する。
5. 承認操作は実行を許可する判断であり、コードや成果物の出所を変えるものではない。
6. 設定例だけで導入済みと判断せず、提供元の設定と実際の実行結果を確認する。

GitHub Actions向けの具体例は[実装例](../../../../engineering/cicd-security/untrusted-pr-boundary/implementations/github-actions/README.md)にあります。

## 判定例

| 観測した状態 | このコントロールでの判断 |
|---|---|
| `pull_request`ジョブにread-only tokenしかないが、組織内のself-hosted runnerを再利用している | 合格を裏付けない。ローカル資産、永続化、内部ネットワークを確認する |
| `pull_request_target`でPRのheadをcheckoutし、テストを実行する | 不合格。未信頼コードを権限のある文脈へ持ち込んでいる |
| PR検証結果をartifactで渡し、後続の権限ジョブがその中のscriptを実行する | 不合格。イベントを分けても実行可能状態が境界を越えている |
| メタデータ専用処理がPR本文を構造化データとして検証し、限定した権限でラベルだけを操作する | 条件付きで適合し得る。PRのコード、依存関係、成果物を読み込まないことを別に確認する |
| マージ後の保護ブランチを新しくcheckoutし、PR実行の状態を使わず処理を始める | `PR-BOUNDARY-5`を支える。ただしブランチ保護や権限の実効状態は別途確認する |
| fork設定や実際のrunを取得できない | `NOT_CHECKED`または`ERROR`。安全とは判断しない |

## 保証しない範囲

このコントロールは、未信頼処理から価値のある権限と状態を分離しますが、テスト対象コードが安全であること、
信頼済みブランチが侵害されないこと、権限処理そのものに脆弱性がないことは保証しません。分離により
pre-mergeで実行できない統合試験が生じる場合は、mock、隔離された検証環境、merge queue、迅速なrollbackを検討します。
