# PSB-CICD-005: Untrusted PR boundary

**外部PRで変えられるコードや成果物から、書き込み権限や秘密情報に届かないか。**

## なぜ必要か

PRのテストへ公開用トークンを渡さなくても、そのテストが作ったスクリプトを後の公開ジョブが実行すれば、権限を使われます。PRのコードを動かす場所と、その結果を受け取る場所を一緒に確認します。

## 満たすべきこと

1. **変えられるものを追う。** PR作成者が変えられるコード、依存関係、設定、成果物、キャッシュ、出力と、それを後で使う処理を洗い出す。各処理が持つ権限も確認する。
2. **権限を渡さない。** 未確認のコードを実行する処理には、書き込み権限、秘密情報、クラウド認証用の権限、保護された環境を渡さない。永続ランナーや内部ネットワークなど、トークン以外の到達先も確認する。
3. **後続処理へ持ち込まない。** 権限を使う処理は、レビュー済みの変更から新しく始める。PRの実行で作ったスクリプトやキャッシュを信頼済みとして実行しない。データだけを渡す場合も、内容と使い道を検証する。

PRの実行を承認した人がいても、PRの内容や作られた成果物の出所は変わりません。ワークフロー、サービス側の設定、実際の実行を確認できない場合も、境界が守られているとは判断しません。

## 基本の分け方

```text
CICD-005
外部PRのコード・依存関係
  → 権限のない検証環境 → 検証結果

レビュー済みの変更
  → 新しい作業領域で権限付き処理を開始
```

PR検証で作ったスクリプト、依存環境、キャッシュ、成果物を後の権限付きジョブが実行すれば、ジョブを分けても境界は破れます。後続へデータだけ渡す場合も、形式、内容、使い道を検証し、コードやコマンドとして解釈しません。PRが自己申告した成功だけを公開の承認にもしません。

## 設計時に確認すること

| 判断 | 見る場所 |
|---|---|
| PRから何を変えられるか | コード、テスト、依存関係、設定、読み込む外部ファイル、ジョブ出力、成果物、キャッシュ。作成元から受け取る処理まで追う |
| どんな権限へ届くか | トークンだけでなく、秘密情報、OIDC、保護された環境、ランナー上の認証情報、管理用ソケット、内部ネットワーク、後続ジョブの権限を見る |
| PRをどこで実行するか | 書き込み権限や秘密情報を渡さず、できれば使い捨ての環境で実行する。永続ランナーや後続ジョブへ状態を残さない |
| 権限付き処理を何から始めるか | レビュー済みの変更を新しく取得する。ブランチへの直接pushや保護設定の例外も確認する。PR検証の作業領域や成果物を引き継がない |
| 結果だけ渡す場合はどうするか | 作成元、対象の版、形式、許可する値、受け取る側の使い道を決める。表示用の結果と、権限操作を許可する判断は分ける |

イベント名や実行者名、ラベル、過去の実行承認だけでは、PRの内容が信頼済みに変わりません。`pull_request_target`のような権限付きの起動方式でも、PRからコードや依存関係を読み込むかどうかで判断します。マージ後の実行でも、未レビューの変更が直接pushや例外経路から入るなら、レビュー済みとは言えません。

## 方式を選ぶ

| 方法 | 向く場面と負担 |
|---|---|
| PRでは無権限の検証だけ行い、権限付き処理はレビュー後に始める | 境界が分かりやすい。マージ前の統合試験は限定される |
| PRのメタデータだけを扱う権限付き処理を分ける | ラベルやコメントが必要な場合。PRのコードを実行せず、本文をコマンドとして解釈しない |
| 隔離した一時環境で統合試験する | 外部サービスが必要な場合。権限、通信先、環境の破棄を別に決める |
| 厳密に検証したデータだけ後続へ渡す | 検査結果の表示など。PR由来の成果物全体を信頼しない |

具体的な設定は[GitHub Actionsの実装例](../../../../engineering/implementations/github-untrusted-pr/README.md)を参照してください。設計レビューでは[controlの診断項目](README.md#failure-checks)を使い、全関連ワークフローの権限とデータの流れを確認します。実際の導入ではサービス側のfork・権限・環境・ランナー設定と無害なPRの実行も確認します。確認できない経路を合格にしません。

<a id="failure-checks"></a>

## 診断で確認する項目（異常時テスト）

- PRのコードや依存関係を変えると、トークンを渡していないつもりの処理から書き込み権限や秘密情報へ届かないか。
- PRが作ったスクリプト、成果物、キャッシュを、後続の権限付き処理が実行していないか。
- 実行の承認後にPRを更新したとき、古い承認だけで新しい内容を権限付き処理へ渡せないか。
- マージ後の処理がレビュー済みの変更から始まっているか。直接pushや保護設定の例外で未レビューの変更を混ぜられないか。
- fork設定や実際の実行を確認できないとき、設定例だけで合格と判断していないか。

これらは設計レビューや診断の確認項目です。試す場合は無害な入力と使い捨ての対象を使い、実際の秘密情報を取り出しません。

## フレームワークとの関係

GitHubの3件は公式の製品ガイダンス、OSPSの1件は規格との関係です。

| 参照先 | このControlとの関係 | 限界 |
| --- | --- | --- |
| GitHub「Secure use」 | 権限付きjobで未信頼PRのコードを動かさず、別runの成果物やrunnerの資産も確認する。 | 全ての受け渡し経路を網羅した証拠ではない。 |
| GitHub「Securely using pull_request_target」 | 権限付きイベントでPRコードを実行するとtokenやsecretへ届く経路を説明する。 | そのイベントの一律禁止やcheckoutだけでの実行を意味しない。 |
| GitHub「Actions repository settings」 | Fork workflowとtokenの既定権限を確認する手掛かりになる。 | Job固有の権限、secret、runner、成果物の受け渡しは別に確認する。 |
| OpenSSF OSPS Baseline 2026.02.19 OSPS-BR-01.03 | 未信頼の変更を扱うCIから特権認証情報・資産へ届かせない判断を支える。 | 特定のGitHubイベントやcache設定を規定しない。 |

対象特性と残る範囲は[マッピング](../../../../mappings/frameworks.yaml)に記録しています。実際のrunでの拒否やOSPSへの準拠を示しません。

## このコントロールの範囲

対象は、低信頼の変更をCIで実行したり、その結果を後続処理で使ったりする経路です。個々の権限の絞り方は[CICD-004](../psb-cicd-004-workflow-authority-minimization/README.md)、キャッシュの信頼は[CICD-009](../psb-cicd-009-cache-trust-boundary/README.md)、ランナーの残存状態は[CICD-007](../psb-cicd-007-runner-lifecycle-isolation/README.md)で詳しく扱います。この分離だけで、レビュー済みコード自体の安全性は保証しません。

攻撃の流れは[教材](learning.md)、GitHub Actionsの設定例は[実装例](../../../../engineering/implementations/github-untrusted-pr/README.md)を参照してください。6つの特性と根拠のIDは[control.yaml](control.yaml)、資料の採否は[Sources](../../../../sources/README.md#ref-cicd-010)、フレームワークとの関係は[マッピング](../../../../mappings/frameworks.yaml)、旧関係の採否は[移行台帳](../../../../docs/MIGRATION.md#2026-10-04cicd-005のframework関係を再照合)にあります。

工程をまたぐ判断は[PRの検証からリリース用ビルド・公開への引き渡しまで](../../../../engineering/pull-request-to-release-build.md)で確認できます。
