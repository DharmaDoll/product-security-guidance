# 正しいOIDCトークンでも、本番権限を渡してよいか

[コントロール記録](README.md) · [設計パターン](../../../../engineering/cicd-security/workload-federation-boundary/README.md)

## シナリオ：別のジョブも本番権限を得られた

チームはCIに保存していた長期のAWS鍵を廃止し、GitHubのOIDCトークンをAWSの一時的な権限へ交換する方式に変えました。本番へのデプロイ用ジョブだけに権限を渡すつもりです。

ところが交換先の許可条件（trust policy）が組織内の全リポジトリを許していると、侵害された別のテスト用リポジトリからも本番の権限を得られる可能性があります。トークンをGitHubが正しく発行したとしても、**そのジョブへ本番権限を渡してよいか**は別の判断です。

リポジトリを一つに限定した後も、同じ`production`環境を使う別のワークフローからトークンを取得できるなら、デプロイ用ジョブだけの許可にはなりません。さらに、許可したジョブ内の処理が侵害されれば、一時的な認証情報の有効期間中に権限を使えます。被害範囲は交換後に許した操作と対象によって変わります。

## 答えから考える：鍵の保管と、権限を渡す判断は別

このシナリオで直すのは、クラウド側が「どのジョブへ権限を渡すか」を決める条件です。長期の鍵をCIへ保存しないことには意味がありますが、別のリポジトリも本番権限を取得できる条件は、そのまま残ります。盗んだ鍵がなくても、許可条件を満たす別のジョブから権限を取得できるためです。

許可するジョブを絞った後は、取得できる権限も確認します。本番へ成果物を配置するだけの仕事に、バックアップの削除まで許す必要はありません。短命化は使える時間を狭めますが、その時間内にできる操作は減らしません。「誰へ渡すか」と「何をさせるか」を両方絞ることが、このcontrolの中心です。

## 発行、交換、利用を分けて考える

発行者（issuer）はトークンを発行した相手、受け入れ先（audience）はそのトークンを使う相手、主体（subject）は権限を求めるジョブの実行文脈を示します。これらはトークン内の情報（claim）です。情報が入っているだけでは制限にならず、交換先が必要な値を条件として照合して初めて効きます。こうして外部の発行者が示した身元を、受け入れ先の一時的な権限へ交換する仕組みがworkload federationです。

```text
ジョブ側：どの処理がトークンを要求できるか
  → 交換先：発行者・真正性・期限を確認し、この実行文脈を許すか
  → 権限側：どのアカウントで、何を、どの対象へ、いつまでできるか
```

ジョブ側で取得を絞っても、交換先が広く受け入れれば別のジョブを止められません。交換先を絞っても、渡す権限が広ければ正規ジョブの侵害による被害が大きくなります。

## この場面でどう判断するか

組織内の全リポジトリを許す条件が見つかったら、まず本番権限の移行が完了したとは扱いません。交換先が実際に照合できる値を調べ、意図したリポジトリと実行文脈に絞ります。`production`という環境名だけを条件にするなら、どのブランチやワークフローがその環境を使えるかも確認します。交換先で区別できない条件は、保護された環境やワークフローの変更管理など、実際に強制できる場所へ置きます。それでも別のジョブを排除できなければ、「デプロイ用ジョブだけ」とは判断しません。

条件を直した後は、意図したジョブが交換できることと、別のジョブや別の受け入れ先を指定したトークンが拒否されることを分けて確かめます。正しい役割を得られたことだけでは十分ではありません。その役割で許される操作と対象、有効期間も確認します。古いAWS鍵は保存場所から消すだけでなく、以前の利用者を移したうえで提供元側で使えないことを確かめます。設定や拒否結果を取得できない部分は未確認として残します。

## 直感と実際の境界

| 直感 | 確認すること |
|---|---|
| OIDCなら認証情報は盗まれない | トークンと交換後の一時的な認証情報も、実行中の処理から漏れる可能性がある |
| 環境名が`production`なら`main`だけ | トークンや環境の保護設定で、許すブランチが実際に制限されているか |
| リポジトリを固定したのでワークフローも固定 | 同じリポジトリで同じ条件を使える別のワークフローはないか |
| トークンに識別子があるので再利用できない | 交換先が一度限りの利用を強制しているか。識別子の存在だけでは保証しない |
| `get-caller-identity`が成功したので最小権限 | 正しいアカウント・役割の確認と、許可した操作・対象の妥当性は別 |
| 秘密情報の保存先から旧鍵を消したので移行完了 | 提供元側で旧鍵や既存の一時的な認証情報が使えないか、旧鍵を使う処理が残っていないか |

別のジョブのトークンが交換先で拒否されれば、その経路から本番権限は得られません。ただし正規ジョブが侵害される経路は別です。短い有効期間は悪用できる時間を狭め、操作権限の限定は影響範囲を狭めます。

## レビューで使う問い

「どのジョブがトークンを取得でき、交換先はどの条件で拒否し、交換後は何を操作できるか」を説明してください。
ワークフロー、環境の保護設定、交換先の許可条件を変えたとき、その説明が成り立つか確認します。
意図したジョブの成功と、別の主体・受け入れ先を指定したトークンの拒否は別々に観測します。

この教材は[REF-PORTFOLIO-001](../../../../sources/README.md#ref-portfolio-001)を使い、
プラットフォームの認証を運用・ガバナンスへ接続するリポジトリ独自の解釈です。
[攻撃段階5→6→7→9・10](../../../../docs/ANALYSIS_LENSES.md)では、
未信頼の変更、権限取得、ランナー、公開・デプロイの責任を分けて読みます。

## 講義と振り返りの記録

2026-10-21、CICD-005に続き、長期の鍵を廃止しても別リポジトリのジョブが本番権限を得られるシナリオで講義を開始しました。鍵の保存をなくすこと、権限を渡す相手を絞ること、取得後の操作を絞ることを分けて説明しました。

1. 長期の鍵はなくなったものの、テスト用リポジトリからも本番権限を取得できます。どこの、何を制限する必要がありますか。
2. 正規のデプロイジョブだけに絞れました。ただし、取得する権限には不要なバックアップ削除も含まれています。有効期間が短ければ、この権限を残してよいでしょうか。

一問目には「利用できるリポジトリ・ブランチを制限する」、二問目には「必要最小限にする」と回答がありました。講師からは、条件を書くだけでなく、交換先やCI側の保護設定で実際に制限できているかを確認する、と補足しました。環境名だけでブランチまで限定できると決めつけず、条件をどこで強制するかを確かめます。短命な権限でも不要な操作は除きます。

実環境での権限取得・拒否・操作範囲は未確認です。
