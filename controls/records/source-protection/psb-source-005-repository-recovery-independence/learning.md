# リポジトリを失っても修正を続けられるか

対象controlは[SOURCE-005 Repository recovery independence](README.md)です。ここでは、コピーを保管することから開発再開までの違いを考えます。

## 一つの事故から考える

製品の修正に必要な`main`、保守ブランチ、リリースタグを持つリポジトリが削除されました。原因は、盗まれたソース管理者のセッションです。開発チームは「毎晩バックアップしている」と答えます。

調べると、コピーは同じ組織内の別リポジトリにあり、盗まれた権限でこちらも削除できます。コピーの場所を変えても、破壊できる主体が同じなら復旧手段は一緒に失われます。これはRECOVERY-3で問う境界です。

次に、別の保管先に昨日のGitコピーが見つかりました。そこには`main`がありますが、必要なリリースタグがありません。`git fsck --full`は成功しました。それでも、タグを基に過去版の修正を始めることはできません。

`fsck`は存在するGit objectの整合性等を調べるものです。製品が必要とするタグの一覧を知っているわけではありません。必要なref名とobject IDを、復旧時にバックアップだけから作らず、取得時の記録や製品の復旧対象と照合します。これがRECOVERY-1とRECOVERY-5の関係です。

もう一つ、必要なrefが全部そろう世代でも安心はできません。削除の前に攻撃者がworkflowや製品コードを書き換え、その後の取得が成功していれば、`fsck`も取得時のref一覧との比較も通ります。これは「変更された内容を正確にコピーした」という結果です。復旧担当は変更が始まった可能性のある時点と、承認済みの変更記録・以前の保管世代を照合し、どの世代を採用できるか判断します。時点が不明なら最新世代を自動採用せず、疑わしい世代を調査用に残して判断を保留します。

## 用語を判断に結び付ける

| 用語 | 何を判断するために使うか |
|---|---|
| ref | ブランチやタグが指すobjectを識別する。名前の存在だけでなくobject IDも照合する |
| mirror clone | 通常の作業用cloneと異なりrefを写すGitの方式。ソース管理サービスの全設定を写す意味ではない |
| 保管世代 | 特定時点のコピー。最新の一つを更新し続けるだけでは、不正変更前の状態も失われ得る |
| RPO | 復旧できる時点がどれだけ古くてもよいか。毎晩の取得が製品の許容するデータ損失に足りるかを判断する |
| RTO | 開発再開までどれだけ待てるか。Gitの転送時間だけでなく、必要なデータ・設定・確認まで含める |
| 保持期間の保護（retention lock） | 取得済みの世代を誰がいつ消せるか。書込担当が保持期間を短縮できないかも確認する |

## 履歴が戻った後にも残ること

正しいタグからソースを取り出せても、LFS管理のファイルはpointerだけかもしれません。Submoduleは別リポジトリのcommitを指していても、そのリポジトリの内容を含みません。これらがビルドに必要なら、別に戻す経路が必要です。

さらに、復元先のアクセス制限が外れたままでは、戻したソースを別の人が変更できます。旧workflowを不用意に動かせば、侵害されたスクリプトや認証情報を再利用するかもしれません。まず履歴を実行せずに照合し、必要な制限と実行環境を準備してから、隔離した場所で修正・ビルドを確かめます。

RECOVERY-6の合否はここまでの確認で判断します。[Git mirror例](../../../../engineering/source-protection/independent-repository-backup-and-restore/implementations/git-mirror/README.md)の成功は、開発再開の全条件やRTOを満たした証拠ではありません。

## よくある誤解を問いへ変える

- 「削除禁止だからバックアップは不要」：制限を変更できる管理者が侵害されたら、何が残るか。
- 「別bucketだから独立している」：同じIDで削除できないか。暗号鍵や復旧用IDを失っても取り出せるか。
- 「最新コピーが一番よい」：不正変更前の世代を選べるか。その時点のソースをどう判断するか。
- 「GitHubからarchiveを取得したから戻せる」：取得できることと、その形式から必要なデータを戻せることを実際に区別したか。
- 「テストが成功したから組織も復旧できる」：使ったのは実保管世代か、手元の練習用コピーか。対象範囲と時間を何で確認したか。

方式・権限・保持・復旧確認を組み合わせる判断は[設計パターン](../../../../engineering/source-protection/independent-repository-backup-and-restore/README.md)、資料の採否は[参照資料](../../../../sources/README.md#ref-repository-recovery-001)からたどれます。
