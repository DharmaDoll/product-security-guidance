# PSB-SOURCE-005: Repository recovery independence

重要なリポジトリを失ったとき、ソース管理サービスとは別に保管したデータから開発を再開できるかを問います。
読者はリポジトリ管理者、バックアップ担当、製品の開発責任者です。守る資産は、修正・再ビルド・調査に必要な履歴と、その利用を再開するための設定・関連データです。

例えば、盗まれた管理者セッションでリポジトリが削除されたとします。同じ管理者がバックアップも削除できれば、コピーがあっても復旧手段は残りません。Gitの履歴だけ戻せても、必要なLFSファイルやアクセス制限を戻せなければ、開発再開には届きません。

## 適用範囲と直接の失敗

製品の修正・再構築・調査に必要なリポジトリを、製品の責任者が選びます。対象の識別子、必要なデータ、許容するデータ損失と復旧時間を決めるところから、隔離先での復旧確認までを扱います。

直接の失敗は、ソースを破壊できる権限や同じ障害が保管済みの復旧手段まで失わせること、または欠けた・古い・取り出せないバックアップを復旧可能と扱うことです。攻撃者はソース管理者の権限を奪った者、障害要因は誤操作、収集の失敗、暗号鍵や復旧用IDの喪失です。

## 満たすこと

| 特性 | 判断・強制すること |
|---|---|
| RECOVERY-1 | 対象の固定した識別子、必要なブランチ・タグ・関連データ・設定、責任者を決める。許容するデータ損失時間（RPO）と開発再開までの時間（RTO）も決める |
| RECOVERY-2 | リポジトリの削除・移管、重要なブランチ・タグの削除・履歴の書換えを必要な主体に限定する。制限を変更・迂回できる権限も把握する |
| RECOVERY-3 | ソースの破壊権限やバックアップの書込権限だけでは、保管済みの世代を削除・上書きしたり、保持期間を短縮したりできない。暗号鍵と復旧用IDの管理も分ける |
| RECOVERY-4 | 最後に成功した取得時点、収集範囲、保管世代、取得障害を区別する。RPO超過を検知し、破壊や不正変更の前に戻れる世代を残す |
| RECOVERY-5 | 破壊・不正変更の経緯を踏まえて復旧に使う世代を選び、実際の保管世代を隔離先へ戻して独立した期待値と照合する。必要なref・内容・外部データの欠落、破損、読取り不能、侵害が疑われる内容を復旧成功にしない |
| RECOVERY-6 | 必要な設定とアクセス制限を戻したうえで、開発チームが隔離した環境で修正またはビルドを行えることを確認する。そこまでの時間と未解決の失敗を記録する |

強制点は一つではありません。破壊操作はソース管理側、世代の保護は保管先、復旧の合否は製品の責任者が確認します。ソース管理者がバックアップの削除権限まで持つ構成では、信頼境界を分けたことになりません。

直接の参照資料は[REF-REPOSITORY-RECOVERY-001](../../../../sources/README.md#ref-repository-recovery-001)です。RPO・RTOの値や確認間隔は組織が決め、資料中の例を共通要件にはしません。

## 診断で確認する項目（異常時テスト）

以下は設計レビュー・診断で使う観点です。実施済みの結果ではありません。

| 試す状況 | 確認する結果 |
|---|---|
| 通常の開発者、管理者、Appから削除・移管・force pushを試す | 誰が拒否され、誰が制限を変更・迂回できるかが説明できる。ブランチの保護をリポジトリ自体の削除禁止と混同しない |
| ソース管理用IDとバックアップ書込IDで保管済み世代を削除する | 保護対象の世代の削除と保持期間短縮が拒否される。別名のbucketや別repositoryだけで独立性を判断しない |
| 暗号鍵を無効化する、復旧用IDが使えない | コピーが残っていても取出し不能として扱い、代替の復旧経路と責任者へ渡す |
| 取得失敗、対象の移管、RPO超過が起きる | 前回の成功を今回の成功にせず、対象漏れ・経過時間を担当者へ渡す |
| 必要なタグがない、タグ名は同じでもobject IDが異なる、LFS実体がない | `fsck`やファイル数だけで成功にせず、期待する復旧対象との不一致を示す |
| 不正なソース変更の後に取得した最新世代が`fsck`とref照合を通る | 取得時点の一覧だけで正常な内容と判断しない。変更の経緯、承認済みの変更記録、前の世代を照合し、採用できる時点を判断する。判断できなければ保留する |
| 元サービスが使えず、保管世代だけから復旧する | 元サービスへの追加取得に頼らず、必要なデータを取り出せる |
| 復元先に広い権限や自動実行が残る、RTOを超える | 履歴の復元と開発再開を別の結果にし、制限・実行環境・時間の不足を残す |

## 境界と読み進め方

Gitのコピーは、LFS実体、submoduleの別リポジトリ、Issues、PR、Packages、ruleset、権限、Secrets等を一括復元するものではありません。必要なものをRECOVERY-1で選び、それぞれの復元方法を確認します。ハッシュの一致も、バックアップが改ざんされていないことや、選んだソースが侵害前だったことを単独では証明しません。

このcontrolは、製品の稼働データやサービス全体の災害復旧を扱いません。[SOURCE-004](../psb-source-004-source-access-credential-lifecycle/README.md)はIDの発行・失効、[GOV-004](../../governance-operations/psb-gov-004-credential-exposure-containment/README.md)は漏えい後の権限封じ込め、[GOV-005](../../governance-operations/psb-gov-005-deployed-artifact-recovery/README.md)は配布済みartifactの置換を扱います。

[教材](learning.md)で「コピーがある」と「開発を再開できる」の違いを追い、[設計パターン](../../../../engineering/source-protection/independent-repository-backup-and-restore/README.md)で方式を選びます。[Git mirror例](../../../../engineering/source-protection/independent-repository-backup-and-restore/implementations/git-mirror/README.md)は手元で履歴の復元を試せます。旧4項目との関係は[移行記録](../../../../docs/REPOSITORY_RECOVERY_MIGRATION.md)へ分けています。
