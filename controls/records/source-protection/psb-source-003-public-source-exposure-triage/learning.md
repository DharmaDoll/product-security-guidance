# 自社ドメインが見つかった後に何を確認するか

[Control: PSB-SOURCE-003 Public source exposure triage](README.md) · [設計: Public exposure observation and triage](../../../../engineering/source-protection/public-exposure-observation-and-triage/README.md)

自社とは関係のないリポジトリに、自社の情報が貼られていたらどうするかを考える教材です。読む人は、セキュリティ担当者と、その情報を管理する人を想定しています。

## 自社の検査では見つからない投稿

開発チームは、自社のリポジトリへ秘密情報を入れないよう検査しています。ところが、第三者が公開リポジトリのIssueに自社の情報を貼った場合、その検査では見つけられません。そこで自社ドメインと連絡先メールアドレスを検索すると、同じIssueが両方の検索結果に出ました。

検索結果は、調べるきっかけです。まずそのIssueを開き、本当に公開されている内容を確かめます。ドメイン名やメールアドレスだけなら、公開する予定の連絡先かもしれません。一方、社内だけで使う接続先や認証情報が含まれていれば、第三者が内部構成を調べたり、サービスへのアクセスを試みたりする手がかりになります。

**見つかっただけで漏えいと決めず、問題なしとも決めません。** その情報は社内機密か、公開する意図があったか、第三者が知ると何ができるかを、情報の所有者と確認します。見つけた認証情報を使ってログインを試す必要はありません。

## 見つけた後の流れ

| 段階 | 確かめること |
|---|---|
| 検索 | どの言葉で、どの公開場所を、どこまで調べられたか |
| 内容の確認 | 自社に関係する情報か、公開する意図があったか、誰が判断するか |
| 通知 | 判断に必要な人へ届いたか。届かなければどう再送するか |
| 対応 | 削除、認証情報の失効、影響調査などを誰が担い、結果をどう確認するか |

通知には、投稿のURLなど必要な情報だけを載せます。認証情報や投稿の本文をチャットやチケットへコピーすると、新たな漏えい先を作るおそれがあります。通知先のシステムが受け付けても、担当者が読んだことや対応が終わったことまでは分かりません。

## 同じIssueでも内容が変われば確認し直す

最初の検索では、ドメイン名とメールアドレスが同じIssueに当たりました。二通の通知を出す代わりに、一つの候補としてまとめられます。これが重複通知の抑制です。

ところが、翌週そのIssueに認証情報が追記されたとします。投稿のURLは同じでも、公開された内容と影響は変わりました。前回の「確認済み」をそのまま使わず、新しい内容を確認します。いったん検索結果から消えて再び現れた場合も、削除、非公開化、検索結果の変動、検索失敗を見分ける必要があります。

[GitHub indicator watch](../../../../engineering/source-protection/public-exposure-observation-and-triage/implementations/github-indicator-watch/README.md)は、少数の検索語で公開コード・Issue・Pull Requestを探し、同じ投稿への通知を減らす実装例です。**同じ投稿の内容変更や再出現を自動で再通知しません。** この例を使うなら、誰が変更を見直すかを別に決めてください。判断理由や見直す期限も、この実装の外で管理します。

## 検索結果が0件だったとき

「新しい候補が0件」でも、以前見つけた候補が未対応かもしれません。検索が途中で止まったなら、残りの範囲に候補があるかどうかも分かりません。

まず、今回検索できた範囲、取得できなかった部分、最後に検索が正常に終わった時刻を確認します。取得できた候補は調査に使えますが、それだけで検索全体を完了扱いにはしません。検索が正常に終わっても、検索対象外の公開場所や過去のコピーまでは調べられていません。

何を試して確認するかは[controlの診断項目](README.md#failure-checks)、実装が返す正常・一部取得・失敗の違いは[実装README](../../../../engineering/source-protection/public-exposure-observation-and-triage/implementations/github-indicator-watch/README.md)を参照してください。

## 既に共有したと分かっている場合

開発者が「認証情報をGitHubの非公開リポジトリへ誤ってpushした」と連絡してきたとします。これは公開検索で新たな候補を探す場面ではありません。検索結果を待たず、[SOURCE-002](../psb-source-002-secret-publication-boundary/README.md)から認証情報の所有者と[GOV-004](../../governance-operations/psb-gov-004-credential-exposure-containment/README.md)の対応担当へ渡します。通常時の認証情報管理は[SOURCE-004](../psb-source-004-source-access-credential-lifecycle/README.md)の対象です。

非公開なら閲覧できる人は限られるかもしれません。それは優先度を考える材料の一つです。ただし、非公開という理由だけで優先度は決められません。認証情報がまだ有効か、何を操作できるか、誰が履歴を読めたか、ほかにコピーがあるかを確認して、対応の急ぎ方を決めます。[GitHubの漏えい対応ガイダンス](https://docs.github.com/en/code-security/how-tos/manage-security-alerts/manage-secret-scanning-alerts/resolving-alerts)も、非公開リポジトリに記録された認証情報を対応対象にしています。

## 講義から得た見方

今回の三つの問いから、次の判断を残します。検索で一致したこと、漏えいかどうか、対応の優先度は別です。公開状態と内容を確かめ、第三者が何をできるかを考え、所有者が判断します。同じ投稿への通知をまとめても、後から変わった内容まで確認済みにはなりません。既に認証情報を共有したと分かっているなら、公開検索を待たずに対応へ渡します。
