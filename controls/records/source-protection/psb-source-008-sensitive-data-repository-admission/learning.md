# DBダンプをGitに入れてよいか

[対応するcontrol](README.md)

開発者が障害を再現するため、顧客情報を含むDBダンプを非公開リポジトリへ置こうとします。チームにはアクセス制限があり、secret scannerも通りました。ところが、このダンプには認証情報はなくても実際の利用者の記録があります。コミット後に削除しても、履歴を取得した人のcloneやバックアップに残り得ます。

ここで先に聞くのは「どの検査器ならダンプを見つけられるか」ではありません。「この実データを誰が所有し、何のためにGitへ置く必要があるか」です。非公開という設定だけでは、履歴へ広がってよいという許可になりません。

検査ではファイル名、拡張子、大きさ、形式、内容を手掛かりにできます。ただし、名前の変更、圧縮、暗号化、分割、Git LFSの参照で読み取れないことがあります。「疑わしいものが見つからない」と「対象をすべて読めた」は違います。読めない場合は、許可済みとして先へ進めず、データの所有者の判断へ戻します。

ローカルhookは早く知らせますが、省略できます。サーバー側の受入拒否は共有refへの追加を止められても、送信先へデータが届く前の阻止とは異なります。CIのmerge拒否なら、送信は既に終わっています。どの時点より前に止める必要があるかを、データの性質に合わせて決めます。

## この場面の判断例

この時点では、DBダンプをGitへ追加しません。secret scannerの「検出なし」は、そのスキャナーが対象とする秘密値の検査結果であり、顧客の記録を履歴へ入れる許可ではないためです。まず再現に必要なデータの形を確かめ、架空の小さなテストデータで代えられるか考えます。実データが必要なら、データの所有者に用途、許される保管先、閲覧者を確認します。判断が出る前や内容を調べられない間は、受入を保留します。

すでに共有先へ送ったと分かった場合は「受入前に止めた」とは言えません。コミットと履歴、共有先、閲覧・複製できた範囲を調べ、元データを通知やログに転載せず、データの所有者と組織の情報漏えい対応担当へ渡します。過去のコピーがすべて消えたとは、最新コミットからファイルを削除しただけでは判断できません。

必要な状態は[controlの診断項目](README.md#診断で確認する項目異常時テスト)、旧資料の採否は[Sources](../../../../sources/README.md#ref-sensitive-data-repository-001)を参照してください。この例は実環境での受入拒否や、顧客データの取扱いを確認した結果ではありません。
