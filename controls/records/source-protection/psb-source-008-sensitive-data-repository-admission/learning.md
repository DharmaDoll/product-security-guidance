# DBダンプをGitに入れてよいか

開発者が障害を再現するため、顧客情報を含むDBダンプを非公開リポジトリへ置こうとします。チームにはアクセス制限があり、secret scannerも通りました。ところが、このダンプには認証情報はなくても実際の利用者の記録があります。コミット後に削除しても、履歴を取得した人のcloneやバックアップに残り得ます。

ここで先に聞くのは「どの検査器ならダンプを見つけられるか」ではありません。「この実データを誰が所有し、何のためにGitへ置く必要があるか」です。再現に必要なのがデータの形だけなら、無害化した小さなテスト用データを作れます。実データが必要なら、取扱い方針に照らして許可された保管先と閲覧者を別に決めます。非公開という設定だけでは、履歴へ広がってよいという許可になりません。

検査ではファイル名、拡張子、大きさ、形式、内容を手掛かりにできます。ただし、名前の変更、圧縮、暗号化、分割、Git LFSの参照で読み取れないことがあります。「疑わしいものが見つからない」と「対象をすべて読めた」は違います。読めない場合は、許可済みとして先へ進めず、データの所有者の判断へ戻します。

ローカルhookは早く知らせますが、省略できます。サーバー側の受入拒否は共有refへの追加を止められても、送信先へデータが届く前の阻止とは異なります。CIのmerge拒否なら、送信は既に終わっています。どの時点より前に止める必要があるかを、データの性質に合わせて決めます。

よくある誤解は「secret scannerが通ったから機密データもない」というものです。scannerの検出対象に顧客情報や独自形式が含まれるとは限りません。次に「拡張子とサイズで弾けば十分」という誤解もあります。これは調査対象を絞る兆候にはなりますが、安全の証明にはなりません。

判断の問いは三つです。実データをこのリポジトリに置く理由と承認者を説明できるか。コミット予定の内容と、共有先へ入る履歴・別の書込み経路を確認したか。検査不能や判断待ちを許可に変えていないか。[コントロール](README.md)の診断項目へ戻り、採用先の経路で確かめます。
