# PSB-SOURCE-008 Sensitive data repository admission

**顧客データなど、Gitへ入れてはいけない情報を受け入れる前に止められるか。**

例えば、調査用のDBダンプを非公開リポジトリへ追加しようとしても、認証情報がなければsecret scannerは何も報告しないかもしれません。いったん受け入れると履歴やコピーへ広がるため、「secretの検出なし」はデータの持込み許可になりません。

## 満たすべきこと

1. **何を入れてよいか決める。** データの所有者と取扱い方針に基づき、禁止する実データ、許可する無害なテストデータ、代わりの保管先を決める（DATA-ADMISSION-1）。
2. **受入前に判断する。** ファイル名・大きさ・形式・内容は手がかりとして使い、読めない内容やGit LFSなどの外部格納物を「機密データなし」と扱わない。コミットする内容と共有先へ入る履歴を確かめ、hookを省略した書込み経路でも必要な受入判断を維持する（DATA-ADMISSION-2〜3）。
3. **不明なら止め、届いたら渡す。** 禁止対象、判断待ち、検査不能、許可済みを分け、必要な所有者の判断が出るまで受け入れない。検出内容をログや通知に複製せず、既に共有先へ届いたら到達範囲をデータの所有者と組織の情報漏えい対応担当へ渡す（DATA-ADMISSION-4〜5）。

## 診断で確認する項目（異常時テスト）

- DBダンプの拡張子を変える、小さく分ける、アーカイブへ入れるだけで、持込みが許可されていない実データを通していないか。
- 暗号化、破損、サイズ上限、Git LFSなどで読めない内容を「検出なし」としていないか。
- ステージ後に作業ツリーだけ直す、過去コミットの内容を最新コミットで消す、hookを省略してWeb UI・API・botから書く場合も、必要な受入判断が残るか。
- テストデータの許可を別の内容へ使い回したり、所有者の判断待ちを自動許可したりしていないか。
- 検出結果や通知へ実データを転載せず、共有後は履歴・コピー・閲覧できた範囲を担当者へ渡せるか。

これらは設計レビューや診断の項目であり、実際の顧客データを使った結果ではありません。試すときは無害な架空データを使います。

## このコントロールの範囲

対象は組織のソースリポジトリへ追加する、認証情報以外の公開を制限すべき内容です。非公開リポジトリも含めます。認証情報は[SOURCE-002](../psb-source-002-secret-publication-boundary/README.md)、公開後の未知の候補の発見は[SOURCE-003](../psb-source-003-public-source-exposure-triage/README.md)が扱います。既に共有先へ届いたと分かっている場合、公開検索を待たずに対応担当へ渡します。Git以外の持ち出し全般や、組織のデータ分類規程そのものはここでは定めません。

どのデータを止めるかはデータの所有者が決めます。書込み経路と検査を置く場所は[既存の設計](../../../../engineering/source-protection/secret-checks-before-publication/README.md)を参考にできますが、secret用の検出ルールでは実データの判定を代替できません。[教材](learning.md)、５つの特性と参照資料IDを残した[control.yaml](control.yaml)、旧資料の採否を示す[Sources](../../../../sources/README.md#ref-sensitive-data-repository-001)へも辿れます。実装例は選ばず、対象組織のデータ分類と実際の受入拒否は未確認です。
