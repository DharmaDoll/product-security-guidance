# Managed is not currently trusted

[コントロール記録](README.md) · [設計パターン](../../../../engineering/source-protection/managed-developer-endpoint/README.md)

「管理対象の端末です」と「今この資産へのアクセスを許可できます」は、別の判断です。

## 登録は残り、観測が止まった

ある開発者の端末は、導入時に暗号化と監視を有効にし、台帳にも登録されました。
その後、更新の延期が続き、管理基盤との通信も途絶えました。しかしソース管理へのセッションは有効なままです。

ここで外部コードを通常の開発環境で実行し、そのコードが利用者のファイルやセッションへアクセスできたとします。
攻撃者は管理者権限を得なくても、利用者が読めるソースや変更できるリポジトリを狙えます。
登録時の良好な記録は、その処理が動いた時点の状態を説明していません。

## 三つの事実を分ける

- **登録**：誰が管理するどの端末か。対象一覧の事実です。
- **観測**：いつ、何を、どこから確認したか。取得できなかった状態も含みます。
- **アクセス判断**：その観測を受けて、どの資産への操作をいつまで許可するか。資産側で強制する判断です。

MDMに登録済みでも、古い観測を許可条件として使い続ければ、判断は変わりません。
また新規ログインだけを拒否しても、既存セッションや別途発行した認証情報は個別に確認する必要があります。

例えば端末の監視が止まった後、Webの新規ログインだけ拒否しても、昨日開いたソース管理のセッションで書き込みが続けられるなら、その資産では制限が働いていません。端末側の状態表示、認証基盤での判断、ソース管理側で続いている操作を別々に見ます。
端末の状態悪化を監視していても、既存セッションが使えれば、意図したアクセス制限の対象から漏れます。どの資産で継続中の操作を止めるか、セッションの失効・再認証・操作拒否のうち採用先で実際に使える方法を選び、止まった結果まで確認します。

CLI用トークンの状態が分からないなら、アクセス制限は完了として閉じません。認証情報の値を表示せず、種類、発行された主体、使えるリポジトリと操作、どの端末・プロセス・接続元から利用できるか、有効期限、最近の利用を確認します。管理者が失効できるか、失効後にその権限を使う要求が拒否されるかも別に確かめます。利用履歴から悪用の兆候を調べることと、現在の権限を止めることは別の判断です。履歴を取得できない場合も「悪用なし」とは言えません。認証情報とセッションの詳細は[SOURCE-004](../psb-source-004-source-access-credential-lifecycle/README.md)へ渡します。

### 一覧や利用履歴を取得できないとき

既知のトークンを失効しても、一覧の取得に失敗したなら「すべてのトークンを止めた」とは言えません。利用履歴が一部しか取れないなら「悪用はなかった」とも言えません。まず結果を分けます。

- 失効後の拒否まで確認した権限は、止まったと記録する。
- 一覧に出なかった可能性のある権限は、まだ使えるか不明として残す。
- 取得できなかった期間の利用は、調査できていないとして残す。

そのうえで資産の管理者と、ソース管理側で対象利用者やリポジトリの操作を一時的に制限できるか判断します。これは不明なトークンが残る間の被害を狭めるためで、一覧の取得や利用履歴の調査を済ませたことにはなりません。制限できない経路も、担当者と確認期限を付けて未完了のまま引き継ぎます。取得が戻ったら棚卸しと利用履歴の確認、残る権限の拒否確認をやり直します。

## 違う攻撃には違う境界が効く

電源を切った暗号化済み端末を盗み、回復鍵も持たない攻撃者には、ディスクからデータを読む障壁があります。
一方、ログイン済みの利用者として動く悪意あるコードは、利用者が読めるデータを扱えます。
「暗号化済みだから、認証情報の悪用も防げる」とは判断できません。

逆に、外部コードへソース管理の認証情報も対象ファイルも渡していなければ、この例の直接の読み取り経路は成立しません。
それでも隔離環境の迂回や、許可した書き込み先を通じた改変は別途確認します。

## レビューで問うこと

端末の観測が途絶えたとき、誰が気付き、どの権限がどこで止まるでしょうか。
端末がオフラインでも、サーバー側で止められる権限は何でしょうか。
接続が戻らなければ完了を確認できない消去・隔離と、既に実行されたソース変更をどう区別するでしょうか。

具体的な設計は[Managed developer endpoint](../../../../engineering/source-protection/managed-developer-endpoint/README.md)、
権限の停止は[Source credential lifecycle](../../../../engineering/source-protection/source-access-credential-lifecycle/README.md)で検討します。
この教材は[利用者提供資料のリポジトリによる解釈](../../../../sources/README.md#ref-developer-endpoint-baseline-001)です。
攻撃段階1の端末から段階2のソース管理、段階12の調査へ続く例であり、実際の組織への導入を評価したものではありません。

対応する成果物：[コントロール記録](README.md) · [Managed developer endpoint](../../../../engineering/source-protection/managed-developer-endpoint/README.md)

## 講義から得た見方

この三つの問いから、端末が管理対象かどうかだけでなく、**現在の観測が資産側の継続中の権限まで届くか**を端末管理の判断に含める、という見方を得ました。新規ログインの拒否、既存セッションの停止、CLI用トークンの失効は別々に確認します。

また、権限を今止められたかと、過去に悪用されたかは別の問いです。認証情報の一覧が欠けていれば現在の利用可能性を閉じられず、利用履歴が欠けていれば過去の悪用がなかったとも言えません。どちらかの調査が進んでも、もう一方を完了扱いにしないことが、この講義で得た判断基準です。これは本PJでの学習から導いた見方であり、実環境で確認した結果ではありません。

## 講義と振り返りの記録

- 2026-10-06、三つの問いで区切りました。新規ログインだけを止めた場合、CLI用トークンの状態が不明な場合、認証情報の一覧と利用履歴が一部しか取れない場合をたどりました。前者二つでは利用者の指摘を反映し、最後は難しい判断を「既知の拒否・残る権限・過去の利用」に分けて説明しました。上のシナリオと判断基準へ反映済みです。理解度の評価、実トークンの棚卸し・失効・監査、製品固有の期限や挙動の確認は行っていません。
