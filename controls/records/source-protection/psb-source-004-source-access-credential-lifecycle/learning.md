# Source credential lifecycle — 学習ノート

[コントロール記録](README.md) · [設計pattern](../../../../engineering/source-protection/source-access-credential-lifecycle/README.md)

## この文書の目的

認証情報を「漏らしてはいけない文字列」とだけ捉えず、ソース管理基盤上の権限として設計するための教材です。
特定のGitHub画面や、一種類のトークンだけを覚えることは目的ではありません。

## 1. 具体的なシナリオ

開発者がIDE拡張機能からソースリポジトリを読むために、長期間有効なPATを設定しています。
PATはシェルの設定ファイルから環境変数へ書き出され、IDE本体とすべての子プロセスが読み取れます。
利用対象は一つのリポジトリですが、トークンは複数のリポジトリへの書き込み権限を持ち、有効期限もありません。

悪意ある拡張機能や侵害されたツールが環境変数を読み取ると、攻撃は次のように進みます。

```text
悪意ある拡張機能
      |
      v
親プロセスからPATを取得
      |
      v
ソース管理基盤が有効な認証情報として受理
      |
      +--> 関係のないリポジトリを読む
      +--> ソースコードやワークフローを変更する
      +--> 開発者が気付くまで再利用する
```

問題はPATという名称ではありません。一つの認証情報が、必要以上のリソース、操作、期間、利用プロセスへ
権限を広げていることです。

### 攻撃連鎖の前後を見る

この例は、サプライチェーン攻撃の一段階だけで終わりません。

```text
端末／拡張機能／AIツールの侵害
  -> 認証情報を取得
  -> ソース管理基盤上の権限を悪用
  -> ソース、ワークフロー、依存関係を変更
  -> 正常に見えるビルドとリリースへ進む
```

この学習ノートが詳しく扱うのは、認証情報からソース管理上の権限へ変わる箇所です。
端末の侵害防止、AIツールの実行時認可、変更内容のレビュー、後続のビルドと署名は別の境界です。
この切り分けは[`REF-PORTFOLIO-001`](../../../../sources/README.md#ref-portfolio-001)と
[サプライチェーン攻撃段階](../../../../docs/ANALYSIS_LENSES.md#サプライチェーン攻撃の12段階)を使って確認しています。

## 2. 用語

### ID

誰または何が要求を行っているかを表す主体です。利用者アカウント、アプリケーション、ワークロードなどがあります。

### 認証情報

ソース管理基盤がIDや権限を確認するために受け入れる、トークン、鍵、許可情報などです。

### 権限

実際に許可される操作の範囲です。認証情報を保護する目的は、文字列そのものではなく、権限を奪われないようにすることです。

### セッション

認証情報や認証処理から派生し、一定期間要求を許可する状態です。元の認証情報だけを削除しても、
既存のセッションが引き続き使える場合があります。

### 失効

古い権限を無効にし、同じ要求が拒否される状態へ変えることです。新しい認証情報の発行やファイルの削除とは異なります。

## 3. 脅威モデル

想定する相手は、フィッシングを行う攻撃者、情報窃取型マルウェア、悪意ある拡張機能、
侵害された開発ツール、元の役割を失った利用者です。ソース管理基盤の制御面全体が支配されているとは仮定しません。

守る対象は、ソースコード、ワークフロー、リリース設定、リポジトリのメタデータと、それらを変更できる権限です。

主な信頼境界は次の三つです。

1. 端末上の保管場所から、利用するプロセスへの受け渡し。
2. 利用プロセスから、ソース管理基盤への認証と認可。
3. 人事、IdP、インシデントの事象から、サービス提供側での失効までの連携。

## 4. セキュリティ不変条件

> 一つの認証情報が盗まれても、攻撃者は元の主体、目的、リソース、操作、期間を越えた権限を取得できず、
> ライフサイクル上の事象が発生した後は、古い認証情報から得た権限を再利用できない。

認証情報の盗難を完全に防げるとは仮定せず、盗難時の被害範囲と攻撃者が居座れる期間を制限します。

## 5. 直感と実際の判定を合わせる

### 「きめ細かな権限を設定できるPATなら安全」ではない

Fine-grained PATでも、すべてのリポジトリ、書き込み権限、長い有効期限を選べば、広い権限になります。
名称ではなく、実際に付与された権限を確認します。

### 「キーチェーンに入れたから安全」ではない

保護された保管場所は不正な複製を減らします。しかし正規のプロセスが不要なリソースへアクセスできるなら、過剰権限は残ります。

### 「短命なトークンなら失効処理は不要」ではない

有効期間を短くすると攻撃者が居座れる期間を抑えられますが、インシデント中に有効なセッションや
再発行経路が残る可能性があります。

### 「新しいトークンへ切り替えたから完了」ではない

古い認証情報と関連セッションが拒否されるまでは、新しいトークンを発行しても権限を一つ追加しただけです。

## 6. 設計判断

主体ごとに必要なアクセスを分けます。

| 主体 | 優先する考え方 |
|---|---|
| 開発者 | 組織が承認した対話型認証、保護された保管場所、必要なリソースだけへの権限 |
| 自動処理 | 利用者の認証情報を再利用せず、リソースと処理内容を限定した短命なワークロードID |
| 緊急時の運用担当者 | 通常権限を恒久的に広げず、範囲を狭くして監視する期限付き経路 |
| AIエージェント／ツール | 認証情報の範囲に加え、ツールと引数に対する実行時認可を別の境界で強制 |

## 7. コントロール境界

このコントロールに合格しても、端末上のマルウェア、悪意あるソース変更、危険なツール呼び出し、
ソース管理基盤の制御面の侵害まで安全になるわけではありません。逆に、端末を十分に強化していても、
サービス提供側に所有者不明の認証情報が残っていれば、このコントロールは成立しません。

## 8. 実務で確認する問い

- 現在利用可能なソース管理上の権限を、認証情報の値を見ずに一覧化できるか。
- 自動処理が利用者個人のアカウントへ依存していないか。
- 認証情報の保管場所と、実際に受け取るプロセスを区別できるか。
- 退職や端末紛失の発生から、関連セッションの拒否まで追跡できるか。
- 監査事象を、現在有効な権限と取り違えていないか。
