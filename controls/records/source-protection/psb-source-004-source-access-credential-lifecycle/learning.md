# 学習：一つのリポジトリを読むトークンが、ほかも書き換えられるとき

[対応するcontrol](README.md) · [設計パターン](../../../../engineering/source-protection/source-access-credential-lifecycle/README.md)

## シナリオ

開発者がIDE拡張からリポジトリAを読むため、個人用アクセストークン（PAT）を渡しています。必要な操作はAの読み取りだけですが、トークンにはリポジトリBを含む複数の場所への書き込み権限があり、期限も設けていません。

拡張が侵害され、トークンをコピーされた疑いが出ました。担当者は新しいトークンを作ってIDEの設定を変え、「古いものはもう使っていない」と考えました。しかし、ソース管理サービス側では古いトークンがまだ有効です。この場面は判断を学ぶための架空の例です。

## 何が問題か

トークンは単なる文字列ではなく、ソース管理サービスが操作を許すための認証情報です。IDEでAだけを開く設定でも、サービス側でBへの書き込みを認めていれば、値を得た別の処理はその権限を試せます。守る対象はAだけでなく、Bのソースと、そこに書き込める権限です。

新しいトークンが使えても、古いトークンが拒否される証拠にはなりません。関連するセッション、別に登録された鍵やアプリの権限も、同じ操作で一度に止まるとは限りません。端末から値を消したことと、サービス側の権限を止めたことを分けます。

## この場面の判断例

まず、現在使える認証情報の種類と所有者を一覧にします。それぞれについて、どの処理・場所から、どのリポジトリに、何を、いつまで許すか、誰が止められるかを確認します。この例で必要なのはAの読み取りです。Bへの書き込みや不要な長期利用を残す理由はありません。自動処理があるなら、開発者個人のトークンを使い回さず、処理専用の権限を決めます。

次に、古いトークンをサービス側で失効させ、関連するセッションや別の鍵・アプリの権限が残るかを確認します。止めたい操作が古い権限では拒否されることを、対象を絞った安全な方法で確かめます。確認できない経路は「失効済み」とせず、担当者と次の確認を残します。利用履歴では、時刻、接続元、使われた権限と操作をどこまで調べられるか確認します。ログに見えない操作を「なかった」とは判断しません。

トークンが実際に漏れた疑いと、第三者による利用の調査は[GOV-004](../../governance-operations/psb-gov-004-credential-exposure-containment/README.md)へ渡します。値を端末の`.env`や広い環境変数に残さず、必要な処理だけへ渡す方法は[SOURCE-007](../psb-source-007-developer-local-credential-storage/README.md)の主題です。ここでは**ソース管理サービスが認める権限と、その失効**を判断します。権限を止めても、すでに持ち出されたソースまで回収できるわけではありません。

必要な状態は[control](README.md)、方式の選択は[設計パターン](../../../../engineering/source-protection/source-access-credential-lifecycle/README.md)、製品固有の失効対象は[GitHub実装例](../../../../engineering/source-protection/source-access-credential-lifecycle/implementations/github/README.md)を参照してください。資料の版と採否は[Sources](../../../../sources/README.md#spec-github-security-guidance)にあります。この例は実環境の権限や失効を確認した結果ではありません。
