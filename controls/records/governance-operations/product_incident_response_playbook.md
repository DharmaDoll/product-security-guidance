# プロダクトインシデント対応プレイブック（社内Wiki標準版）

本プレイブックは、自社プロダクト（SaaS・API・オンプレミス・SDK等）に関するセキュリティインシデントおよび重大な脆弱性が発覚した際、部門を横断して迅速かつ一貫した対応を行うための標準手順書です。

> **運用上の大原則**
> 有事の際は「完璧な調査完了」を待ってから動くと手遅れになります。**事実確認（技術調査）と並行して、初動封じ込め・法務判断・顧客連絡の準備を進める**ことを基本とします。

## 1. 全体フローと重要度判定基準（SLA）

### 1.1 対応ライフサイクル（6フェーズ）

1. **検知・受付と記録**：窓口受信・アラート検知と同時に機密チケットを起票し、タイムライン記録を開始
2. **トリアージと重要度判定**：再現確認・影響範囲特定を行い、重要度（S1〜S4）と緊急体制の発令を判断
3. **封じ込めと証拠保全**：被害拡大の遮断（機能停止・鍵失効）と、ログ・スナップショットの保全
4. **原因調査と恒久対策・パッチ提供**：非公開環境での修正開発・検証と、必要に応じた暫定回避策の策定
5. **当局報告・顧客通知・対外公表**：法定期限・契約SLAに則った報告と、顧客・市場への正確な情報開示
6. **事後振り返り（RCA）とナレッジ還元**：Blame-freeなポストモーテム実施と、本プレイブック・検知ルールの更新

### 1.2 重要度判定基準と目標SLA

「恒久対策（パッチ）目安」は初動計画の参考値です。正式なパッチ提供期限は、別途定める社内の修正期限基準を参照してください（社内Wikiの参照先は確定後に追記）。PSIRTと製品担当は、[脆弱性の優先度と対応期限の判断手順](psb-gov-003-vulnerability-priority-decision/README.md)に沿って、案件ごとの期限と根拠をチケットに記録します。

| 重要度 | 判定基準の例 | 一次回答 / 初動 | 緊急対策室 | 恒久対策（パッチ）目安 |
| :--- | :--- | :--- | :--- | :--- |
| **S1（Critical）** | 実環境での悪用確認、顧客データの漏洩・改ざん、全顧客影響の停止・認証回避 | **1時間以内**に初動開始<br>（外部報告は24h以内返信） | **即時招集**（経営・法務・広報含む） | **24〜72時間以内**（または即時ワークアラウンド提供） |
| **S2（High）** | 重大な脆弱性（CVSS High相当以上）で悪用リスクが高い、一部テナントへの影響 | **4時間以内**にトリアージ<br>（外部報告は24h以内返信） | 必要に応じて招集 | **7日以内** |
| **S3（Medium）** | 悪用に特定条件が必要、影響範囲が限定的な脆弱性 | **1営業日以内** | 不要（通常チケット連携） | **30日以内**（通常スプリント） |
| **S4（Low）** | 情報漏洩リスクが極めて低い軽微な不備、ベストプラクティス改善 | **3営業日以内** | 不要 | 次期計画リリースにて対応 |

## 2. 役割分担（RACIマトリクス）

緊急時の判断空白を防ぐため、**「A（Accountable：最終承認・説明責任）」は原則として各タスク1ロールに固定**します。

* **R（Responsible）**：実作業を行う担当
* **A（Accountable）**：最終判断・承認・説明責任を持つ担当
* **C（Consulted）**：判断や作業にあたって意見を求める協議先
* **I（Informed）**：決定事項や進捗を共有する報告先

以下の1〜9は、役割分担を参照するためのタスク番号です。各タスクをいつ開始するかは、第3節の手順と判断条件に従います。

| 主要タスク（番号・作業内容） | PSIRT / セキュリティ | 開発チーム | SRE / インフラ | CS / サポート | 法務・広報 | 経営層 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **1. 受付・トリアージ**（一次受領・影響調査開始） | **A / R** | **C** | **C** | **I** | - | - |
| **2. 重要度判定**（Severity決定・緊急体制発令） | **A / R** | **C** | **C** | **C** | **I** | **I** (S1/S2) |
| **3. 封じ込め・遮断**（機能停止・鍵失効・隔離） | **C** | **C** | **A / R** | **I** | - | **I** (S1時) |
| **4. 証拠保全・原因調査**（ログ解析・再現検証） | **C** | **R** | **A / R** | - | **I** | - |
| **5. 修正パッチ開発・検証**（コード修正・テスト） | **C** | **A / R** | **C** | - | - | - |
| **6. リリース判断**（緊急デプロイ・配信承認） | **C** | **R** | **R** | **I** | - | **A** (S1時) / **C** |
| **7. 当局報告・法的判断**（個人情報保護・CRA等） | **C** | **I** | **I** | - | **A / R** | **C** |
| **8. 顧客通知・対外公表**（アドバイザリ・PR対応） | **R** | **C** | - | **R** | **A** | **C** |
| **9. 事後振り返り（RCA）**（再発防止・ナレッジ更新） | **A / R** | **R** | **R** | **C** | **I** | **I** |

> **運用の注記**
> * S3/S4の通常案件では、法務・広報・経営層への共有（I/C）は週次・月次サマリに集約し、開発スピードを優先します。
> * メンバーの異動に耐えられるよう、RACI表は「個人名」ではなく「ロール（役割）」で管理します。

## 3. フェーズ別アクション手順

以下のPhase 1〜6は、1.1「対応ライフサイクル」の6フェーズに対応します。

### Phase 1〜4：検知・封じ込め・修正（技術対応）

1. **受付・トリアージ（PSIRT / 開発）**
   * [ ] 非公開のインシデント管理チケットを起票し、情報共有範囲を制限（TLP:AMBER/RED相当）する
   * [ ] 外部報告の場合、テンプレートを用いて24時間以内に一次受領確認を返信する
   * [ ] 対象プロダクト・影響バージョン・悪用有無を確認し、S1〜S4を決定する
2. **封じ込め・証拠保全（SRE / 開発）**
   * [ ] サーバーやコンテナを停止・再起動する**前に**、監査ログ（CloudTrail/Audit Logs等）とメモリ・ディスクのスナップショットを保全する
   * [ ] 漏洩の疑いがあるAPIキー・トークン・証明書を即時失効・ローテーションする
   * [ ] 必要に応じて該当機能の無効化、WAFルール適用、ネットワーク隔離を実施する
3. **原因調査・修正開発（開発 / QA）**
   * [ ] パブリックリポジトリへ修正内容が露出しないよう、非公開のセキュリティブランチ／プライベートフォークでパッチを開発する
   * [ ] 同種の脆弱性・実装ミスが他のプロダクトやマイクロサービスに存在しないか横断検索する
   * [ ] リグレッションテストおよび再発防止テスト（自動テスト化）を実施する

### Phase 5：当局報告・顧客通知・対外公表（第2節のタスク7・8）

#### 5.1 判断を止めないための「即断トリガー基準」

技術調査の全容が確定していなくても、以下の条件に**1つでも該当した時点で即座に対外対応アクションへ移行**します。

| 領域 | 即断トリガー（Yesなら即アクション） | 意識すべき期限・確認事項 |
| :--- | :--- | :--- |
| **7. 当局報告・法的判断** | ・個人データ／機微情報の漏洩・滅失・毀損の恐れがある<br>・顧客の事業継続に重大な支障（SLA違反・広域停止）が出ている<br>・製品脆弱性の**実環境での悪用（Active Exploitation）**が確認された | 法務を招集し、5.3に沿って法令・契約ごとに起算時刻、期限、通知先を確定する。 |
| **8. 顧客通知・対外公表** | ・顧客側での対処（パッチ適用、設定変更、鍵更新）が必要<br>・特定顧客のテナント／データへの不正アクセス痕跡がある<br>・外部研究者やSNS等により近く公知になり得る | ・修正完成前でも**暫定回避策（ワークアラウンド）**を先行通知するか<br>・影響顧客への個別通知か、全体公開（アドバイザリ等）かの切り分け |

#### 5.2 タイムライン別アクション（発覚〜72時間・公表）

| 経過時間目安 | 担当ロール | 実施する判断とアクション |
| :--- | :--- | :--- |
| **発覚〜2時間** | PSIRT・開発 | **【初報共有】** 法務・広報・CSへ「①確定事実」「②調査中の事項」「③顧客が今取るべき行動」の3点のみを速報する（テンプレートA使用）。 |
| **2〜6時間** | 法務・CS | **【報告判定・対象抽出】** 法務が当局報告・契約通知の要否を一次判定（A）する。並行してCSが契約DB等から影響顧客リストと適用規制を抽出する。 |
| **6〜12時間** | PSIRT・広報・CS | **【ドラフト並列作成】** 技術調査と並行し、「当局向け速報」「顧客向け先行通知（調査中）」「社内FAQ」をテンプレートから同時作成する。 |
| **〜24時間** | 法務・経営層 | **【緊急決裁・早期警告】** 事前指定の緊急承認者が決裁し、該当制度の指定窓口へ期限内に提出する。JPCERT/CC等への対応調整依頼は別に記録する。 |
| **24〜48時間** | CS・広報 | **【先行通知・FAQ展開】** 影響顧客へ確定情報と暫定回避策を通知する。同時に営業・サポート窓口へ社内FAQを配布し、問い合わせ回答を一本化する。 |
| **修正リリース時〜事後** | PSIRT・法務・広報 | **【公表・確報】** 修正内容と顧客の対処を公表する。調査が続く場合も、制度ごとの期限までに判明事項を報告し、続報・確報の担当と期限を追跡する。 |

#### 5.3 どの法律・契約に基づいて、誰にいつ知らせるか

例えば、EU向けSDKの脆弱性が悪用され、顧客環境の個人データにも影響した疑いがある場合、PSIRTは製品・版・流通国・悪用を知った時刻を、CSは顧客の所在地・契約・データ処理上の役割を法務へ渡す。製品の悪用と個人データ侵害は別々に評価し、それぞれの認知時刻を記録する。表5.2は社内の作業目安であり、通知義務が先に生じた場合はその時点で動く。

| 適用を調べる条件 | 法務と担当部門が確認する報告・通知（参照確認日 2026-11-22） |
| :--- | :--- |
| 日本の個人データの漏えい・滅失・毀損またはそのおそれ | **個人情報保護法26条**。民間事業者は要配慮個人情報、財産的被害のおそれ、不正目的のおそれ、本人が1,000人を超える事態の各類型を確認する。該当時は知った時から速やかに速報（概ね3〜5日）、確報は知った日から30日以内、不正目的の類型は60日以内。個人情報保護委員会または権限委任先への報告と、状況に応じた速やかな本人通知を追跡する。受託案件は委託元への通知による報告義務免除の条件も確認する。[個人情報保護委員会](https://www.ppc.go.jp/personalinfo/legal/leakAction/) |
| GDPRの適用を受ける個人データ侵害 | **GDPR 33・34条**。処理者は認知後、不当な遅滞なく管理者へ通知する。管理者は本人の権利・自由にリスクを生じる可能性が低い場合を除き、管轄監督機関へ不当な遅滞なく、可能なら認知から72時間以内に通知する。高リスクの場合は本人への通知と例外も判定する。未判明情報は段階的に補い、判断根拠を保存する。[規則本文](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng/) |
| EU市場に提供したデジタル要素を含む製品の悪用済み脆弱性、または製品のセキュリティに影響する重大インシデント | **EU CRA 14条**（報告義務は2026年9月11日適用開始）。製造者に該当するか、対象製品・事象かを判定する。該当時は認知から不当な遅滞なく、最長24時間で早期警告、原則72時間で詳細通知。単一報告プラットフォームを通じ指定CSIRT・ENISAに同時通知する。最終報告は悪用済み脆弱性では是正・緩和措置が利用可能になってから14日以内、重大インシデントでは原則として詳細通知から1か月以内。影響を受ける利用者への情報提供も追跡する。[規則14・16・71条](https://eur-lex.europa.eu/eli/reg/2024/2847/oj/eng) |
| EUで対象サービスを提供する、または対象事業者に供給する | **NIS2**は対象主体・サービス・重大性を加盟国の国内法で判定する。指令23条の基本線は認知から24時間以内の早期警告、72時間以内のインシデント通知。金融では**DORA**の対象金融機関による重大ICTインシデント報告と、ICT供給者が契約で負う顧客支援を確認する。[NIS2第23条](https://eur-lex.europa.eu/eli/dir/2022/2555/oj/eng)・[DORA第19・30条](https://eur-lex.europa.eu/eli/reg/2022/2554/oj/eng) |
| 日本で個人番号、通信の秘密、規制業種のサービスまたは身体安全に影響する製品を扱う | 特定個人情報は**番号法**、電気通信事業の通信の秘密漏えい・重大事故は**電気通信事業法28条**を確認する。金融・決済は銀行法、資金決済法等の業態別監督報告、医療機器は医薬品医療機器等法、消費生活用製品の重大製品事故は消費生活用製品安全法を候補に、製品責任者と所管窓口を特定する。[番号法](https://laws.e-gov.go.jp/law/425AC0000000027)・[電気通信事業法](https://laws.e-gov.go.jp/law/359AC0000000086)・[e-Gov法令検索](https://laws.e-gov.go.jp/) |
| 海外居住者、規制業種または上場法人への影響 | 居住州・国ごとの漏えい通知法（米国各州、英国UK GDPR等）を確認する。米国医療ではHIPAA対象主体・業務委託先と保護対象医療情報、米国証券開示では届出法人の区分と重要性を確認する。Form 8-K Item 1.05の対象なら原則として重要性決定後4営業日以内。日本上場企業も適時開示の要否をIR部門へ引き継ぐ。[HHSの漏えい通知規則](https://www.hhs.gov/hipaa/for-professionals/breach-notification/index.html)・[SECの開示説明](https://www.sec.gov/newsroom/speeches-statements/gerding-cybersecurity-disclosure-20231214) |

**調査・封じ込め中にも法務判断が必要になる。** 顧客環境へのアクセスは契約・調査権限を確認し、国外の調査会社へログを渡す前に個人データの委託・越境移転条件を確認する。証拠にはアクセス制限と保存期限を設定し、紛争・捜査に伴う保全指示があれば廃棄を止める。身代金の要求があれば支払判断の前に制裁・外為規制を法務に照会する。

**案件記録**には、対象国・業種・契約ごとに「根拠条項／義務を負う法人と役割／該当・非該当・調査中と理由／起算事実・日時・時間帯／通知先・期限／担当・代理／提出時刻・受領証／次回更新」を残す。DPA・SLA、販売代理店やクラウド事業者との契約、カードブランド規則、サイバー保険の事故通知も独立した行で追跡する。事業国・顧客業種・製品区分が増える際は、法務がその地域の一次資料と窓口を追加する。

---

### Phase 6：事後振り返り（RCA）とナレッジ還元

S1/S2のインシデント（および重要度の高いS3）の収束後、**1〜2週間以内**に振り返りミーティングを実施します。

* [ ] **Blame-free（個人を責めない）** の前提で、発覚から収束までのタイムラインと意思決定のボトルネックを整理する
* [ ] 技術的な再発防止策（SAST/SCAルール追加、ガードレール強化、テスト追加）をプロダクトのバックログに登録する
* [ ] 本プレイブックの記述やテンプレートに不足・迷いがあった箇所をその場で修正し、組織ナレッジを最新化する

## 4. すぐ使えるテンプレート集

### テンプレートA：社内エスカレーション初報（Slack / Teams用）

```text
【インシデント初報 / 重要度：[S1 / S2]】
■ 発生日時・検知経路：[YYYY/MM/DD HH:MM / 外部報告・監視アラート等]
■ 対象プロダクト：[プロダクト名 / バージョン / 環境]

1. 確定している事実
- [例：〇〇機能のAPIにおいて、認証バイパスの脆弱性が再現確認された]

2. 現在調査中の事項（仮説含む）
- [例：過去30日間の悪用痕跡（ログ）の有無を確認中。〇時頃に中間報告予定]

3. 顧客・他部門へのお願い（今すぐ取るべき行動）
- SRE：[例：〇〇機能のレート制限強化／ログ保全]
- 法務・広報：[例：〇〇時までに緊急チャネルへ参加ください（報告要否判定のため）]
- CS：[例：本件に関する問い合わせが来た場合は #inc-xxxx へ連携してください]

■ 緊急対応チャネル：[#inc-YYYYMMDD-xxx]
■ チケットURL：[URL]
```

### テンプレートB：外部報告者向け 一次受領確認メール（24時間以内目標）

```text
件名：[Case #XXXX] 脆弱性情報のご報告ありがとうございます / Acknowledgement of Vulnerability Report

[報告者様のお名前 / Handle] 様
```
