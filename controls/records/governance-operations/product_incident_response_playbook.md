# プロダクトインシデント対応プレイブック（社内Wiki標準版）

本プレイブックは、自社プロダクト（SaaS・API・オンプレミス・SDK等）に関するセキュリティインシデントおよび重大な脆弱性が発覚した際、部門を横断して迅速かつ一貫した対応を行うための標準手順書です。

> **運用上の大原則**
> 有事の際は「完璧な調査完了」を待ってから動くと手遅れになります。**事実確認（技術調査）と並行して、初動封じ込め・法務判断・顧客連絡の準備を進める**ことを基本とします。

## 1. 全体フローと重要度判定基準（SLA）

### 1.1 対応ライフサイクル（6フェーズ）

1. **検知・受付と記録**：窓口受信・アラート検知と同時に機密チケットを起票し、タイムライン記録を開始
2. **トリアージと重要度判定**：再現確認・影響範囲特定を行い、重要度（S1〜S4）と緊急体制の発令を判断
3. **封じ込めと証拠保全**：被害拡大の遮断（機能停止・鍵失効）と、ログ・スナップショットの保全
4. **原因調査と恒久対策・パッチ提供**：非公開環境での修正開発・検証と、必要に応じた暫定回避策の策定
5. **当局報告・顧客通知・対外公表**：法定期限・契約SLAに則った報告と、顧客・市場への正確な情報開示
6. **事後振り返り（RCA）とナレッジ還元**：Blame-freeなポストモーテム実施と、本プレイブック・検知ルールの更新

### 1.2 重要度判定基準と目標SLA

| 重要度 | 判定基準の例 | 一次回答 / 初動 | 緊急対策室 | 恒久対策（パッチ）目安 |
| :--- | :--- | :--- | :--- | :--- |
| **S1（Critical）** | 実環境での悪用確認、顧客データの漏洩・改ざん、全顧客影響の停止・認証回避 | **1時間以内**に初動開始<br>（外部報告は24h以内返信） | **即時招集**（経営・法務・広報含む） | **24〜72時間以内**（または即時ワークアラウンド提供） |
| **S2（High）** | 重大な脆弱性（CVSS High相当以上）で悪用リスクが高い、一部テナントへの影響 | **4時間以内**にトリアージ<br>（外部報告は24h以内返信） | 必要に応じて招集 | **7日以内** |
| **S3（Medium）** | 悪用に特定条件が必要、影響範囲が限定的な脆弱性 | **1営業日以内** | 不要（通常チケット連携） | **30日以内**（通常スプリント） |
| **S4（Low）** | 情報漏洩リスクが極めて低い軽微な不備、ベストプラクティス改善 | **3営業日以内** | 不要 | 次期計画リリースにて対応 |

## 2. 役割分担（RACIマトリクス）

緊急時の判断空白を防ぐため、**「A（Accountable：最終承認・説明責任）」は原則として各タスク1ロールに固定**します。

* **R（Responsible）**：実作業を行う担当
* **A（Accountable）**：最終判断・承認・説明責任を持つ担当
* **C（Consulted）**：判断や作業にあたって意見を求める協議先
* **I（Informed）**：決定事項や進捗を共有する報告先

| フェーズ / 主要タスク | PSIRT / セキュリティ | 開発チーム | SRE / インフラ | CS / サポート | 法務・広報 | 経営層 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **1. 受付・トリアージ**（一次受領・影響調査開始） | **A / R** | **C** | **C** | **I** | - | - |
| **2. 重要度判定**（Severity決定・緊急体制発令） | **A / R** | **C** | **C** | **C** | **I** | **I** (S1/S2) |
| **3. 封じ込め・遮断**（機能停止・鍵失効・隔離） | **C** | **C** | **A / R** | **I** | - | **I** (S1時) |
| **4. 証拠保全・原因調査**（ログ解析・再現検証） | **C** | **R** | **A / R** | - | **I** | - |
| **5. 修正パッチ開発・検証**（コード修正・テスト） | **C** | **A / R** | **C** | - | - | - |
| **6. リリース判断**（緊急デプロイ・配信承認） | **C** | **R** | **R** | **I** | - | **A** (S1時) / **C** |
| **7. 当局報告・法的判断**（個人情報保護・CRA等） | **C** | **I** | **I** | - | **A / R** | **C** |
| **8. 顧客通知・対外公表**（アドバイザリ・PR対応） | **R** | **C** | - | **R** | **A** | **C** |
| **9. 事後振り返り（RCA）**（再発防止・ナレッジ更新） | **A / R** | **R** | **R** | **C** | **I** | **I** |

> **運用の注記**
> * S3/S4の通常案件では、法務・広報・経営層への共有（I/C）は週次・月次サマリに集約し、開発スピードを優先します。
> * メンバーの異動に耐えられるよう、RACI表は「個人名」ではなく「ロール（役割）」で管理します。

## 3. フェーズ別アクション手順

### Phase 1〜4：検知・封じ込め・修正（技術対応）

1. **受付・トリアージ（PSIRT / 開発）**
   * [ ] 非公開のインシデント管理チケットを起票し、情報共有範囲を制限（TLP:AMBER/RED相当）する
   * [ ] 外部報告の場合、テンプレートを用いて24時間以内に一次受領確認を返信する
   * [ ] 対象プロダクト・影響バージョン・悪用有無を確認し、S1〜S4を決定する
2. **封じ込め・証拠保全（SRE / 開発）**
   * [ ] サーバーやコンテナを停止・再起動する**前に**、監査ログ（CloudTrail/Audit Logs等）とメモリ・ディスクのスナップショットを保全する
   * [ ] 漏洩の疑いがあるAPIキー・トークン・証明書を即時失効・ローテーションする
   * [ ] 必要に応じて該当機能の無効化、WAFルール適用、ネットワーク隔離を実施する
3. **原因調査・修正開発（開発 / QA）**
   * [ ] パブリックリポジトリへ修正内容が露出しないよう、非公開のセキュリティブランチ／プライベートフォークでパッチを開発する
   * [ ] 同種の脆弱性・実装ミスが他のプロダクトやマイクロサービスに存在しないか横断検索する
   * [ ] リグレッションテストおよび再発防止テスト（自動テスト化）を実施する

---

### Phase 5：当局報告・顧客通知・対外公表（手順7・8のブレイクダウン）

#### 5.1 判断を止めないための「即断トリガー基準」

技術調査の全容が確定していなくても、以下の条件に**1つでも該当した時点で即座に対外対応アクションへ移行**します。

| 領域 | 即断トリガー（Yesなら即アクション） | 意識すべき期限・確認事項 |
| :--- | :--- | :--- |
| **7. 当局報告・法的判断** | ・個人データ／機微情報の漏洩・滅失・毀損の恐れがある<br>・顧客の事業継続に重大な支障（SLA違反・広域停止）が出ている<br>・製品脆弱性の**実環境での悪用（Active Exploitation）**が確認された | ・個人情報保護法：速報（おおむね3〜5日以内）／確報（30日等）<br>・海外規制（GDPR・EU CRA等）：早期警告（24h）／通知（72h）<br>・個別契約（NDA・SLA）上のインシデント通知期限 |
| **8. 顧客通知・対外公表** | ・顧客側での対処（パッチ適用、設定変更、鍵更新）が必要<br>・特定顧客のテナント／データへの不正アクセス痕跡がある<br>・外部研究者やSNS等により近く公知になり得る | ・修正完成前でも**暫定回避策（ワークアラウンド）**を先行通知するか<br>・影響顧客への個別通知か、全体公開（アドバイザリ等）かの切り分け |

#### 5.2 タイムライン別アクション（発覚〜72時間・公表）

| 経過時間目安 | 担当ロール | 実施する判断とアクション |
| :--- | :--- | :--- |
| **発覚〜2時間** | PSIRT・開発 | **【初報共有】** 法務・広報・CSへ「①確定事実」「②調査中の事項」「③顧客が今取るべき行動」の3点のみを速報する（テンプレートA使用）。 |
| **2〜6時間** | 法務・CS | **【報告判定・対象抽出】** 法務が当局報告・契約通知の要否を一次判定（A）する。並行してCSが契約DB等から影響顧客リストと適用規制を抽出する。 |
| **6〜12時間** | PSIRT・広報・CS | **【ドラフト並列作成】** 技術調査と並行し、「当局向け速報」「顧客向け先行通知（調査中）」「社内FAQ」をテンプレートから同時作成する。 |
| **〜24時間** | 法務・経営層 | **【緊急決裁・早期警告】** 平時の稟議を通さず、事前指定の緊急承認者（2名以内）で決裁する。24h期限の規制該当時は当局・JPCERT/CC等へ第一報を提出する。 |
| **24〜48時間** | CS・広報 | **【先行通知・FAQ展開】** 影響顧客へ確定情報と暫定回避策を通知する。同時に営業・サポート窓口へ社内FAQを配布し、問い合わせ回答を一本化する。 |
| **修正リリース時〜事後** | PSIRT・法務・広報 | **【公表・確報】** パッチ公開に合わせてセキュリティアドバイザリ（CVE番号・謝辞含む）を公開する。調査完了後、当局へ確報を提出しクローズする。 |

---

### Phase 6：事後振り返り（RCA）とナレッジ還元

S1/S2のインシデント（および重要度の高いS3）の収束後、**1〜2週間以内**に振り返りミーティングを実施します。

* [ ] **Blame-free（個人を責めない）** の前提で、発覚から収束までのタイムラインと意思決定のボトルネックを整理する
* [ ] 技術的な再発防止策（SAST/SCAルール追加、ガードレール強化、テスト追加）をプロダクトのバックログに登録する
* [ ] 本プレイブックの記述やテンプレートに不足・迷いがあった箇所をその場で修正し、組織ナレッジを最新化する

## 4. すぐ使えるテンプレート集

### テンプレートA：社内エスカレーション初報（Slack / Teams用）

```text
【インシデント初報 / 重要度：[S1 / S2]】
■ 発生日時・検知経路：[YYYY/MM/DD HH:MM / 外部報告・監視アラート等]
■ 対象プロダクト：[プロダクト名 / バージョン / 環境]

1. 確定している事実
- [例：〇〇機能のAPIにおいて、認証バイパスの脆弱性が再現確認された]

2. 現在調査中の事項（仮説含む）
- [例：過去30日間の悪用痕跡（ログ）の有無を確認中。〇時頃に中間報告予定]

3. 顧客・他部門へのお願い（今すぐ取るべき行動）
- SRE：[例：〇〇機能のレート制限強化／ログ保全]
- 法務・広報：[例：〇〇時までに緊急チャネルへ参加ください（報告要否判定のため）]
- CS：[例：本件に関する問い合わせが来た場合は #inc-xxxx へ連携してください]

■ 緊急対応チャネル：[#inc-YYYYMMDD-xxx]
■ チケットURL：[URL]
```
