# プロダクトインシデント対応プレイブック（社内Wiki標準版）

本プレイブックは、Kubernetes（k8s）上で稼働し、LLMエージェントとデータベース（DB）を利用するWebアプリケーション（SaaS）、および自社が配布するモバイル・デスクトップアプリに関するセキュリティインシデントおよび重大な脆弱性が発覚した際、部門を横断して迅速かつ一貫した対応を行うための標準手順書です。

> **運用上の大原則**
> 有事の際は「完璧な調査完了」を待ってから動くと手遅れになります。**事実確認（技術調査）と並行して、初動封じ込め・法務判断・顧客連絡の準備を進める**ことを基本とします。

## 1. 全体フローと重要度判定基準（SLA）

### 1.1 対応ライフサイクル（6フェーズ）

1. **検知・受付と記録**：窓口受信・アラート検知と同時に機密チケットを起票し、タイムライン記録を開始
2. **トリアージと重要度判定**：再現確認・影響範囲特定を行い、重要度（S1〜S4）と緊急体制の発令を判断
3. **封じ込めと証拠保全**：被害拡大の遮断（機能停止・鍵失効）と、ログ・スナップショットの保全
4. **原因調査・恒久対策と復旧確認**：回避策・パッチを提供し、対象環境での効果と残る影響を確認
5. **当局報告・顧客通知・対外公表**：法定期限・契約SLAに則った報告と、顧客・市場への正確な情報開示
6. **事後振り返り（RCA）とナレッジ還元**：Blame-freeなポストモーテム実施と、本プレイブック・検知ルールの更新

### 1.2 重要度判定基準と目標SLA

「恒久対策（パッチ）目安」は初動計画の参考値です。正式なパッチ提供期限は、別途定める社内の修正期限基準を参照してください（社内Wikiの参照先は確定後に追記）。PSIRTと製品担当は、[脆弱性の優先度と対応期限の判断手順](psb-gov-003-vulnerability-priority-decision/README.md)に沿って、案件ごとの期限と根拠をチケットに記録します。

| 重要度 | 判定基準の例 | 一次回答 / 初動 | 緊急対策室 | 恒久対策（パッチ）目安 |
| :--- | :--- | :--- | :--- | :--- |
| **S1（Critical）** | 実環境での悪用確認、顧客データの漏洩・改ざん、全顧客影響の停止・認証回避 | **1時間以内**に初動開始<br>（外部報告は24h以内返信） | **即時招集**（経営・法務・広報含む） | **24〜72時間以内**（または即時ワークアラウンド提供） |
| **S2（High）** | 重大な脆弱性（CVSS High相当以上）で悪用リスクが高い、一部テナントへの影響 | **4時間以内**にトリアージ<br>（外部報告は24h以内返信） | 必要に応じて招集 | **7日以内** |
| **S3（Medium）** | 悪用に特定条件が必要、影響範囲が限定的な脆弱性 | **1営業日以内** | 不要（通常チケット連携） | **30日以内**（通常スプリント） |
| **S4（Low）** | 情報漏洩リスクが極めて低い軽微な不備、ベストプラクティス改善 | **3営業日以内** | 不要 | 次期計画リリースにて対応 |

## 2. 役割分担（RACIマトリクス）

緊急時の判断空白を防ぐため、**「A（Accountable：最終承認・説明責任）」は原則として各タスク1ロールに固定**します。

* **R（Responsible）**：実作業を行う担当
* **A（Accountable）**：最終判断・承認・説明責任を持つ担当
* **C（Consulted）**：判断や作業にあたって意見を求める協議先
* **I（Informed）**：決定事項や進捗を共有する報告先

以下の1〜9は、役割分担を参照するためのタスク番号です。各タスクをいつ開始するかは、第3節の手順と判断条件に従います。

| 主要タスク（番号・作業内容） | PSIRT / セキュリティ | 開発チーム | SRE / インフラ | CS / サポート | 法務・広報 | 経営層 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **1. 受付・トリアージ**（一次受領・影響調査開始） | **A / R** | **C** | **C** | **I** | - | - |
| **2. 重要度判定**（Severity決定・緊急体制発令） | **A / R** | **C** | **C** | **C** | **I** | **I** (S1/S2) |
| **3. 封じ込め・遮断**（機能停止・鍵失効・隔離） | **C** | **C** | **A / R** | **I** | - | **I** (S1時) |
| **4. 証拠保全・原因調査**（ログ解析・再現検証） | **C** | **R** | **A / R** | - | **I** | - |
| **5. 修正パッチ開発・検証**（コード修正・テスト） | **C** | **A / R** | **C** | - | - | - |
| **6. リリース判断**（緊急デプロイ・配信承認） | **C** | **R**（S2〜S4は開発のリリース責任者が **A**） | **R** | **I** | - | **A**（S1の担当役員） |
| **7. 当局報告・法的判断**（個人情報保護・CRA等） | **C** | **I** | **I** | - | **A / R** | **C** |
| **8. 顧客通知・対外公表**（アドバイザリ・PR対応） | **R** | **C** | - | **R** | **A** | **C** |
| **9. 事後振り返り（RCA）**（再発防止・ナレッジ更新） | **A / R** | **R** | **R** | **C** | **I** | **I** |

> **運用の注記**
> * S3/S4の通常共有は週次・月次サマリに集約します。5.1に該当した場合は重要度を問わず直ちに担当者を招集します。
> * メンバーの異動に耐えられるよう、RACI表は「個人名」ではなく「ロール（役割）」で管理します。

## 3. フェーズ別アクション手順

以下のPhase 1〜6は、1.1「対応ライフサイクル」の6フェーズに対応します。

### Phase 1〜4：検知・封じ込め・修正・復旧確認（技術対応）

1. **受付・トリアージ（PSIRT / 開発）**
   * [ ] 非公開のインシデント管理チケットを起票し、情報共有範囲を制限（TLP:AMBER/RED相当）する
   * [ ] 外部報告の場合、テンプレートを用いて24時間以内に一次受領確認を返信する
   * [ ] PSIRTは対象製品・版・悪用の証拠を確認し、1.2の複数基準に該当したら最も高い重要度を採る。影響が未確定なら、通報と観測事実から疑う被害に応じて暫定指定し、根拠・未確認事項・調査担当・次回判定時刻をチケットに残す。
   * [ ] **例：単一テナントから「他社の氏名が見えた」と通報があり、該当時間帯のログが欠けている。** 顧客データ漏えいの疑いとして暫定S1で招集し、被害の有無は「調査中」と記録する。SREは拡大防止、法務は5.3の通知判断を開始する。追加証拠の入手時または次回判定時刻にPSIRTが見直し、変更理由を残す。
2. **封じ込め・証拠保全（SRE / 開発）**
   * [ ] 原則として停止・再起動前に監査ログと揮発性の証拠を保全する。**保全を待つ間も漏えい・改ざんが続く場合は、SRE当番が先行遮断を決定**し、開発が並行して取得可能な証拠を保全する。決定者・時刻・理由・取得できなかった証拠と調査への影響をチケットに残す。
   * [ ] 漏洩の疑いがあるAPIキー・トークン・証明書を即時失効・ローテーションする
   * [ ] 必要に応じて該当機能の無効化、WAFルール適用、ネットワーク隔離を実施する
   * [ ] **LLMエージェントによる想定外のDB操作が疑われる場合**、SREと開発は該当するツール呼び出しや実行権限を一時停止する。利用可能なリクエストID・実行時刻を手掛かりに、アプリ、エージェント、DBの記録を照合し、読み取り・更新の範囲と対象テナントをPSIRTに渡す。照合できない期間・操作も記録する。
   * [ ] SREは対象環境で遮断の効果を確認する（例：失効した鍵での要求が拒否される）。確認できない環境は「未確認」として指揮者へ報告する。
3. **原因調査・修正開発（開発 / QA）**
   * [ ] **調査を依頼するとき**：PSIRTは「いつまでに、何を判断したいか」を調査担当へ伝える（例：対象機能の再開可否、個別通知が必要なテナント）。対象ログ・期間、回答期限、報告の形式と共有先を合意し、チケットに残す。新たな影響顧客が判明した場合や封じ込めの効果に疑義が生じた場合は、次の定例を待たず指揮者へ速報する。[JPCERT/CCの依頼者向けチェックリスト](https://github.com/JPCERTCC/ir_report_checklist/blob/main/checklist_for_customer.md)
   * [ ] **調査結果を渡すとき**：開発・SREまたは調査会社は、依頼時の問いごとに、結論、根拠となるログと対象期間、証拠不足で判断できない事項を示す。正式報告書が必要な場合はサンプルから案件に必要な項目を選ぶ。[JPCERT/CCの作成者向けチェックリスト](https://github.com/JPCERTCC/ir_report_checklist/blob/main/checklist_for_reporter.md)・[調査報告書サンプル](https://github.com/JPCERTCC/ir_report_checklist/blob/main/incident_forensic_report_template_ja.md)
   * [ ] パブリックリポジトリへ修正内容が露出しないよう、非公開のセキュリティブランチ／プライベートフォークでパッチを開発する
   * [ ] **影響する製品・版を絞る。** 開発は同じ部品を使う製品と、同種の実装ミスがあり得る別のサービスを調べる。例えばモバイルアプリで別テナントの情報が表示されたら、該当ビルドのほか、同じAPIを使うWeb・デスクトップアプリにも影響するかを調べる。製品・版ごとに「影響あり／影響なし（根拠）／調査中」を記録し、PSIRTへ修正・通知の対象候補を渡す。[FIRST PSIRT Services Framework v1.1 機能3.3.5](https://www.first.org/standards/frameworks/psirts/FIRST_PSIRT_Services_Framework_v1.1_ja.pdf#page=62)
   * [ ] リグレッションテストおよび再発防止テスト（自動テスト化）を実施する
4. **配信・復旧確認（開発 / SRE / PSIRT）**
   * [ ] **報告を受けた指揮者が聞くこと**：「どの期間・どのテナントまで確認できたか。ログが欠けた時間帯について、顧客にどこまで説明できるか」。[依頼者向けチェックリストの「調査結果のレビュー」](https://github.com/JPCERTCC/ir_report_checklist/blob/main/checklist_for_customer.md)に沿って確認し、機能を再開できる根拠はSREへ、過去の影響について説明できる範囲と未確認事項は法務・CSへ渡す。追加調査が必要なら担当と次回報告時刻を決める。
   * [ ] 第2節タスク6の承認者が、対象版・検証結果・異常時の再遮断策を確認して配信を決裁する。
   * [ ] **SaaS・API**：SREは影響したワークロードで稼働中のPodが修正版に切り替わったこと、問題の操作の拒否、通常の顧客操作の成功を確認する。監視対象と観測期間を決め、再発や顧客影響があれば再遮断して指揮者へ戻す。
   * [ ] **モバイル・デスクトップアプリ**：開発はOS・配布経路ごとに、利用者が修正版を取得できることと、更新後のビルド番号を確認する。CSは影響版、更新方法、更新までの回避策を案内する。PSIRTは端末への適用を確認できた範囲と、旧版・適用状況不明の範囲を記録し、追跡担当と次回確認日を決める。
   * [ ] **配布経路によって更新可能な時刻が異なる場合**、PSIRTは開発と公開状況を照合し、CSへ経路ごとの回避策・更新可否・次回案内時刻を渡す。[FIRST PSIRT Services Framework v1.1 サービスエリア4](https://www.first.org/standards/frameworks/psirts/FIRST_PSIRT_Services_Framework_v1.1_ja.pdf#page=64)
   * [ ] **収束判断**：PSIRTの指揮者は復旧の確認範囲と証拠、残るリスクをチケットに記録する。自社の緊急対応を終了する際は、未復旧・未確認案件と未完の通知を、期限付きで担当者が引き受けたことを確認する。

### Phase 5：当局報告・顧客通知・対外公表（第2節のタスク7・8）

#### 5.1 判断を止めないための「即断トリガー基準」

**1つでも該当したら、PSIRTは判明した事実と認知時刻をチケットに記録し、該当する行の担当者を直ちに招集します。** 複数行に当てはまる場合は並行して着手します。法務は5.3で報告要否・通知先・期限を確定します。

| 何が起きたか（例） | 誰が今すぐ何をするか | 期限・判断の目安 |
| :--- | :--- | :--- |
| **個人データの漏えい・滅失・毀損の疑い**。例：顧客から「別テナントの氏名が表示された」と通報 | PSIRTは対象データ・確認時刻を法務へ渡す。法務は本人・委託元・監督機関への通知要否を判定する。 | [日本の個人情報保護法](#legal-appi)の報告対象なら、知った時から**速やかに速報（概ね3〜5日）**、確報は原則30日以内（不正目的の類型は60日以内）。[GDPR](#legal-gdpr)では処理者は管理者へ**不当な遅滞なく**通知。管理者に当局通知義務がある場合は認知後、不当な遅滞なく、可能なら**72時間以内**。 |
| **製品脆弱性の実環境での悪用を確認**。例：EU向けデスクトップアプリについて顧客から悪用を示すログを受領 | PSIRTは製品・版・悪用を知った時刻を法務へ渡す。法務はCRAの対象製品か、自社が製造者かを確認する。 | [CRA](#legal-eu-cra)の報告対象なら認知後、不当な遅滞なく、**最長24時間で早期警告、原則72時間で詳細通知**。 |
| **顧客の業務が停止**。例：広域API障害で顧客が受注できない | SREは停止時刻・影響範囲を共有し、CSと法務は対象顧客の契約で初報期限と指定窓口を確認する。 | [契約の起算条件](#notification-case-record)で期限を計算する。[5.2の標準時刻](#notification-action-timeline)より早ければ通知を前倒しする。 |
| **顧客側で対処が必要、または特定テナントに不正アクセスの痕跡**。例：対象顧客による鍵更新が必要 | PSIRTは対象・対処手順を示し、CSは[テンプレートC](#template-c-customer-early-notification)で個別通知を準備する。 | 修正前でも被害を抑えられる場合は、法務・広報の承認を経て[回避策と次回更新時刻を先行通知](#template-c-customer-early-notification)する。 |
| **近く公知になる見込み**。例：研究者から公開予定日の連絡を受領 | PSIRTは公開予定時刻を確認し、法務・広報・CSは、影響顧客への個別通知と一般向け告知の順序を決める。 | 公開予定と顧客の対処に必要な時間を基に、[告知の承認時刻](#notification-action-timeline)を決める。 |

#### 5.2 タイムライン別アクション（発覚〜72時間・公表）

この表は、**5.1の即断トリガーに該当し、外部通知・報告の検討を開始した案件**について、関係者の招集、判断材料の収集、文案作成を止めないための社内作業目安である。すべてのインシデントに一律適用するSLAや法定期限ではない。期限は、(1) 法令・規制、(2) 契約、(3) 被害抑制や公表予定など事案固有の緊急性、(4) 本表の目安、の順に確認し、より早い期限があれば前倒しする。外部通知が不要と判断された軽微な事案、顧客影響のない事案、誤検知では、本表の全工程を実施する必要はない。各時間は当番体制と承認経路を机上演習で検証し、組織の実態に合わせて見直す。

| 経過時間目安 | 担当ロール | 実施する判断とアクション |
| :--- | :--- | :--- |
| **発覚〜2時間** | PSIRT・開発 | **【初報共有】** 法務・広報・CSへ「①確定事実」「②調査中の事項」「③顧客が今取るべき行動」の3点のみを速報する（テンプレートA使用）。 |
| **2〜6時間** | 法務・CS | **【報告判定・対象抽出】** 法務が当局報告・契約通知の要否を一次判定（A）する。並行してCSが契約DB等から影響顧客リストと適用規制を抽出する。 |
| **6〜12時間** | PSIRT・広報・CS | **【ドラフト並列作成】** 技術調査と並行し、「当局向け速報」「顧客向け先行通知（調査中）」「社内FAQ」をテンプレートから同時作成する。 |
| **〜24時間** | 法務・経営層 | **【緊急決裁・早期警告】** 事前指定の緊急承認者が決裁し、該当制度の指定窓口へ期限内に提出する。JPCERT/CC等への対応調整依頼は別に記録する。 |
| **24〜48時間** | CS・広報 | **【先行通知・FAQ展開】** 影響顧客へ確定情報と暫定回避策を通知する。同時に営業・サポート窓口へ社内FAQを配布し、問い合わせ回答を一本化する。 |
| **修正リリース時〜事後** | PSIRT・法務・広報 | **【公表・確報】** 修正内容と顧客の対処を公表する。調査が続く場合も、制度ごとの期限までに判明事項を報告し、続報・確報の担当と期限を追跡する。 |

<a id="notification-requirements"></a>

#### 5.3 どの法律・契約に基づいて、誰にいつ知らせるか

例えば、EU向けデスクトップアプリの脆弱性が悪用され、顧客環境の個人データにも影響した疑いがある場合、PSIRTは製品・版・流通国・悪用を知った時刻を、CSは顧客の所在地・契約・データ処理上の役割を法務へ渡す。製品の悪用と個人データ侵害は別々に評価し、それぞれの認知時刻を記録する。表5.2は社内の作業目安であり、通知義務が先に生じた場合はその時点で動く。

参照確認日：2026-11-22

<a id="legal-appi"></a>

##### 日本の個人データの漏えい・滅失・毀損、またはそのおそれ（個人情報保護法26条）

- **対象**　民間事業者は、要配慮個人情報、財産的被害のおそれ、不正目的のおそれ、本人が1,000人を超える事態のいずれかに該当するかを確認する。
- **速報**　報告対象の事態を知った時から速やかに（概ね3〜5日）、個人情報保護委員会または権限委任先へ報告する。
- **確報**　知った日から**30日以内**。不正目的の類型は**60日以内**。
- **本人通知**　状況に応じて速やかに本人へ通知する。
- **受託案件**　委託元への通知により報告義務が免除される条件を確認する。[個人情報保護委員会](https://www.ppc.go.jp/personalinfo/legal/leakAction/)

<a id="legal-gdpr"></a>

##### GDPRの適用を受ける個人データ侵害（33・34条）

- **自社が処理者**　侵害を認知した後、不当な遅滞なく管理者へ通知する。
- **自社が管理者**　本人の権利・自由にリスクを生じる可能性が低い場合を除き、管轄監督機関へ不当な遅滞なく、可能なら**認知から72時間以内**に通知する。
- **本人通知**　高リスクの場合は、本人への通知要否と例外を判定する。
- **続報・記録**　未判明の情報は段階的に補い、判断根拠を保存する。[GDPR本文](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng/)

<a id="legal-eu-cra"></a>

##### EU市場に提供した製品での悪用・重大インシデント（EU CRA 14条）

- **対象**　自社が製造者で、デジタル要素を含む対象製品に悪用済み脆弱性があるか、製品のセキュリティに影響する重大インシデントがあるかを確認する。報告義務は2026年9月11日から適用。
- **早期警告・詳細通知**　認知後、不当な遅滞なく、早期警告は**最長24時間**、詳細通知は**原則72時間以内**。単一報告プラットフォームを通じ、指定CSIRTとENISAへ同時に通知する。
- **悪用済み脆弱性の最終報告**　是正・緩和措置が利用可能になってから**14日以内**。
- **重大インシデントの最終報告**　原則として詳細通知から**1か月以内**。
- **利用者への連絡**　影響を受ける利用者への情報提供も追跡する。[CRA第14・16・71条](https://eur-lex.europa.eu/eli/reg/2024/2847/oj/eng)

##### EUで対象サービスを提供する場合・対象事業者に供給する場合

- **NIS2**　対象主体・サービス・事象の重大性を加盟国の国内法で判定する。指令の基本線は、認知から**24時間以内**に早期警告、**72時間以内**にインシデント通知。[NIS2第23条](https://eur-lex.europa.eu/eli/dir/2022/2555/oj/eng)
- **DORA**　金融機関は重大ICTインシデントの報告義務を、ICT供給者は契約上の顧客支援義務を確認する。[DORA第19・30条](https://eur-lex.europa.eu/eli/reg/2022/2554/oj/eng)

##### 日本の規制業種・製品に影響する場合

製品責任者とともに、該当する法令と所管窓口を特定する。

- **特定個人情報**　個人番号を含む場合は番号法を確認する。[番号法](https://laws.e-gov.go.jp/law/425AC0000000027)
- **通信**　通信の秘密の漏えい・重大事故は電気通信事業法28条を確認する。[電気通信事業法](https://laws.e-gov.go.jp/law/359AC0000000086)
- **金融・決済**　銀行法、資金決済法等に基づく業態別の監督報告を確認する。
- **製品安全**　医療機器は医薬品医療機器等法、消費生活用製品の重大製品事故は消費生活用製品安全法を確認する。[e-Gov法令検索](https://laws.e-gov.go.jp/)

##### 海外居住者・米国の医療分野・上場法人に影響する場合

- **海外居住者**　本人の居住州・国に適用される漏えい通知法を確認する（米国各州法、英国UK GDPR等）。
- **米国の医療情報**　HIPAAの対象主体・業務委託先に該当するか、保護対象医療情報が含まれるかを確認する。[HHSの漏えい通知規則](https://www.hhs.gov/hipaa/for-professionals/breach-notification/index.html)
- **米国の証券開示**　届出法人の区分と事象の重要性を確認する。Form 8-K Item 1.05の対象なら、原則として**重要性決定後4営業日以内**に届け出る。[SECの開示説明](https://www.sec.gov/newsroom/speeches-statements/gerding-cybersecurity-disclosure-20231214)
- **日本の上場企業**　適時開示の要否をIR部門へ引き継ぐ。

**調査・封じ込め中にも法務判断が必要になる。** 顧客環境へのアクセスは契約・調査権限を確認し、国外の調査会社へログを渡す前に個人データの委託・越境移転条件を確認する。証拠にはアクセス制限と保存期限を設定し、紛争・捜査に伴う保全指示があれば廃棄を止める。身代金の要求があれば支払判断の前に制裁・外為規制を法務に照会する。

<a id="notification-case-record"></a>

**案件記録**には、対象国・業種・契約ごとに「根拠条項／義務を負う法人と役割／該当・非該当・調査中と理由／起算事実・日時・時間帯／通知先・期限／担当・代理／提出時刻・受領証／次回更新」を残す。DPA・SLA、販売代理店やクラウド事業者との契約、カードブランド規則、サイバー保険の事故通知も独立した行で追跡する。事業国・顧客業種・製品区分が増える際は、法務がその地域の一次資料と窓口を追加する。

### Phase 6：事後振り返り（RCA）とナレッジ還元

S1/S2のインシデント（および重要度の高いS3）の収束後、**1〜2週間以内**に振り返りミーティングを実施します。

* [ ] **Blame-free（個人を責めない）** の前提で、発覚から収束までのタイムラインと意思決定のボトルネックを整理する
* [ ] 技術的な再発防止策（SAST/SCAルール追加、ガードレール強化、テスト追加）をプロダクトのバックログに登録する
* [ ] 本プレイブックの記述やテンプレートに不足・迷いがあった箇所をその場で修正し、組織ナレッジを最新化する

**平時の点検・演習（PSIRT責任者）**

- 当番交代・組織変更時は第0節の呼出先と代理権限を確認する。四半期ごとに当番用アカウントで連絡網の閲覧、代理へのテスト呼出し、機密チケットへのアクセスを確認し、実施日を第0節に記録する。
- 次回の机上演習では、夜間の他テナント情報表示とログ欠落を想定する。当番が代理を呼び、暫定重要度、先行遮断、通知期限、復旧に必要な証拠を判断できたかを記録する。
- **脆弱性報告を受けてから顧客に対策が届くまでを点検する。** PSIRT責任者は外部報告を扱った案件を1件選び、受領返信、影響版の判断、修正の検証結果、顧客への通知記録を順にたどる。引き継ぎを確認できない箇所は、次の演習で担当者同士が試す。対象案件がなければ模擬報告で手順を試し、演習結果として記録する。[FIRST PSIRT Maturity Document 成熟度レベル1](https://www.first.org/standards/frameworks/psirts/FIRST_PSIRT_Maturity_Document_ja.pdf#page=3)
- 実事案と演習で見つけた不備は、改善チケットに担当・期限・再確認方法を記入する。PSIRT責任者は修正後に該当手順を再確認し、結果と次回演習日を記録する。
