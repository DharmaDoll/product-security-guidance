# 攻撃の通知はあるのに、何が起きたか分からない

## 公開アプリから内部へ

注文を受け付ける公開アプリに、脆弱性を狙ったリクエストが届きました。入口のWAFには攻撃らしい通信の記録があります。しかし、その記録だけではアプリが処理したのか、入口で止めたのか、別の入口を使われたのか分かりません。担当者が調べ始めた時点でアプリは再起動しており、実行中のログも消えていました。

GOV-011が必要なのはこのためです。事故が起きてから記録を有効にしても、過去の操作は取り戻せません。まず「このアプリが侵害されたら何を調べたいか」を考え、その判断に必要な記録を残します。

ここでいう監査ログは、誰がどの対象へ何をしたかを追う記録です。それだけで十分とは限りません。通信の記録は接続先を、実行環境の記録はプロセスなどの行動を、アプリの記録は業務上の操作を説明します。それぞれ分かることが違います。

| 調べたいこと | 記録から確かめること | それだけでは分からないこと |
|---|---|---|
| 攻撃がアプリへ届いたか | 入口の処理結果とアプリ側の受付。利用可能ならrequestの識別子を照合する | HTTP 200でも攻撃成功とは限らず、500でも処理の途中に何も起きなかったとは限らない |
| アプリで何をされたか | 対象の実行環境、操作やプロセス、ファイル変更、外向き通信 | シェルが起動しないデータ窃取や、記録対象外の操作もある |
| 内部へ広がったか | 送信元・宛先、接続の成否、移動先の認証・認可、実際の操作 | 接続が成功しても認証や操作まで成功したとは限らない |

たとえば内部APIの記録に、アプリのサービス用IDによる大量のデータ取得が残っていたとします。ネットワーク上は許可した相手への通信でも、操作の内容や量が通常と異なる可能性があります。通信制限があることを理由に調査を終えず、そのIDの用途、対象データ、実行元、通常の処理と照合します。

時刻が近いというだけで、入口の通信と内部操作を同じ攻撃と結び付けてはいけません。同じIPを複数の処理が共有することもあります。識別情報が足りなければ「関連する可能性あり、未確定」とし、追加の調査材料を探します。記録が示す主体は認証に使われたIDであり、実際に操作した人物とは限りません。

## 0件と、調べられなかった状態

検索結果が0件でも、収集が止まっていた、閲覧権限がない、保存期間が切れていた、移動先が対象外だったなら、不正操作がなかったとは判断できません。調べられた範囲と調べられない範囲を分け、後者は調査担当へ残します。

このため、イベントの内容とは別に、取得元ごとの最終収集時刻、配送の遅れ、エラー、対象一覧を確認します。静かなサービスで新しいイベントがないことと、収集障害を区別する方法も必要です。保存先が正常でも、アプリ側で記録が無効なら必要な事実は残りません。

攻撃者がアプリの権限を得た場合に、その権限で過去の調査記録まで削除できないようにします。ただし、別の場所へ転送すればすべて解決するわけではありません。取得前に記録を止められる可能性、転送停止、保存先の管理権限の侵害は残ります。どの境界まで守れるかを設計時に説明します。

## 開発者のtokenが悪用された場合も同じ

ソース変更から不正なリリースが作られた場面では、認証の記録、コミット、CI実行、公開した成果物、配備先を照合します。すべてが一つの監査ログに入っているとは限りません。成果物を識別するdigestやCI実行IDなどを使い、つながらない部分を未確認として残します。

調査のためでもtokenの値そのものを集める必要はありません。参照できる識別子や権限情報を使い、機微な本文や認証ヘッダーを通知へ載せないようにします。調査記録を新たな漏えい元にしないことも、このControlの一部です。

## 判断の振り返り

- WAFには攻撃記録があり、内部APIのログは収集停止中でした。「内部への影響なし」としてよいでしょうか。**いいえ。入口の観測と内部の未確認を分けます。**
- アプリが再起動しても記録は別の場所に残っています。それで十分でしょうか。**必要な期間と対象を、権限のある担当者が実際に検索し、操作の関係をたどれるかまで確かめます。**
