# PSB-GOV-012 Detection and response readiness

**止めたい攻撃の兆候を見つけ、対応できる人が判断を始められるか。**

## なぜ必要か

公開アプリから内部管理先への不審な操作を記録できても、検知条件がない、通知先が古い、誤検知に埋もれる場合は対応が始まりません。一度動いたルールも、ログの形式やサービス構成が変われば効かなくなることがあります。

## 満たすべきこと

1. **検知したい行動と限界を決める。** 攻撃の場面、対象、必要な入力、正常操作との違い、拾えない行動を示す。入口の攻撃と侵入後の行動を分ける（DETECTION-1）。
2. **検知を変更・検証できるようにする。** 条件、担当者、版、変更理由を管理し、検知すべき例・似た正常例・入力不足で確認する。配備対象と有効な版を確かめ、問題時に戻せるようにする（DETECTION-2・3）。
3. **障害と抑制による見逃しを扱う。** 監視・通知の停止、処理遅延、対象漏れを把握する。例外の対象・理由・期限を決め、重複通知をまとめても新しい被害対象を消さない（DETECTION-4）。
4. **判断できる人へ渡す。** 対象、時刻、理由、証拠の参照先、未確認範囲を伝え、受領・担当決定まで確認する。不在時の引き継ぎ先と初動の目標を決める（DETECTION-5）。
5. **処置の権限と効果を確かめる。** インシデントとして対応を始める条件と、誰が隔離・失効などを判断し実行するかを定め、対応先から結果と未完了事項を受け取る。重大度ラベルだけで破壊的な操作を行わない（DETECTION-6）。
6. **運用結果を検知へ戻す。** 誤検知や判明した見逃し、データ・環境の変更から検知を見直す。ルールを停止・廃止するときは失う範囲と代替を残す（DETECTION-7）。

## 診断で確認する項目（異常時テスト）

- 安全な試験行動を正しい対象で検知できるか。似ている正常な保守作業を根拠なく侵害確定にしないか。
- 必要な項目や入口の通知が欠けても、別の重要な兆候まで捨てていないか。入力不足を「異常なし」にしないか。
- 配備先のルール版が古い場合、レビュー済みという理由だけで反映済みにしないか。
- 通知先の停止や担当者不在で処理が止まったことを把握できるか。送信成功だけで対応開始にしないか。
- 例外の期限が切れても抑制が残らないか。同じ攻撃者による新しい対象への操作を重複として消さないか。
- 誤った対象の通知だけで停止・削除されないか。事前承認した緊急対応を、都度の承認待ちで実行不能にしていないか。
- 演習で見逃した行動をルール改善へ戻せるか。改善後も正常例を再確認し、廃止による空白を隠さないか。

診断項目としての完成と、実ルール・担当者・処置の検証済みは別です。

## フレームワークとの関係

NIST SP 800-61 Rev.3のDE.CM（継続監視と調整）、DE.AE-06（担当者への情報提供）、DE.AE-08（インシデント判断）へ部分的に関係します。[参照記録](../../../../sources/README.md#ref-security-operations-lifecycle-001)と[framework mapping](../../../../mappings/frameworks.yaml)に特性と限界を残しています。ルールの記述には[Sigmaの資料](../../../../sources/README.md#ref-detection-rule-description-001)も使いますが、Sigma形式やSIEM導入は必須にしません。ATT&CKの番号を付けたことは検知能力の証明ではありません。

## このコントロールの範囲

製品・開発基盤の検知を作り、効く状態に保ち、初動へ渡す共通条件です。記録の準備は[GOV-011](../psb-gov-011-security-event-evidence/README.md)、コンテナ固有のセンサー・ルールは[CONTAINER-004](../../container-cloud-iac-security/psb-container-004-runtime-threat-detection/README.md)が扱います。スキャナー結果の[GOV-009](../psb-gov-009-scanner-evidence-trust-boundary/README.md)、人から届く脆弱性報告の[GOV-006](../psb-gov-006-vulnerability-report-intake/README.md)とは入口が異なります。

[教材](learning.md)で検知後の判断を読み、[Detection Engineeringの設計](../../../../engineering/detection-engineering-lifecycle.md)で検証・配備・改善を選びます。隔離・復旧は[既存の対応設計](../../../../engineering/security-signal-to-response.md#intrusion-containment)へ渡します。このControlだけで封じ込めや復旧全体の完了を保証しません。[特性と根拠](control.yaml)も参照してください。
