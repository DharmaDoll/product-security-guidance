# 検知したのに、被害が広がったのはなぜか

## 通知を出すことと、対応が始まること

公開アプリの脆弱性が悪用され、アプリから内部管理APIへの不審な操作が始まりました。監視は通知を出しましたが、通知先は以前の担当者のままです。誰も処置を判断しない間に、攻撃者が別のサービスへ足場を広げました。

この場面で必要なのはルールを増やすことだけではありません。通知がどの対象を指すか、何が疑わしいか、誰が確認し、誰の権限で何を止められるかがつながっている必要があります。

SOCは検知と調査を担っても、アプリの停止や管理権限の変更を直接実行できるとは限りません。初動担当は根拠と未確認範囲をまとめ、基盤担当やサービス責任者と処置を判断します。事前に承認した緊急対応の条件があれば、その範囲で動けるようにします。すべての対応を新しい承認待ちにする必要はありません。

## 攻撃の段階ごとに、判断を分ける

| 見えたこと | その時点の判断 | 次に確かめること |
|---|---|---|
| 入口で攻撃らしいリクエストを検知 | 攻撃の試行を観測した | 拒否した範囲、アプリ側の処理、別経路の有無 |
| アプリが想定外の処理を実行 | 侵入後の操作の疑いがある | 対象・用途・変更予定と照合し、記録を保全して対応判断へ進める |
| 内部APIへの接続・認証が成功 | 内部へのアクセスを観測した | 使われた権限、許された操作、実際の処理、他の移動先 |
| 管理設定の不正な変更を確認 | 被害が別の管理対象へ広がった | 侵入先と移動先の隔離・権限停止、残された鍵や処理を調べる |

必ずこの順番で通知が出るとは限りません。入口の記録がなくても、内部管理APIで不正な鍵の追加が見つかれば調査を始めます。複数の兆候を合わせると判断しやすくなりますが、すべてそろうまで重要な単独検知を止めてはいけません。

## Detection Engineeringは、効く状態を保つ仕事

Detection Engineeringは、検知したい攻撃を選び、必要なデータと条件を設計し、検証・配備し、運用結果から改善する仕事です。ルールを書いて保存した時点では終わりません。

「公開アプリによる想定外の内部管理操作」を検知するなら、まず正常な処理で管理APIを使うのかを確認します。正当な保守でも似た操作が起こるためです。実行主体や許可された用途を照合し、保守時間内という理由だけで全操作を除外しないようにします。

次に、検知すべき安全な例と似た正常例を比較します。ログの重要な項目が欠けた場合も確認します。検索式だけの試験は条件の確認には役立ちますが、実際の取り込み、通知先、担当者の受領までは確かめません。どこまで試したかを区別します。

配備後、誤検知が多いからと広い除外を入れると、本当に拾いたい操作まで見えなくなることがあります。除外には対象・理由・期限を置き、重要な検知例を再確認します。同じ送信元の通知をまとめる場合も、新しい被害対象や新しい操作は残します。

サービスの構成やログ形式が変わったら、条件が今も成立するか見直します。検知が0件になったことは成功とは限りません。入力が来ていない、必要な項目名が変わった、古い版が動いている可能性も調べます。

## 封じ込めと復旧へ渡す

被害拡大が続いている場合、全容が分かるまで対応を待つ必要はありません。対象、根拠、使える権限、通常業務への影響を踏まえ、記録の保全と隔離・失効を並行します。通知の重大度だけで、関係のないサービスまで一律に停止する設計は避けます。

パッチを適用して入口を閉じても、盗まれた認証情報、追加された鍵、横展開先の不正な処理は残るかもしれません。復旧では入口の修正と残存するアクセス経路の除去を別に確認します。サービスが正常応答しても、調べられない環境が残れば、その範囲まで復旧済みとはしません。

開発者tokenから不正リリースが作られた場合も、担当者への引き渡しは同じです。ソース変更のレビューだけで終えず、tokenの失効、公開先、実際の配備先を調べます。署名の検証成功は、承認された変更だったことや、悪用された権限がもう使えないことの証明ではありません。

## 判断の振り返り

- 入口の攻撃通知はありませんが、内部で不正な管理操作を検知しました。入口の通知を待つべきでしょうか。**待ちません。今ある根拠から調査と封じ込めの判断を始めます。**
- 誤検知を減らす変更後、通知が0件になりました。改善できたでしょうか。**重要な試験行動が今も検知され、入力と配送が正常かを確かめないと判断できません。**
- パッチ適用後は正常に動いています。対応を閉じてよいでしょうか。**侵入後に残された権限や移動先まで処置し、その効果を確認する必要があります。**
