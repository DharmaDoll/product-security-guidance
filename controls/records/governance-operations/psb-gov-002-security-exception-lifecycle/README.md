# PSB-GOV-002 Security exception lifecycle

**一時的な例外は、承認された対象と期限だけに効き、期限後は元の拒否に戻るか。**

## なぜ必要か

例えば、特定の依存パッケージの導入を急ぐため待機期間を一度だけ免除しても、その承認が別のパッケージや将来の版にも使えたら、もとの検査が形だけになります。例外を認めても、検査が見つけた問題自体は消しません。

## 満たすべきこと

1. **対象と理由を限定する。** どのcontrolのどの失敗に対し、どの対象・環境をいつまで例外扱いするかを明記する。理由、受け入れるリスク、代替策、是正作業を残し、申請者だけで承認を完結させない（EXCEPTION-1〜4）。
2. **使う時点で有効か確かめる。** 例外を使う側が、同じ対象の承認、期限、取消状態を確認する。台帳の欠落・改変・取得失敗を「有効」と扱わず、期限切れや確認不能なら元の拒否を維持する（EXCEPTION-5・7〜8）。
3. **記録で別の漏えいを起こさない。** 申請・承認・監査には必要な参照と判断だけを残し、認証情報や本番データを貼らない（EXCEPTION-6）。

## 診断で確認する項目（異常時テスト）

- 別の製品、成果物、環境、失敗項目へ同じ例外を渡しても、元の拒否が解除されないか。
- 申請者の自己承認や、承認後に対象・期限を広げる変更を防げるか。
- 期限切れ・取消・台帳の一部取得・時刻の評価不能で、元の拒否に戻るか。
- 例外を使った後も、元の検査結果や是正期限が残るか。修正済み・復旧完了と誤表示されないか。
- 申請や監査の記録に秘密値や本番データを複製していないか。

これらは確認項目であり、実際の承認システムや検査を試した結果ではありません。

## フレームワークとの関係

- NIST SSDF 1.1 **PW.1.2**を部分的に支えます。承認された例外の理由、受け入れるリスク、代替策、是正作業を記録する点が対応します。PW.1.2はこのControlの期限や承認者の分離を指定していません。また、このControlだけで全要件の管理や未使用例外の定期見直しはできません。

対応する特性と限界は[マッピング](../../../../mappings/frameworks.yaml)に記録しています。実際の承認・強制や準拠を示すものではありません。

## このコントロールの範囲

ここで共通にするのは、例外の対象・承認・期限・失効の扱いです。そもそも例外を認めてよいリスクかは、元のcontrolの担当者が判断します。例えば依存の待機は[DEPS-001](../../dependency-security/psb-deps-001-dependency-release-cooldown/README.md)、脆弱性の対応優先度は[GOV-003](../psb-gov-003-vulnerability-priority-decision/README.md)、稼働中の旧成果物の置換は[GOV-005](../psb-gov-005-deployed-artifact-recovery/README.md)が扱います。例外を承認しても、これらの失敗が合格になったり、復旧が完了したりはしません。

例外をどの検査へ接続するかは[consumer mapping](../../../../mappings/exception-consumers.yaml)、台帳と検査をどう結ぶかは[engineering](../../../../engineering/governance-operations/security-exception-decision-boundary/README.md)を参照してください。[教材](learning.md)、8つの特性と参照資料IDを残した[control.yaml](control.yaml)、資料の採否を示す[Sources](../../../../sources/README.md#ref-security-exception-lifecycle-001)へも辿れます。旧YAML verifierは移植しておらず、実環境での強制も未確認です。
