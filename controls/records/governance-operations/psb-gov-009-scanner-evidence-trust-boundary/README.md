# PSB-GOV-009: Scanner evidence trust boundary

**「指摘なし」という検査結果は、信頼できるツールで、必要な対象を最後まで調べた結果か。**

## なぜ必要か

たとえば、スキャナーが途中で止まって空の結果を返したのに、CIが「問題なし」と受け取れば、未検査の変更が通ります。スキャナーの結果は、ツール・検出データ・設定・対象範囲・実行状態と一緒に判断します。

## 満たすべきこと

1. **何で調べたかを残す。** 実行したスキャナーの配布元と実体、検出データ、ルールや方針の版・鮮度を確認する。検査対象、除外した範囲、何を検出する検査かも明確にする。
2. **結果と失敗を分ける。** 検査が必要な範囲を終えたか確かめ、「指摘なし」「指摘あり」「評価不能」を分ける。終了コード0や結果0件だけで「指摘なし」にしない。一部で指摘が見つかり、別の部分が失敗した場合は両方を残す。
3. **後続の判断へ安全に渡す。** 必要な識別情報を残しつつ、見つけた秘密情報や不要なソースの抜粋を記録に複製しない。指摘の除外はルール・対象・期限を絞った[GOV-002](../psb-gov-002-security-exception-lifecycle/README.md)の例外で扱う。AIによる説明や修正案だけで受入を決めない。

二つ目のスキャナーは、固有の検出や確認の価値が、増える保守・侵害リスクに見合う場合に選びます。ツールを増やすこと自体は成果ではありません。

## 境界を分ける

取得処理は配布元へ接続し、チェックサム・署名・発行者を検証します。検出データの更新処理は、内容のダイジェスト、形式、作成時刻、有効期限を記録します。検査処理には対象の成果物と読取り専用の入力だけを渡し、リリース用の認証情報を持たせません。
出力の正規化では、製品固有の状態を`CLEAN`・`FINDING`・`ERROR`へ変換します。未知の状態や欠けた項目を`CLEAN`で補いません。後続の判断では、検出件数だけでなく、検査の正常完了と対象の一致を確認します。

複数の対象やカテゴリをまとめるときは、それぞれの完了状態と指摘を別に残します。予定した範囲がすべて完了し、受入を止める指摘がなければ`CLEAN`、完了して受入を止める指摘があれば`FINDING`です。受入を止めない指摘も結果から消しません。一つでも必要な範囲が評価不能なら全体は`ERROR`とし、既に得た指摘を消さずに調査へ渡します。これは集約結果の扱いであり、各toolの終了コードの意味は採用版と出力modeで確認します。

## ツールを追加するときの選び方

ツールを追加する前に、共通のテスト対象で重複する検出と固有の検出を比較します。配布経路、通信先、必要な認証情報、更新頻度、出力の意味も判断材料にします。
修正支援ツールは検査結果の正本を置き換えず、元の検出結果へ辿れる説明を提供します。この設計ではAIによる説明を別の処理へ分け、許可・拒否の条件にしません。外部サービスへ送信する情報の分類と保存期間も確認します。

## 保存する証拠と例外

通常保存するのはツール・検出データ・方針・検査対象の識別情報と、検出カテゴリ、重大度、ルール、状態、時刻です。検出した秘密情報やソースの抜粋を長期保存用の証拠へ複製しません。
検出結果の例外は特定のルール・対象・成果物へ限定し、[共通の例外管理](../psb-gov-002-security-exception-lifecycle/README.md)を利用します。ツール、データ取得、出力解析、検査範囲の異常は、リスクを受容する例外ではなく`ERROR`です。

既知の試験対象で検出できても、全対象の網羅性、検出データの最新性、未知脆弱性の不在は証明できません。旧Trivy 0.72.0とDockSec 2026.7.5のadapterは移植せず、採用時に仕様と配布物を再確認します。

## 診断で確認する項目（異常時テスト）

- ツールや検出データが入れ替わった、または古くなったとき、同じ検査結果として受け入れていないか。
- タイムアウト、対象の欠落、不正な出力、未知の終了状態を「指摘なし」にしていないか。
- 一部で指摘が見つかり別の部分が失敗したとき、指摘か失敗のどちらかを消していないか。
- 検査対象の変更だけでルールや除外設定を弱め、指摘を隠せないか。
- 結果の保存先へ認証情報を複製したり、AIの説明だけでマージ・リリースを許可したりしていないか。

ここに書いたのは確認項目であり、実際のスキャナーやCIを検査した結果ではありません。

## フレームワークとの関係

- NIST SP 800-190 §4.1.1（コンテナイメージの脆弱性検査）を**部分的に支えます**。検査結果を対象イメージ、検出データ、対象範囲、完了状態へ結び付ける点が対応します。すべてのイメージや稼働環境を検査したことは示しません。

対応する特性と限界は[マッピング](../../../../mappings/frameworks.yaml)に記録しています。設計上の関係であり、実環境での検査や準拠を示すものではありません。

## このコントロールの範囲

依存関係、コンテナ、IaC、秘密情報、SBOM、ワークフローなどの検査に使えます。一つのツールがすべてを調べる必要はありません。指摘が0件でも、対象外のコードや未知の脆弱性まで安全とは言えません。CIで結果を必須検査に接続する方法は[別のengineering](../../../../engineering/workflow-analysis-gate-and-reporting.md)で扱います。

具体的な場面は[教材](learning.md)、スキャナーの取得・検出データ・結果の扱いは上の方式説明を参照してください。8つの特性と根拠のIDは[control.yaml](control.yaml)、資料の採否は[Sources](../../../../sources/README.md#ref-scanner-evidence-001)、フレームワークとの関係は[マッピング](../../../../mappings/frameworks.yaml)にあります。

調査・対応・復旧のつなぎ方は[問題の発見から対応・再開まで](../../../../engineering/security-signal-to-response.md)を参照してください。
