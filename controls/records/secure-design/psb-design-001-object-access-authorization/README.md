# PSB-DESIGN-001: Object access authorization

**ログイン済みの利用者が対象IDを変えても、他人や別tenantのデータを操作できないか。**

## なぜ必要か

たとえば自分の請求書を開いた利用者がURLの請求書IDを他人のものに変える。ログイン済みというだけで読めたり更新できたりすれば、対象ごとの認可が抜けています。

## 満たすべきこと

- 利用者とtenantは認証済みの情報から、対象の所有者とtenantはサーバー側の記録から確認する。リクエスト中の`owner_id`や`tenant_id`を許可の根拠にしない。
- 読取り、更新、削除、exportを操作ごとに許可する。対象の取得・変更条件にも利用者とtenantを結び付け、確認後に別の対象へすり替わらないようにする。
- 一覧、検索、batch、非同期処理、cacheから同じ対象に届く場合も認可する。
- 認証情報や所有関係を確認できないときは処理を許可せず、障害として分けて扱う。

<a id="failure-checks"></a>

## 診断で確認する項目（異常時テスト）

- 利用者Aが利用者Bや別tenantの対象IDを指定しても、読取り・更新・削除・exportができないか。
- 読取りだけ許可された利用者が、更新など別の操作を実行できないか。
- `owner_id`や`tenant_id`を書き換えたリクエスト、一覧・検索・batch・非同期処理・cacheで認可を迂回できないか。
- 許可確認後に所有関係が変わった場合や、認可情報の取得が失敗した場合に処理を続けないか。

これは設計レビューや診断で使う項目であり、対象アプリで試験した記録ではありません。

## フレームワークとの関係

| 参照先 | このControlとの関係 | 限界 |
| --- | --- | --- |
| OWASP ASVS 5.0.0 V8.2.1 | 請求書の閲覧・更新を、操作ごとに許可する設計が機能単位の認可要件を部分的に支える。 | すべての機能や認証の正しさは確認していない。 |
| OWASP ASVS 5.0.0 V8.2.2 | 所有者とtenantをサーバ側で照合する設計が、対象データごとの認可を部分的に支える。 | 一覧・一括処理・cacheなど全経路は確認していない。 |

対応する特性と根拠は[フレームワーク・マッピング](../../../../mappings/frameworks.yaml)にあります。これはモデル化した請求書操作との設計上の関係で、ASVSへの適合を示しません。

## このコントロールの範囲

対象はアプリケーション内の利用者・tenant・対象・操作の関係です。認証方式、管理者権限、すべてのendpointの安全性まで保証しません。Webアプリ共通の検証要件は[ASVS 5.0.0](../../../../sources/README.md#spec-owasp-asvs-5-0-0)を参照してください。本件とV8.2.1・V8.2.2の関係は、対象データと操作の認可に限る[部分的な対応](../../../../mappings/frameworks.yaml)です。
