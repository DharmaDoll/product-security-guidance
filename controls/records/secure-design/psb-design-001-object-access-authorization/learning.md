# 学習：ログイン済みでも他人の請求書は読めない

[コントロール記録](README.md) · [設計パターン](../../../../engineering/secure-design/object-access-boundary/README.md)

## 正規利用者が攻撃者になる

架空の場面です。利用者Aが自分の請求書画面を開き、APIへ送る請求書IDを利用者Bのものへ変えます。
この要求のログイン情報は正規です。認証は「誰か」を確認しますが、「この請求書を読んでよいか」という認可までは決めません。

この例では、同じ組織の請求書でも、所有者本人にだけ操作を許します。共有や代理操作はない前提です。サーバーが請求書の所有者と利用者を照合すれば、AへBの請求書を返す経路を止められます。推測しにくいIDにすることだけでは、既にIDを知っている利用者の操作を防げません。

組織や顧客を分ける単位をtenant（テナント）と呼びます。別のテナントにも同じ利用者IDがある構成では、利用者IDだけの照合で他社のデータを返してしまう可能性があります。「誰が」「どの組織の」「どの請求書へ」「何をするか」を一緒に確認します。

## リクエストの自己申告を、許可の根拠にしない

リクエストの請求書IDは「どれにアクセスしたいか」という指定です。それだけでは、操作してよい証拠にはなりません。
ログイン情報から確認した利用者・所属組織と、データベースに保存された請求書の所有者・所属組織を照合します。

例えばAがリクエストに`owner_id=A`と書いても、Bの請求書をAのものとして扱ってはいけません。`tenant_id`を書き換えた場合も同じです。更新内容を丸ごとデータベースへ渡すと、所有者や所属組織まで変更される経路が生まれます。通常の更新で変更できる項目は、説明文など必要なものに限ります。

署名や来歴が正規のイメージでも、アプリの認可の欠陥は残ります。[成果物を使ってよいかの判断](../../release-integrity/psb-rel-001-signature-provenance-verification/learning.md)と、利用者に請求書の操作を許す判断は別です。

## この場面でどう判断するか

AがBの請求書IDを指定したなら、ログイン済みでも閲覧・更新を拒否します。画面でリンクや編集ボタンを隠すだけでは、APIへ直接送る要求を止められません。サーバー側で確認が必要です。

A自身の請求書であっても、Aに閲覧だけを許す設定なら更新は拒否します。所有者の一致は、すべての操作を許可する理由にはなりません。共有、代理操作、管理者の操作が必要になった場合も、例外として無条件に通すのではなく、許す関係と操作を別に定めます。

所有者を確認した後、実際に書き込むまでの間に所有関係が変わる場合も考えます。確認時の結果だけを使い、請求書IDだけで更新すると、既に権限を失った相手のデータを書き換えかねません。対象の取得・変更条件にも所有者とテナントを含め、許可判断と実際の操作が食い違わない設計にします。具体的な方法は[設計パターン](../../../../engineering/secure-design/object-access-boundary/README.md)で扱います。

認可に必要な情報を取得できなければ、読取りや更新を進めません。これは「他人の請求書だから拒否した」とは別の障害です。以前の許可や、リクエストに書かれた所有者へ頼って処理を続けないようにします。

## 別の入口から同じ請求書へ届かないか

一件ずつ開く画面を守っても、一覧、検索、ファイルへの出力、一括処理から他人の請求書が返れば情報は漏れます。後で実行する非同期処理も、対象と操作の認可を確認する経路です。

一度取得した結果をキャッシュへ保存する場合は、別の利用者やテナントへ同じ結果を返さないか、権限が変わった後も古い許可で読めないかを確認します。

対象が存在しない場合と権限がない場合を同じ応答にしても、それだけですべての情報漏えいを防げるわけではありません。例えば応答時間の違いから存在を推測される可能性は、別に検討します。

## 振り返りで確認すること

- 利用者・テナント・対象・操作のどれを、何の情報から確認しているか。
- 閲覧できることを、更新・削除・出力もできる理由にしていないか。
- 一覧、検索、一括処理、非同期処理、キャッシュにも同じ認可が必要だと確認したか。
- 所有関係の変更や情報取得の失敗が起きても、古い許可や自己申告を使って処理を続けないか。

設計入力は[参照資料と採否](../../../../sources/README.md#ref-application-authorization-001)に記録したOWASP Authorization Cheat Sheetです。請求書のシナリオは本PJ独自の教材です。Webアプリ共通の検証要件は[ASVS 5.0.0](../../../../sources/README.md#spec-owasp-asvs-5-0-0)、このcontrolとの部分的な関係は[README](README.md#フレームワークとの関係)からたどれます。

[REF-PORTFOLIO-001](../../../../sources/README.md#ref-portfolio-001)のアプリケーション層を扱い、供給経路の12段階へ無理に割り当てません。教材と診断項目で判断を支える主題とし、アプリ診断の実装例は追加していません。実アプリでの認可の強制や、同時に変更が起きる場合の動作は未確認です。
