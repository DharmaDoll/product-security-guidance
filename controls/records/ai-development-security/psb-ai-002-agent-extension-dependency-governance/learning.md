# 承認したSkillでも、更新後まで同じように使ってよいか

[コントロール記録](README.md) · [設計パターン](../../../../engineering/ai-development-security/agent-extension-admission/README.md)

## レビュー用Skillを更新したとき

チームが採用したSkillは、変更差分を読み、問題を説明するためのものでした。更新版には「診断情報を送るために認証設定を読み取る」という指示が追加されました。
同じ名前のSkillでも、審査対象の内容と必要な権限が変わっています。過去の承認をそのまま使うと、review用の拡張が認証情報を持ち出す入口になり得ます。

## 先に答えを押さえる

この更新は、以前の承認だけで使い始めず、追加された読取りと送信を確認します。コードの差分をレビューするために、開発者の認証設定まで送る必要は通常ありません。このシナリオでは、その追加処理を認めず、取り除いた版を審査するか、別の拡張を選びます。

見る順番は「何を頼みたいか → 何を読み、どこへ送るか → その仕事に必要か」です。よく知られた名前、正しい署名、読取り専用という説明だけでは、目的に合うかは決まりません。AI-001ではチームの指示変更を確認しました。AI-002では、追加・更新する拡張の内容と必要な権限を確認します。

## 何を審査したのか

Commitとdigestは内容を識別します。その内容を読んだ人、許可した権限、評価で観測した挙動、承認期限まで結び付けることで、採用判断を説明できます。
これはコードだけでなく、agentへ渡す文章にも必要です。文章自体がOS権限を持たなくても、agentが持つtoolを使わせようとすることがあります。

内容審査では、指示の目的だけでなく、対象ファイル、通信先、返す情報、更新時の処理をたどります。
「読取専用」と説明されたtoolも、どこから何を読み、どこへ返すかで影響が変わります。表示名や説明だけを根拠に権限を付けないことが出発点です。

## 採用の承認と、権限を渡す判断を分ける

このSkillの用途はコードレビューです。必要なのは対象の差分を読むことで、開発者の認証設定を読むことではありません。診断という説明が付いていても、必要性、取得する内容、送信先が変わったなら、以前の承認のまま使わず見直します。

さらに、Skillの本文が承認時と同じでも、呼び出すagentに新しい権限を与えたら影響が変わります。昨日は読めなかった認証キャッシュが今日は見えるかもしれません。内容の固定だけでは、実際に使える権限の固定にはなりません。

| 採用時に確かめること | 実行側へ渡す条件 |
|---|---|
| どの仕事をさせるか | 対象リポジトリ、必要なファイル、許す操作 |
| どの内容を承認したか | 取得元、版、配布物と参照ファイルの識別情報 |
| どの権限が必要か | 認証情報の用途・対象・期限、必要な通信先 |
| 何が変わったら止めるか | 内容・起動方法・接続先・権限の変更、承認の期限切れや取消 |

ここでいう「渡す」は、すべての拡張へ秘密値を配ることではありません。文章を読むSkill、ローカルで動く処理、外部のMCPサービスでは、秘密を持つ主体も強制できる場所も違います。必要な操作だけを仲介する方式でも、仲介先が何でも実行してよいわけではありません。

[利用者提供資料の権限ペアリングの観点](../../../../sources/README.md#ref-user-agent-isolation-pairing-001)は、この採用判断を[AI-004の実行環境設計](../../../../engineering/ai-development-security/development-runtime-isolation/README.md#credential-operation-pairing)へ渡すために使います。少ない権限のtokenを渡しても、別の強い鍵を読めるなら、その経路も制限する必要があります。

## 名前・署名・読取り専用という説明だけで決めない

署名やdigestの一致は、確認した出所や内容との対応を調べる材料です。目的に合うことや、秘密情報を送信しないことまで証明しません。「読取り専用」でも、機密ファイルを読み外部へ返す処理なら漏えいにつながります。書込み権限がないことと、渡してよい情報しか読めないことを分けます。

外部のMCPサービスでは、接続先の名前や公開されたソースが同じでも、実際の稼働内容を確認できない場合があります。その場合は未確認のまま記録し、送るデータや許す操作を狭める、確認できる方式へ切り替える、利用を見送る、といった判断をします。確認できない内容を推測で審査済みにしません。

## 審査を実行につなげる

問題のある更新を見つけたため、チームは承認を取り消しました。しかし、ある端末は古い承認をcacheし、別の端末では既にtoolの呼出しが始まっています。
このとき「台帳が失効になった」「次の呼出しを拒否した」「既存の処理を止めた」「外部変更の結果を確認した」は別の事実です。通知が届かない端末を調査済みへ含めたり、取消を外部変更の取り消し成功と読んだりしてはいけません。
対応時は拡張の内容と承認の版を特定し、未送信の呼出し、既存session、認証情報、送信済み操作を分けます。[設計側の受け渡し表](../../../../engineering/ai-development-security/agent-extension-admission/README.md#失効を実行環境へ渡す)で、それぞれの担当と完了条件を確認できます。

審査済みの内容を実行環境が読み込んでいるか確認します。Local pluginなら配布物と読み込み先、remote MCPなら接続先と稼働版の証拠を照合します。
審査結果の期限切れや失効情報の取得障害が起きたときに、どこで利用を止めるかも決めます。

この例では、認証情報へのアクセスと外部送信を実行環境で拒否すれば漏えいを止められます。
ただし、悪意ある指示の採用自体は別の問題です。審査と実行時の制限を両方使い、評価に通ったことを将来の全入力への保証にはしません。

## 判断の振り返り

- 更新版の署名は正しく、名前も同じです。以前なかった認証設定の読取りが追加されました。そのまま採用してよいでしょうか。**いいえ。署名の確認とは別に、変更した内容と権限の必要性を審査します。**
- 承認を取り消しましたが、接続できない端末があり、既に始まった処理も残っています。停止完了でしょうか。**いいえ。新規利用の拒否、動いている処理、認証情報、送信済み操作を分け、未確認の対象を残します。**
