# 開発agentに、どこまでの操作を任せるか

[コントロール記録](README.md) · [設計パターン](../../../../engineering/development-action-authorization.md)

## 「公開してよい」の後で何が変わったか

開発者はagentが作った修正を確認し、レビュー用branchへの公開を承認しました。ところが、リポジトリ内の作業用scriptには、別のremoteへ送信する処理が含まれていました。
Agentがscriptを実行でき、公開用の認証情報も使えれば、承認したつもりの範囲を越えてソースを送信できます。悪意あるscriptがあっても、公開権限がなく送信経路も閉じていれば、この経路は成立しません。

問題は確認画面の有無ではなく、確認した対象と実際の操作が同じかどうかです。

## 三つの判断を分ける

1. **読み込んでよいか**：その拡張や指示を採用する判断。内容の審査は、後のすべての操作を許可するものではありません。
2. **この操作をしてよいか**：誰が、どのリポジトリ・branchへ、どの内容を、どの方法で公開するかを決める判断。
3. **実際にどうなったか**：実行先が受け付けたか、変更したかを確認する判断。送信したことも、応答がないことも、結果の確定とは違います。

認可とは、特定の主体による特定の操作を許可することです。承認はその入力になり得ますが、agent自身が対象を書き換えたり、有効期限を延ばしたりできるなら強制力がありません。

## 応答が失われたら

公開要求を送った直後に通信が切れました。実行先では成功していても、開発端末では結果が分かりません。
同じ承認を使って再送すると、操作によっては重複したリリースや変更を作ります。元の要求の識別情報を保って実行先を確認し、結果不明を成功・未実行へ置き換えないことが重要です。

## 作業用トークンを絞っても、別の鍵を使えたら意味がない

先ほどの公開作業で、レビュー用リポジトリだけに使える短命トークンを渡したとします。ところが、agentが動く環境から、開発者のホームに保存された別の公開用の鍵も読めます。作業スクリプトがその鍵を使えれば、作業用トークンの制限を通らずに別のリポジトリへ送信できてしまいます。

確認するのは「何を渡したか」だけではありません。**その環境から他に何を使えるか**も一緒に見ます。ファイル、環境変数、認証キャッシュ、認証を代行するサービスが対象です。開発者の認証ディレクトリを読取り専用で渡しても、書換えを防ぐだけで、秘密を読むことは防げません。

この作業なら、修正とテストをする環境には必要なソースとテスト用の権限だけを渡し、公開は対象を確かめる別の経路へ分ける設計を考えます。公開側で、送信先のリポジトリ、ブランチ、送るコミットが承認内容と一致するか確認します。Agentがその確認を通らず同じ公開権限を使えるなら、分けた効果はありません。

秘密を持つ仲介サービス（ブローカー）へ公開を頼む方式もあります。ただし、鍵を見せないことと、勝手な公開を防ぐことは別です。仲介側が任意の送信先を受け付ければ、秘密値が漏れなくても権限を悪用できます。

例えば、agentが認証情報を持たないまま「この成果物を公開して」と依頼できる構成を考えます。公開処理が秘密を管理していても、依頼された任意のリポジトリへ送れるなら、意図しない公開は止まりません。公開処理側で、誰の依頼か、どのリポジトリへ、どの成果物を送る承認なのかを確かめます。秘密値をモデルへ渡さず、許可した操作だけを実行する、という二つの条件が必要です。

公開先は、公開処理側で管理する許可リストに限定します。同じサービス内にも別の組織や公開リポジトリがあるため、ドメイン名だけでなく対象のリポジトリと操作まで絞ります。その一覧に入っていても、今回の成果物をそこへ公開する承認は別に確認します。Agent自身が許可リストを書き換えたり、別の鍵で公開処理を通らず送ったりできないことも必要です。

## Agent本体だけを制限していないか

開発作業では、agent本体のほかに、テスト用の子プロセス、MCPサーバ、hookなどが動くことがあります。実際に使う構成について、誰がファイルを読み、通信し、認証情報を使うかを分けて確認します。

| この場面で動くもの | 確認すること |
|---|---|
| Agent本体 | 作業用ソース以外の秘密や保護設定を読み書きできないか |
| テストや作業スクリプト | 親から別のトークンを引き継いだり、専用ツールの制限を通らず読み書き・送信したりできないか |
| MCPサーバやhook | どこで動き、誰の権限を使うか。Agent本体の隔離の外側で、同じ操作を代行できないか |

「sandboxを有効にした」という設定名だけでは、この表を埋められません。対象のツールとプロセス、読み書きできる場所、通信経路を確認します。採用する方式の比較と診断項目は[実行環境の設計](../../../../engineering/development-runtime-isolation.md)にあります。

## 期限切れと、異常時の停止を分けて考える

テストが長引き、作業用トークンの期限が切れたとします。止まるのが不便だからと広い権限の永続キーに切り替えると、作業のために設けた制限がなくなります。更新が必要なら、同じ対象・操作の範囲で更新できる条件と、更新を打ち切る条件を先に決めます。短命でも更新元を自由に使えれば、作業の終了後まで権限を得続けられるためです。

一方、不審な公開を見つけてagentの画面を停止しても、子プロセスや外部MCPが処理を続けているかもしれません。トークンが外へ漏れていれば、その環境を止めても別の端末から利用され得ます。動いている処理、認証情報の利用・更新、通信をそれぞれ止める必要があるか判断します。既に送った公開要求については、上の「応答が失われたら」と同じく、送信先の結果を確認します。

停止方法は状況に応じて選びます。一つずつ順番に試す義務はなく、被害が続くなら必要な遮断を並行して進めます。漏えいした認証情報の失効と利用履歴の調査は[GOV-004](../../governance-operations/psb-gov-004-credential-exposure-containment/README.md)へ引き継ぎます。

ここまでの判断例は、[利用者提供の多層隔離・権限ペアリング資料](../../../../sources/README.md#ref-user-agent-isolation-pairing-001)を開発作業に当てはめた解説です。原文の製品設定や固定の有効期間を、そのまま推奨構成にはしていません。設計の詳しい選択肢は[認証情報と操作を一緒に決める](../../../../engineering/development-runtime-isolation.md#credential-operation-pairing)へ進んでください。

## Codex CLIでリポジトリをtrustedにする前に

別の開発者から受け取ったリポジトリをCodex CLIで開く場面を考えます。`AGENTS.md`に「ネットワークへ送信しない」と書かれていても、それはagentへの指示です。実際の権限は設定と実行環境で決まります。Trusted projectの`.codex/config.toml`はuser設定より優先されるため、信頼の判断にはリポジトリ内の設定を読ませるかという判断も含まれます。管理側のrequirementsは別の強制層です。

ここで確認するのは、(1) project設定、起動時の指定、管理方針を合わせた実効権限、(2) shell以外のWeb検索・MCP・hookを含む外部経路、(3) 設定とローカル履歴に秘密情報が残る経路です。例えばshellの通信を閉じても、別のtoolに通信経路があれば「外部へ出ない」とは判定できません。履歴を抑える設定についても、どの保存物に効くかを分けて確認します。

このシナリオは[Codex CLI Hardening Cheatsheetと公式資料の照合](../../../../sources/README.md#ref-codex-cli-hardening-001)から得た確認観点です。特定の設定例をそのまま適用する手順ではなく、実効権限の診断も未実施です。境界の置き方は[Development runtime isolation](../../../../engineering/development-runtime-isolation.md)へ進みます。

## 設計レビューで問うこと

- 人が見た対象と実行対象を、どこで照合するか。
- Agentが持つ別の認証情報やshell経由で、その照合を迂回できないか。
- 一つの承認を二つの処理が同時に使用したらどうなるか。
- 結果不明の操作を誰が調べ、どの条件なら再実行するか。
- Trusted projectの設定を変更すると、user設定だけを確認した時より到達範囲が広がらないか。
- Shell、Web検索、MCP、hook、履歴を別々に確認し、未確認の経路を「拒否済み」としていないか。

具体的な方式と代償は[Development action authorization](../../../../engineering/development-action-authorization.md)へ分けています。
供給経路では[攻撃段階3から2・6への受け渡し](../../../../docs/ANALYSIS_LENSES.md)に当たります。資料の版と、この教材における解釈は[参照資料](../../../../sources/README.md#ref-development-action-authorization-001)で確認できます。

対応する成果物：[コントロール記録](README.md) · [Development action authorization](../../../../engineering/development-action-authorization.md)

## 判断の振り返り

- 作業用トークンは短命ですが、agentが開発者の別の鍵を読めます。権限を限定できていますか。**いいえ。渡したトークン以外の経路も閉じる必要があります。**
- 仲介サービスが秘密値を隠してくれます。公開先の確認は省けますか。**省けません。鍵の露出を防ぐことと、その鍵で何を許すかは別の判断です。**
- Agentを終了しました。異常な公開への対応は完了ですか。**まだ判断できません。残る処理や権限、既に送信した操作の結果を確認します。**
